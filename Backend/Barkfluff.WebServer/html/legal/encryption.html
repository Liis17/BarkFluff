Техническое описание шифрования

Действует с 24 января 2026 г. Обновлено 14 мая 2026 г.

1. Введение

Безопасность и конфиденциальность пользовательских данных — приоритет Barkfluff. Настоящий документ предоставляет детальное техническое описание методов шифрования, применяемых на всех уровнях системы.

1.1 Уровни защиты

Barkfluff применяет многоуровневую защиту:

  1. Шифрование в состоянии покоя (Encryption at Rest) — защита данных, хранящихся на серверах
  2. Шифрование при передаче (Encryption in Transit) — защита данных при передаче по сети
  3. Шифрование на стороне клиента (Client-Side Encryption) — защита данных на устройстве пользователя
  4. Контроль доступа (Access Control) — ограничение доступа к данным на уровне приложения

Примечание: End-to-End шифрование (E2EE) в настоящее время не реализовано, но рассматривается на будущее.

2. Шифрование в состоянии покоя

2.1 База данных PostgreSQL

2.1.1 Transparent Data Encryption (TDE)

Метод: все данные в PostgreSQL защищены на уровне хранилища с использованием TDE.

  • Данные автоматически шифруются при записи на диск
  • Данные автоматически расшифровываются при чтении (прозрачно для приложения)
  • Шифрование происходит на уровне страниц базы данных (8 КБ блоки)

Алгоритм: AES-256 (CBC или XTS).

Управление ключами:

  • Мастер-ключ хранится в защищённом хранилище ключей (KMS)
  • Ключи шифрования регулярно ротируются

Что защищено:

  • Все таблицы во всех микросервисах (Identity, Users, Messages, Files, Onliner, FastAuth, Notification, Updates и др.)
  • Хеши паролей (bcrypt с cost factor 12)
  • Refresh Tokens (зашифрованы AES-256 перед сохранением)
  • Сообщения (текст, метаданные)
  • Журналы безопасности

2.1.2 Шифрование на уровне столбцов

Для особо чувствительных данных применяется дополнительное шифрование на уровне столбцов:

  • Identity.Users.PasswordHash — хеш пароля (bcrypt + AES-256)
  • Identity.RefreshTokens.Token — токены обновления (AES-256-GCM)
  • Identity.TwoFactorSecrets.Secret — секреты 2FA (AES-256-GCM)

2.2 Файловое хранилище Minio (S3-compatible)

2.2.1 Server-Side Encryption (SSE)

Метод: все файлы автоматически шифруются на стороне сервера при загрузке.

  • Алгоритм: AES-256-GCM (Galois/Counter Mode)
  • Аутентичное шифрование — защита от подделки данных

Режим: SSE-S3 (Minio управляет ключами) или SSE-KMS (ключи во внешнем KMS).

Что защищено:

  • Аватары и постеры пользователей
  • Вложения в сообщениях (изображения, видео, документы)
  • Превью файлов (thumbnails)
  • Дистрибутивы клиентских приложений (через ClientStorage)

2.3 Кеш Redis

Назначение: Redis используется в сервисе Messages для кеширования метаданных чатов — это технический кеш без персональных сообщений.

Что хранится в Redis:

  • Имена чатов (chat_name_{chatId}_{userId}) — отображаемые названия для списка чатов
  • Аватары чатов (chat_image_{chatId}_{userId}) — URL превью изображений чатов

Что НЕ хранится в Redis: содержимое сообщений, онлайн-статусы пользователей.

Защита:

  • Шифрование TLS для соединений между сервисами и Redis
  • Аутентификация по паролю
  • Изоляция сети: Redis недоступен извне, только из внутренней сети Docker

2.4 Шифрование на стороне клиента

Каждый клиент Barkfluff хранит локально access/refresh-токены, Device ID и часть пользовательских настроек. Чувствительные данные шифруются с использованием стандартных платформенных хранилищ:

ПлатформаХранениеШифрование
Windows (WPF) %AppData%\BarkFluff\GlobalParam.json + локальный кеш сообщений (LiteDB) AES-256-CBC, ключ — производный от PIN-кода (PBKDF2). При отсутствии PIN — DPAPI на уровне пользователя ОС
Android (Kotlin) EncryptedSharedPreferences + локальный кеш в защищённой области приложения Android Keystore (AES-256-GCM, ключи изолированы в системном хранилище)
macOS (SwiftUI) Keychain + sandbox-каталог приложения Apple Keychain Services (AES-256-GCM, защита Secure Enclave при наличии)
iOS (в разработке) Keychain + sandbox-каталог приложения Apple Keychain Services + Data Protection (AES-256-GCM)
Linux Qt (в разработке) Конфигурационные файлы пользователя + Secret Service (libsecret) Хранение секретов через системный keyring (gnome-keyring / KWallet)
Web Память вкладки + защищённые cookies HTTPS-only / SameSite-cookies, без долговременного хранения refresh-токена в localStorage

3. Шифрование при передаче

3.1 gRPC / HTTP/2 с TLS 1.3

Все соединения между клиентом и сервером защищены протоколом TLS 1.3.

Преимущества TLS 1.3:

  • Более быстрое рукопожатие (0-RTT и 1-RTT)
  • Удаление устаревших алгоритмов (RC4, MD5, SHA-1, DES)
  • Perfect Forward Secrecy

Поддерживаемые cipher suites:

  • TLS_AES_256_GCM_SHA384 (рекомендуется)
  • TLS_CHACHA20_POLY1305_SHA256
  • TLS_AES_128_GCM_SHA256

Веб-клиент работает через gRPC-Web-прокси (сервис BarkFluff.Web на порту 7016) с тем же TLS-конвейером.

3.2 RabbitMQ с TLS

Внутренние асинхронные события между микросервисами доставляются через RabbitMQ (MassTransit). Соединения защищены TLS, доступ к брокеру изолирован внутренней сетью Docker.

3.3 Внутренние gRPC-вызовы

Межсервисные gRPC-вызовы используют клиентские интерсепторы (JwtClientInterceptor, ExceptionClientInterceptor) и сервисные JWT-токены (TokenType.Service) для авторизации.

4. End-to-End шифрование (E2EE)

4.1 Текущий статус

End-to-End шифрование в настоящее время не реализовано. Это означает:

  • Сервер имеет техническую возможность доступа к содержимому сообщений
  • Сообщения защищены на уровне хранилища (TDE, AES-256-GCM)
  • Сообщения защищены при передаче (TLS 1.3)
  • Применяется строгий контроль доступа

4.2 Планируемая реализация E2EE

Архитектура E2EE для приватных чатов (предварительная):

4.2.1 Генерация ключей

  1. Клиент генерирует пару ключей (Public/Private) с использованием Curve25519 (ECDH)
  2. Public Key отправляется на сервер и хранится в базе данных
  3. Private Key хранится только на устройстве клиента (зашифрованный с помощью PIN-кода)

Алгоритмы:

  • Обмен ключами: X25519 (ECDH)
  • Симметричное шифрование: AES-256-GCM
  • Подпись сообщений: Ed25519

4.2.2 Отправка сообщения

  1. Клиент A запрашивает Public Key пользователя B с сервера
  2. Клиент A выполняет ECDH с Public Key пользователя B и своим Private Key → получает Shared Secret
  3. Из Shared Secret выводится симметричный ключ AES-256 (через HKDF)
  4. Клиент A шифрует сообщение AES-256-GCM
  5. Клиент A отправляет зашифрованное сообщение

4.2.3 Компромиссы E2EE

  • Невозможен поиск по содержимому на сервере (только на клиенте)
  • Сложная синхронизация между устройствами (требуется экспорт ключей)
  • Невозможно восстановить сообщения при потере Private Key
  • Усложнение модерации запрещённого контента

5. Управление ключами (Key Management)

5.1 Хранение мастер-ключей

Для production мастер-ключи хранятся в KMS:

  • AWS KMS (если развёртывание на AWS)
  • Google Cloud KMS (если развёртывание на GCP)
  • HashiCorp Vault (для on-premise развёртываний)

5.2 Ротация ключей

  • Мастер-ключи БД: каждые 90 дней
  • TLS-сертификаты: каждые 90 дней (автоматически с Let's Encrypt)
  • JWT Secret: каждые 180 дней
  • Refresh Tokens: автоматически при каждом обновлении Access Token

6. Аутентификация и авторизация

6.1 XAuth и заголовки

Все микросервисы используют общую систему XAuth из BarkFluff.GrpcServer. Каждый запрос содержит обязательные metadata-заголовки (Base64):

  • x-auth-token — JWT (нестандартный заголовок вместо Authorization)
  • x-device-id, x-device-name, x-ip
  • x-os, x-app-name, x-app-version

Политики авторизации:

  • TokenType.User — User или Service токен
  • TokenType.Service — только Service токен (для межсервисных вызовов)

6.2 JWT (JSON Web Tokens)

  • Алгоритм подписи: HMAC-SHA256 (симметричный) или RS256 (асимметричный)
  • Срок действия Access Token: 15 минут
  • Длина секретного ключа: 256 бит
  • Секретный ключ хранится в Configuration-сервисе

6.3 Refresh Tokens

  • Формат: UUID v4 (128 бит энтропии)
  • Хранение: Identity.RefreshTokens в PostgreSQL, привязаны к Device ID
  • Срок действия: 30 дней

6.4 QR-авторизация (FastAuth)

Сервис FastAuth позволяет авторизовать новое устройство, отсканировав QR-код в уже залогиненном клиенте. Обмен короткоживущими одноразовыми кодами проходит по тому же TLS-каналу и не раскрывает refresh-токен.

7. Защита от атак

7.1 Защита от Man-in-the-Middle (MITM)

  • TLS 1.3 с проверкой сертификатов
  • HSTS (HTTP Strict Transport Security)
  • Certificate Transparency

7.2 Защита от Replay-атак

  • Nonce: каждое сообщение содержит уникальный идентификатор
  • Timestamp: сообщения старше 5 минут отклоняются
  • GCM-режим AES автоматически защищает от повторной отправки

7.3 Защита от Brute-Force

На пароли:

  • bcrypt с cost factor 12 (генерация хеша занимает ~250 мс)
  • Rate Limiting: максимум 5 попыток входа за 15 минут

На 2FA-коды:

  • TOTP: коды меняются каждые 30 секунд
  • Rate Limiting: максимум 3 неверных попытки

8. Соответствие стандартам

8.1 GDPR

  • Шифрование данных at rest и in transit
  • Псевдонимизация: UserId используется вместо реальных имён в логах
  • Право на удаление: безопасное удаление ключей шифрования

8.2 FIPS 140-2

Алгоритмы, соответствующие FIPS 140-2:

  • AES-256 (FIPS approved)
  • SHA-256, SHA-384 (FIPS approved)
  • HMAC-SHA256 (FIPS approved)
  • RSA-2048 (FIPS approved)
