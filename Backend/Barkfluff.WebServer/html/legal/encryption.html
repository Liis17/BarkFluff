Техническое описание шифрования

Действует с: 24 января 2026 г. Обновлено: 29 июля 2026 г.

1. Введение

Эта страница описывает только те механизмы защиты и шифрования, которые присутствуют в текущей архитектуре Barkfluff. Она относится к программному обеспечению; конкретную конфигурацию — какие функции включены, какие ключи используются, как хранятся резервные копии — определяет администратор ноды, на которой создан ваш аккаунт.

2. Кто что видит: краткая сводка

Тип перепискиВидит ваша нодаВидит нода собеседника
Обычный чат внутри нодыСодержимое сообщений и файлы—
Private-чат (passphrase)Только шифротекст и метаданные—
Secret-чат (устройство-устройство)Только opaque envelope, временно—
Федеративный чат 1-к-1Содержимое сообщений и файлыСодержимое сообщений и файлы

Сквозного шифрования в федеративных чатах нет. Private- и secret-чаты работают только между пользователями одной ноды. Если вам нужно, чтобы содержимое не было доступно серверу вообще, — используйте private- или secret-чат внутри своей ноды.

3. Передача данных и авторизация

  • Клиенты взаимодействуют с backend через gRPC или gRPC-Web.
  • Внешний HTTP/gRPC-трафик проходит через HTTPS/TLS на публичном контуре.
  • Внутренние события между сервисами передаются через RabbitMQ / MassTransit.
  • Авторизация gRPC-запросов использует XAuth metadata, включая x-auth-token и device-заголовки.

4. JWT, refresh-токены и 2FA

  • Access token — JWT, подписанный ключом из конфигурации Identity вашей ноды.
  • Время жизни access token задается JwtSettings:ExpiryMinutes.
  • Refresh token хранится в Identity.RefreshTokens и привязан к Device ID.
  • Сессии можно просматривать и отзывать через GetActiveSessions и RemoveActiveSession.
  • 2FA поддерживает TOTP authenticator и email-коды.

5. Обычные сообщения

Обычные личные и групповые сообщения хранятся в Messages-сервисе вашей ноды. Серверная логика использует эти данные для списка чатов, истории сообщений, read receipts, редактирования, удаления, экспорта и realtime-обновлений. Администратор ноды имеет технический доступ к этой базе данных.

6. Private-чаты

Private-чаты — это 1-к-1 encrypted-чаты через passphrase внутри одной ноды.

  • Клиент создает соль kdf_salt и passphrase_verifier.
  • Ключ выводится на клиенте из passphrase и соли чата.
  • Сообщение отправляется как ciphertext, nonce и associated_data.
  • Нода хранит EncryptedMessage как opaque blob и не получает passphrase.
  • Редактирование private-сообщения заменяет ciphertext/nonce/AAD.
  • Удаление private-сообщения помечает его удаленным и очищает ciphertext.

7. Secret-чаты

Secret-чаты — это 1-к-1 чаты между конкретными устройствами внутри одной ноды.

  • Устройства регистрируют prekey bundle: identity key, signed prekey и one-time prekeys.
  • Инициатор получает prekey bundle устройства собеседника через FetchPrekeyBundle.
  • Сообщения передаются как opaque SecretEnvelope.
  • Нода не создает обычный Chat и не сохраняет историю secret-чата в Messages DB.
  • Envelope ретранслируется получателю и временно буферизуется с TTL 24 часа, если получатель офлайн.
  • После AckSecretMessage envelope удаляется из буфера.

8. Защита канала между нодами

Федеративный трафик идет по отдельному защищенному каналу. Он защищает переписку от подмены и перехвата в пути, но не скрывает содержимое от самих нод.

  • TLS с пиннингом ключа: соединение принимается, только если отпечаток публичного ключа сертификата (SPKI, SHA-256) совпадает с известным для этой ноды. Цепочка удостоверяющих центров при этом намеренно не используется; пустой список отпечатков означает отказ соединяться.
  • Подпись каждого запроса: отправитель подписывает каноническую строку из имени своей ноды, имени ноды-получателя, времени, имени вызываемого метода и хеша тела запроса.
  • Окно времени: подпись действует ограниченное время (по умолчанию 5 минут), что закрывает повтор перехваченного запроса.
  • Подпись каждого события: сообщения, правки, удаления и отметки о прочтении подписываются Ed25519-ключом ноды-отправителя отдельно от подписи транспорта.
  • Идентичность ноды: ключи публикуются в подписанном документе по адресу /.well-known/barkfluff; при первом контакте они дополнительно сверяются через каталог Navigator. Смена ключей принимается, только если новый документ всё ещё содержит хотя бы один ранее доверенный ключ.
  • Ротация ключей: старый ключ остается действительным в течение окна перекрытия, чтобы доставка не прерывалась.
  • Дедупликация и лимиты: повторно доставленное событие не применяется дважды; на создание чатов, запросы файлов и индикаторы набора действуют лимиты частоты для каждой ноды.
  • Блоклист: администратор может заблокировать ноду — её запросы отклоняются.
  • Анти-SSRF: перед любым исходящим запросом имя ноды нормализуется (защита от похожих доменов), IP-литералы и приватные диапазоны отклоняются, соединение идет по уже проверенному адресу.

Чего этот канал не делает: он не мешает администратору ноды-получателя читать и хранить доставленные ему сообщения и файлы. Подпись подтверждает происхождение данных, а не добросовестность получателя.

9. Файлы

Файлы, аватары, постеры, вложения и превью обслуживаются Files-сервисом и хранятся в Minio/S3-совместимом хранилище вашей ноды. Метаданные файлов используются для скачивания, превью, экспорта и отображения в чатах.

В федеративном чате файлы не копируются на чужую ноду заранее: нода собеседника запрашивает их у вашей в момент открытия, и ваша нода перед выдачей проверяет, что запрашивающая нода действительно участвует в чате с этим вложением. Для аватаров вместо проверки чата применяются настройки приватности владельца.

11. Push-уведомления

CloudMessaging получает события из RabbitMQ и отправляет push-уведомления через Firebase Cloud Messaging, если администратор ноды включил эту функцию. Для secret-сообщений push не содержит текст сообщения.

Encryption: technical overview

Effective from: January 24, 2026. Updated: July 29, 2026.

1. Introduction

This page describes only those protection and encryption mechanisms that exist in the current Barkfluff architecture. It concerns the software; the specific configuration — which features are enabled, which keys are used, how backups are kept — is decided by the administrator of the node where your account was created.

2. Who sees what: a short summary

Type of conversationYour node seesThe other node sees
Regular chat within a nodeMessage content and files—
Private chat (passphrase)Ciphertext and metadata only—
Secret chat (device to device)An opaque envelope only, temporarily—
Federated 1-to-1 chatMessage content and filesMessage content and files

There is no end-to-end encryption in federated chats. Private and secret chats work only between users of the same node. If you need the content to be unavailable to the server at all, use a private or secret chat within your own node.

3. Data transfer and authorization

  • Clients talk to the backend via gRPC or gRPC-Web.
  • External HTTP/gRPC traffic goes through HTTPS/TLS on the public perimeter.
  • Internal events between services are delivered via RabbitMQ / MassTransit.
  • gRPC request authorization uses XAuth metadata, including x-auth-token and the device headers.

4. JWT, refresh tokens and 2FA

  • Access token — a JWT signed with a key from your node's Identity configuration.
  • The access token lifetime is set by JwtSettings:ExpiryMinutes.
  • The refresh token is stored in Identity.RefreshTokens and bound to the Device ID.
  • Sessions can be listed and revoked via GetActiveSessions and RemoveActiveSession.
  • 2FA supports a TOTP authenticator and email codes.

5. Regular messages

Regular private and group messages are stored in your node's Messages service. Server logic uses this data for the chat list, message history, read receipts, editing, deletion, export and realtime updates. The node administrator has technical access to this database.

6. Private chats

Private chats are 1-to-1 encrypted chats via a passphrase, within a single node.

  • The client creates the kdf_salt and the passphrase_verifier.
  • The key is derived on the client from the passphrase and the chat salt.
  • A message is sent as ciphertext, nonce and associated_data.
  • The node stores EncryptedMessage as an opaque blob and never receives the passphrase.
  • Editing a private message replaces the ciphertext/nonce/AAD.
  • Deleting a private message marks it as deleted and clears the ciphertext.

7. Secret chats

Secret chats are 1-to-1 chats between specific devices, within a single node.

  • Devices register a prekey bundle: identity key, signed prekey and one-time prekeys.
  • The initiator obtains the correspondent's device prekey bundle via FetchPrekeyBundle.
  • Messages are transmitted as an opaque SecretEnvelope.
  • The node does not create a regular Chat and does not store secret chat history in the Messages DB.
  • The envelope is relayed to the recipient and buffered temporarily with a 24-hour TTL if the recipient is offline.
  • After AckSecretMessage the envelope is removed from the buffer.

8. Protection of the inter-node channel

Federated traffic goes through a separate secured channel. It protects the conversation from tampering and interception in transit, but it does not hide the content from the nodes themselves.

  • TLS with key pinning: a connection is accepted only if the certificate's public key fingerprint (SPKI, SHA-256) matches the one known for that node. The certificate authority chain is deliberately not used; an empty fingerprint list means the connection is refused.
  • Per-request signature: the sender signs a canonical string built from its own node name, the destination node name, the timestamp, the name of the called method and a hash of the request body.
  • Time window: a signature is valid for a limited time (5 minutes by default), which closes off replay of an intercepted request.
  • Per-event signature: messages, edits, deletions and read receipts are signed with the sending node's Ed25519 key, separately from the transport signature.
  • Node identity: keys are published in a signed document at /.well-known/barkfluff; on first contact they are additionally cross-checked through the Navigator directory. A key change is accepted only if the new document still contains at least one previously trusted key.
  • Key rotation: the old key remains valid during an overlap window so that delivery is not interrupted.
  • Deduplication and limits: a redelivered event is not applied twice; chat creation, file requests and typing indicators are rate-limited per node.
  • Block list: an administrator can block a node — its requests are then rejected.
  • Anti-SSRF: before any outgoing request the node name is normalized (protection against look-alike domains), IP literals and private ranges are rejected, and the connection is made to the already validated address.

What this channel does not do: it does not prevent the receiving node's administrator from reading and storing the messages and files delivered to them. A signature proves the origin of the data, not the good faith of the recipient.

9. Files

Files, avatars, posters, attachments and previews are served by the Files service and stored in your node's Minio/S3-compatible storage. File metadata is used for downloads, previews, export and display in chats.

In a federated chat, files are not copied to the other node in advance: your correspondent's node requests them from yours at the moment they are opened, and your node first verifies that the requesting node really participates in a chat containing that attachment. For avatars, the owner's privacy settings apply instead of the chat check.

11. Push notifications

CloudMessaging receives events from RabbitMQ and sends push notifications via Firebase Cloud Messaging, if the node administrator has enabled this feature. For secret messages the push does not contain the message text.
