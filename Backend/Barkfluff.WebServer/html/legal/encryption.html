Техническое описание шифрования

Действует с: 24 января 2026 г. Обновлено: 17 июня 2026 г.

1. Введение

Эта страница описывает только те механизмы защиты и шифрования, которые присутствуют в текущей архитектуре Barkfluff.

2. Передача данных и авторизация

  • Клиенты взаимодействуют с backend через gRPC или gRPC-Web.
  • Внешний HTTP/gRPC-трафик проходит через HTTPS/TLS на публичном контуре.
  • Внутренние события между сервисами передаются через RabbitMQ / MassTransit.
  • Авторизация gRPC-запросов использует XAuth metadata, включая x-auth-token и device-заголовки.

3. JWT, refresh-токены и 2FA

  • Access token — JWT, подписанный ключом из конфигурации Identity.
  • Время жизни access token задается JwtSettings:ExpiryMinutes.
  • Refresh token хранится в Identity.RefreshTokens и привязан к Device ID.
  • Сессии можно просматривать и отзывать через GetActiveSessions и RemoveActiveSession.
  • 2FA поддерживает TOTP authenticator и email-коды.

4. Обычные сообщения

Обычные личные и групповые сообщения хранятся в Messages-сервисе. Серверная логика использует эти данные для списка чатов, истории сообщений, read receipts, редактирования, удаления, экспорта и realtime-обновлений.

5. Private-чаты

Private-чаты — это 1-к-1 encrypted-чаты через passphrase.

  • Клиент создает соль kdf_salt и passphrase_verifier.
  • Ключ выводится на клиенте из passphrase и соли чата.
  • Сообщение отправляется как ciphertext, nonce и associated_data.
  • Сервер хранит EncryptedMessage как opaque blob и не получает passphrase.
  • Редактирование private-сообщения заменяет ciphertext/nonce/AAD.
  • Удаление private-сообщения помечает его удаленным и очищает ciphertext.

6. Secret-чаты

Secret-чаты — это 1-к-1 чаты между конкретными устройствами.

  • Устройства регистрируют prekey bundle: identity key, signed prekey и one-time prekeys.
  • Инициатор получает prekey bundle устройства собеседника через FetchPrekeyBundle.
  • Сообщения передаются как opaque SecretEnvelope.
  • Сервер не создает обычный Chat и не сохраняет историю secret-чата в Messages DB.
  • Envelope ретранслируется получателю и временно буферизуется с TTL 24 часа, если получатель офлайн.
  • После AckSecretMessage envelope удаляется из буфера.

7. Файлы

Файлы, аватары, постеры, вложения и превью обслуживаются Files-сервисом и хранятся в Minio/S3-compatible хранилище. Метаданные файлов используются для скачивания, превью, экспорта и отображения в чатах.

8. Локальное хранение клиентов

КлиентЧто используется
Windows WPFGlobalParam.json, PIN-защита, локальные настройки клиента
AndroidGlobalParam, локальные настройки, Firebase token, key/prekey данные для encrypted/secret-чатов
macOSKeychain для токенов и локальные настройки приложения
WebgRPC-Web, cookies только для технических сценариев web-клиента и перехода с публичной страницы профиля

9. Push-уведомления

CloudMessaging получает события из RabbitMQ и отправляет push-уведомления через Firebase Cloud Messaging. Для secret-сообщений push не содержит текст сообщения.

Technical Encryption Overview

Effective from: January 24, 2026. Updated: June 17, 2026.

1. Introduction

This page describes only the protection and encryption mechanisms present in the current Barkfluff architecture.

2. Data transfer and authorization

  • Clients interact with the backend via gRPC or gRPC-Web.
  • External HTTP/gRPC traffic goes over HTTPS/TLS on the public perimeter.
  • Internal events between services are transmitted via RabbitMQ / MassTransit.
  • gRPC request authorization uses XAuth metadata, including x-auth-token and device headers.

3. JWT, refresh tokens and 2FA

  • Access token — a JWT signed with a key from the Identity configuration.
  • The access token lifetime is set by JwtSettings:ExpiryMinutes.
  • The refresh token is stored in Identity.RefreshTokens and bound to the Device ID.
  • Sessions can be viewed and revoked via GetActiveSessions and RemoveActiveSession.
  • 2FA supports a TOTP authenticator and email codes.

4. Regular messages

Regular private and group messages are stored in the Messages service. Server logic uses this data for the chat list, message history, read receipts, editing, deletion, export and realtime updates.

5. Private chats

Private chats are 1-to-1 encrypted chats secured by a passphrase.

  • The client generates a kdf_salt and a passphrase_verifier.
  • The key is derived on the client from the passphrase and chat salt.
  • A message is sent as ciphertext, nonce and associated_data.
  • The server stores EncryptedMessage as an opaque blob and never receives the passphrase.
  • Editing a private message replaces the ciphertext/nonce/AAD.
  • Deleting a private message marks it as deleted and clears the ciphertext.

6. Secret chats

Secret chats are 1-to-1 chats between specific devices.

  • Devices register a prekey bundle: identity key, signed prekey and one-time prekeys.
  • The initiator fetches the peer device's prekey bundle via FetchPrekeyBundle.
  • Messages are transmitted as an opaque SecretEnvelope.
  • The server does not create a regular Chat and does not store secret chat history in the Messages DB.
  • The envelope is relayed to the recipient and buffered temporarily with a 24-hour TTL if the recipient is offline.
  • After AckSecretMessage, the envelope is removed from the buffer.

7. Files

Files, avatars, posters, attachments and previews are served by the Files service and stored in a Minio/S3-compatible storage. File metadata is used for downloading, previews, export and display in chats.

8. Client local storage

ClientWhat is used
Windows WPFGlobalParam.json, PIN protection, local client settings
AndroidGlobalParam, local settings, Firebase token, key/prekey data for encrypted/secret chats
macOSKeychain for tokens and local app settings
WebgRPC-Web, cookies only for technical web-client scenarios and the transition from a public profile page

9. Push notifications

CloudMessaging receives events from RabbitMQ and sends push notifications via Firebase Cloud Messaging. For secret messages, the push does not contain the message text.
