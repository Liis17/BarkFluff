# Web — сетевые операции и восстановление

Заметка фиксирует текущее поведение браузерного клиента. Основные реализации: `Backend/BarkFluff.Web/wwwroot/js/app/network.js`, `clients.js`, `realtime.js`, `connection.js`, `files.js`, `drafts.js`, `pending-sends.js` и `send-queue.js`.

## Unary gRPC-Web и авторизация

`BF.network.unary` оборачивает callback-style gRPC-Web вызовы. Перед каждой попыткой он копирует metadata и задаёт абсолютный `deadline`; завершает Promise по таймауту, отмене или callback, вызывает `call.cancel()` при timeout/AbortSignal и игнорирует поздний callback. Ошибки нормализуются в `timeout`, `cancelled`, `transport` или `grpc` с `code`, `retryable` и `outcomeUnknown`.

`api.js` выбирает политику по смыслу RPC. Значения в `network.js`:

| Политика | Таймаут попытки / общий бюджет | Попытки | Условия повтора |
|---|---:|---:|---|
| `READ` | 12 с / 35 с | 3 | gRPC-коды 2, 4, 14 или transport; full jitter до 2 с |
| `REFRESH` | 10 с / 22 с | 2 | код 14 или transport; full jitter до 1 с |
| `DRAFT` | 8 с / 26 с | 3 | коды 2, 4, 14 или transport; full jitter до 2 с |
| `MUTATION` | 15 с / 15 с | 1 | автоматического повтора нет; исход отмечается как неизвестный, кроме отмены |

`BF.clients.authCall` добавляет XAuth token и запускает `REFRESH`, если срок access token истёк или осталось не более 30 секунд. Одновременные refresh объединяются. При gRPC-коде 16 клиент один раз обновляет token и повторяет вызов; этот auth-повтор отдельный от счётчика попыток unary-политики. Сессию очищает только явный `x-error-code` Identity о недействительном refresh token. Временная ошибка refresh сохраняет локальную сессию.

Страницы входа, регистрации, выбора ноды и подтверждений также используют `BF.network.unary`; регистрация и auth challenge передают `AbortSignal`. Отмена сообщает серверу о прекращении ожидания, но сама по себе не откатывает уже выполненную операцию. Таймаут мутации поэтому не доказывает, что операция не применилась.

## Server streams и catch-up

В обычной сессии `BF.realtime` открывает девять Updates-потоков: новые сообщения, прочтения, правки, удаления, закрепления, снятия закрепления, снятия всех закреплений, скрытие чата и зашифрованные private messages. Onliner добавляет поток presence для отслеживаемых пользователей и поток typing только для открытого чата. `BF.calls` отдельно держит device-scope поток событий звонков.

Каждый поток восстанавливается независимо: начальный backoff — 2 секунды, удваивается до 30 секунд; стабильная работа сбрасывает backoff. Поток превентивно открывается заново через 180 секунд, watchdog раз в 30 секунд проверяет отсутствие `data`/`status` дольше 90 секунд. Код 16 запускает принудительный refresh. Поток Calls `SubscribeCallEvents` имеет отдельный device scope и такую же политику reconnect. При возвращении вкладки клиент открывает отсутствующие потоки; событие браузера `online` ускоряет reconnect, но не считается проверкой доступности ноды. `SetOnlineStatus` посылается при старте и каждые 3 секунды.

Серверные потоки не воспроизводят пропущенные события. Переоткрытие Updates-потока поднимает `resync`; `BF.connection` объединяет такие сигналы за 1,2 секунды, обновляет список и сверяет хвост открытого чата с Messages. При отсутствии открытого чата обновляется только список. Для private chat перечитывается его содержимое. После восстановления UI показывает короткий статус синхронизации.

`connection_status` имеет состояния `offline`, `reconnecting` и `connected`: `connected` выставляется, когда открыты четыре основных Updates-потока (новые сообщения, прочтения, правки и удаления); прочие потоки могут восстанавливаться независимо. Boolean `connected` при этом означает, что жив хотя бы один из этих четырёх. `offline` определяется по `navigator.onLine`, которое является лишь подсказкой браузера; успешность восстановления подтверждается RPC и catch-up. На локальном HTTP/1.1 без TLS несколько долгих gRPC-Web потоков могут занять все соединения браузера к origin, из-за чего unary-запросы стоят в очереди. Для стенда нужен TLS/HTTP/2; производственный Web gateway задаёт длительные таймауты для streaming-маршрутов (см. [[Backend/Web]]).

## Загрузка, отправка и черновики

`BF.files.uploadFile` сначала резервирует slot через `GetUploadUrl`, затем передаёт multipart через XHR. Загрузка идёт на `files_media_endpoint`, если он задан; иначе — через Web ноды. XHR имеет 30-минутный wall timeout, 12-секундный срок для status GET и 60-секундный watchdog без upload progress. После отправки всех байтов watchdog отключается, но wall timeout остаётся. `AbortSignal` отменяет XHR.

`retryUpload` сначала запрашивает состояние slot: `completed` возвращает итоговый `fileId`, `pending` повторяет POST, `processing` сообщает о незавершённой обработке и не загружает файл повторно. Ошибка или потерянный ответ могут оставить исход неизвестным; UI предлагает ручное продолжение через проверку статуса.

Обычная отправка проходит через `BF.sendQueue`. До сети клиент создаёт локальное сообщение и сохраняет в `BF.pendingSends` operation ID, текст/подпись, reply, file IDs и метаданные загрузок. Если запись в `localStorage` не удалась, send не начинается. `SendMessage` получает тот же `clientOperationId`; ответ, realtime или история заменяют pending bubble и удаляют запись. Автоматического повтора send нет; ручной retry сохраняет operation ID, чтобы сервер мог дедуплицировать запрос. Отменить можно активную загрузку до dispatch `SendMessage`; уже отправляемый RPC так не отменяется.

`File` и `Blob` не сохраняются. После reload клиент восстанавливает metadata отправки и уже полученные file IDs; незавершённую загрузку можно продолжить после повторного выбора файла с совпадающими именем, размером и типом. Бинарного IndexedDB outbox нет.

`BF.drafts` node-scoped для каждого пользователя. Текст и reply локально помечаются `dirty`, синхронизация запускается после двух секунд бездействия, при старте и событии `online`; на чат допускается один in-flight RPC. ACK очищает только отправленную generation. При ошибке запись остаётся dirty, а фоновый backoff растёт с 2 до 30 секунд. Черновики не подключены к private/secret чатам. Локальная запись может не пережить reload, если браузер отклонит запись в `localStorage`.
