# Web

Веб-клиент BarkFluff — SPA на vanilla JavaScript без фреймворка. Исходные модули находятся в `Backend/BarkFluff.Web/wwwroot/js/app/`; хост и режимы шлюза описаны в [[Backend/Web]].

## Сборка и интерфейсы модулей

`index.html` содержит вход и регистрацию, `messenger.html` — приложение. Порядок IIFE-модулей задан в `Backend/BarkFluff.Web/scripts/app-bundle-entry.js`; esbuild собирает их в fingerprinted-файл. `app-loader.js` загружает путь из `app-manifest.json` без кэширования указателя. `BuildMessengerApp` запускает сборку при обычном .NET build/publish. Версии `grpc-web`, `google-protobuf`, `esbuild` и `livekit-client` зафиксированы в `scripts/package.json`.

Модули публикуют клиентские интерфейсы в `window.BF`: `BF.node` выбирает сервер; `BF.clients` содержит callback-style gRPC-Web клиенты; `BF.api` преобразует protobuf в объекты JavaScript; `BF.realtime.on/off` раздаёт события, включая `connection_status` и `resync`, а `BF.connection` выполняет catch-up; `BF.files`, `BF.sendQueue`, `BF.pendingSends` и `BF.drafts` управляют файлами, отправкой и черновиками; `BF.privateChat` отвечает за E2E личных чатов; `BF.calls` — за звонки; `BF.i18n` и `BF.push` — за локализацию и уведомления.

## Нода, авторизация и состояние

`/node-config.js` определяет режим: закреплённая нода направляет запросы на свой origin, Shell позволяет выбрать ноду через Navigator, а Proxy закрепляет браузер за зеркалом ноды. `BF.node.origin()` задаёт адрес для gRPC и upload через шлюз; при наличии `files_media_endpoint` загрузка идёт на отдельный файловый адрес. `node.js` загружается до создания клиентов. Shell показывает каталог, историю и ручной ввод, затем проверяет адрес через Beacon. Navigator остаётся на origin страницы.

Сессия, временный режим входа, приватные ключи, черновики, pending-send metadata и настройка push имеют пространство имён выбранной ноды. Временные токены хранятся в `sessionStorage`, постоянные — в `localStorage`; `x-auth-token` передаётся заголовком, cookie для API не используются. Device ID общий для нод; тема, язык и согласие с документами хранятся в cookie, персонализация — в `localStorage`.

Identity сообщает доступные способы входа; клиент поддерживает регистрацию, пароль, 2FA и FastAuth. Challenge привязан к выбранному origin и поколению попытки; закрытие формы или смена ноды отменяет запросы. Согласие с документами блокирует вход, регистрацию и FastAuth до принятия. Сетевые таймауты и refresh описаны отдельно: [[Clients/Web-Network-Reliability]].

`main.js` владеет состоянием списка чатов и открытого чата. `BF.chatList` рисует виртуализированный список; `BF.feed` удерживает окно до 200 сообщений и подгружает историю страницами. `BF.api` предоставляет клиентские запросы к Messages, Users, Files и Calls. `BF.search` ищет по загруженным названиям чатов и отдельно вызывает `Users.SearchUsers`; поиска сообщений в веб-интерфейсе сейчас нет.

## Сообщения, файлы и звонки

`BF.realtime` принимает события Updates и Onliner, а `BF.connection` после разрыва тихо обновляет список и хвост открытого чата: серверный streaming не воспроизводит пропущенные события. Обычные сообщения отправляются через `BF.sendQueue`; operation ID позволяет сопоставить локальную pending-запись с серверным сообщением. Черновики синхронизируются с Messages. Подробности повторов, отмены и восстановления — в [[Clients/Web-Network-Reliability]].

`BF.files` резервирует загрузку в Files и передаёт файл multipart-запросом. При наличии `files_media_endpoint` используется отдельный файловый адрес; Proxy-режим проводит media через `/media/` и allowlist хостов. Временные ссылки обновляются при ошибке загрузки; после неудачного обновления клиент показывает заглушку. Вложенные файлы не сохраняются в браузере для восстановления после перезапуска.

Приватные чаты используют Argon2id и AES-256-GCM на клиенте: сервер получает шифротекст, а ключ остаётся в памяти или, по выбору пользователя, в node-scoped `localStorage`. Интерфейс приватного чата ограничен текстом. Клиент подключается к Messages и Files только выбранной ноды; федеративную маршрутизацию выполняет сервер узла, отдельного браузерного подключения к Federation нет.

`BF.calls` управляет входящими/исходящими звонками через Calls API и отдельный device-scope stream. Медиа публикуется напрямую в LiveKit SFU; поддерживаются аудио- и видеозвонки один-на-один и в группах. В приватных чатах действия звонка скрыты.

## PWA и локализация

`manifest.webmanifest` задаёт `/messenger` как точку входа, scope `/` и режим `standalone`. Service worker кэширует оболочку и текущий fingerprinted app bundle, для навигации использует сеть с переходом на `/offline.html`, а API, gRPC и файловые данные не кэширует. Запросы JS/CSS обслуживаются по cache-first; manifest app-бандла обновляется по сети с кэш-fallback. Worker регистрируется только при наличии secure context, browser APIs и Firebase/VAPID-конфигурации, поэтому без `/pwa-config.js` недоступны offline cache и push.

Push включается явным действием пользователя: только тогда запрашивается permission и регистрируется FCM token в Users. Service worker не показывает текст сообщения; уведомление о новом сообщении скрывается, если пользователь уже видит этот чат. `BF.i18n` поддерживает `ru`, `en`, `es`, `de` и `zh-Hans`; язык хранится в cookie.

## Текущие ограничения

- Sidebar search ограничен уже загруженными чатами и поиском пользователей; он не выполняет поиск сообщений.
- Черновики и metadata отправок переживают reload, но бинарные `File`/`Blob` не сохраняются: незавершённую загрузку после перезапуска нужно продолжить выбором файла.
- Состояния приглашения и принятия приватного чата не входят в клиентский поток `SubscribePrivateMessages`; список чатов нужно перечитать, чтобы увидеть такое изменение.
