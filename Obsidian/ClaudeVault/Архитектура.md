## Деплой

Основной (реально используемый) compose-файл бэкенд-стека — **`docker/backend/docker-compose-dev-backend.yml`**. Изменения окружений сервисов вносить прежде всего в этот dev-файл.

Постоянные данные Docker вынесены в host-папки рядом с этим Compose: `admindata/` для LiteDB AdminPanel, `data/postgres`, `data/rabbitmq`, `data/redis`, `data/seq`, `data/minio` и `backups/`. Эти каталоги исключены из Git. При миграции со старых named volume сначала нужно остановить контейнеры и скопировать данные из volume, не удаляя исходные volume до проверки запуска.

## Service Discovery Flow

1. Каждый сервис при старте запрашивает конфигурацию у `Configuration` через gRPC
2. Межсервисное взаимодействие — прямые gRPC-вызовы
3. Асинхронные события — через RabbitMQ (MassTransit)
4. Beacon собирает адреса всех сервисов и отдаёт клиентам единый `GetServerInfoResponse`

### Liveness endpoint пользовательского контура

Сервисы основного пользовательского контура (`Navigator`, `Beacon`, `Identity`, `Users`, `Messages`, `Files`, `Updates`, `Onliner`, `FastAuth`, `Calls`, `Web`) предоставляют анонимный `GET /ping`. При доступном listener ответ — `200 text/plain` с телом `pong`.

Endpoint проверяет только доступность процесса и listener, но не готовность PostgreSQL, RabbitMQ, Redis, MinIO или других зависимостей. Для gRPC-сервисов маршрут находится на существующем HTTP/2 listener; если у сервиса уже есть дополнительный HTTP/1 listener, маршрут также доступен на нём. Новые порты не добавляются.

Веб-шлюз [[Backend/Web|BarkFluff.Web]] в режиме `Node` публикует для браузера алиасы
`GET /ping/{service}` (путь внутри проксируется в `/ping` нужного сервиса). Это позволяет
экрану «О приложении» проверить [[Backend/Web|Web]] через `/ping`, а [[Backend/Navigator|Navigator]],
[[Backend/Beacon|Beacon]], [[Backend/Identity|Identity]], [[Backend/Users|Users]],
[[Backend/Messages|Messages]], [[Backend/Files|Files]], [[Backend/Updates|Updates]],
[[Backend/Onliner|Onliner]], [[Backend/FastAuth|FastAuth]] и [[Backend/Calls|Calls]] через один выбранный
origin ноды, не открывая браузеру внутренние адреса и отдельные CORS-правила. Для [[Backend/Navigator|Navigator]]
health-маршрут использует внутренний `NavigatorService:HealthHost` (по умолчанию
`http://navigator:7010`; основной dev-compose переопределяет его на `http://navigator:64646`
через `NAVIGATOR_SERVICE_HEALTH_HOST`), поскольку публичный `NavigatorService:Host`
обслуживает только gRPC.

### Паттерн «шелл + прямое подключение к ноде» (веб-клиент)

Нативные клиенты ([[Клиенты/Android]], [[Клиенты/Windows-WinUI]], [[Клиенты/macOS]]) идут
`Navigator.ListServers` → выбор → `Beacon.GetServerInfo` → per-service каналы. Браузер так
не может: gRPC-Web требует шлюза, а сам Beacon доступен только **через** него — дискавери
замыкается на себя.

Решение: у ноды один gRPC-Web шлюз ([[Backend/Web]]), его адрес нода публикует в каталоге
как `ServerInfo.web_endpoint` ([[Backend/Navigator]]).

1. Браузер грузит статику с глобального `web.barkfluff.com` — [[Backend/Web]] в режиме
   `Web:Mode=Shell`, который проксирует **только** `NavigatorApi`.
2. `ListServers` → пользователь выбирает ноду → её `web_endpoint` сохраняется локально.
3. Все дальнейшие вызовы (gRPC-Web, загрузка файлов, стримы) идут **напрямую в ноду**,
   cross-origin. Шелл в трафике не участвует — федеративная модель не централизуется.
4. `Beacon.GetServerInfo` через шлюз ноды доуточняет метаданные (имя, цвета, `livekit_url`).

Нода остаётся самодостаточной: её `BarkFluff.Web` раздаёт ту же статику и фиксирует себя
через `/node-config.js` (`pinned: true`). Подробности — [[Клиенты/Web]].

### Общий пакет иконок клиентов

Визуальные иконки хранятся в корневом каталоге `icons/` и не дублируются отдельными SVG
в клиентах. Каждый клиент использует одинаковый путь и ключ `/{category}/{name}.svg`;
веб-клиент подключает каталог через MSBuild в `wwwroot/icons/` и отображает монохромные
SVG через `BF.icons`/CSS mask. Контракт категорий и имён описан в `icons/README.md`.

## Аутентификация — XAuth

Все сервисы используют систему `XAuth` из `BarkFluff.GrpcServer`.

- JWT через заголовок `x-auth-token` (не стандартный Authorization)
- Обязательные metadata-заголовки: `x-device-id`, `x-device-name`, `x-ip`, `x-os`, `x-app-name`, `x-app-version` — все в Base64 (кроме токена)
- Политики авторизации:
  - `TokenType.User` — User или Service токен
  - `TokenType.Service` — только Service токен
  - `TokenType.Bot` — только Bot токен (долгоживущий bot-JWT, используется только внешним Bot API в [[Backend/Bots]]; на остальные API не проходит)

```csharp
// Program.cs
builder.Services.AddXAuth(builder.Configuration);
app.UseXAuth();

// Защита gRPC-методов
[Authorize(Policy = nameof(TokenType.User))]
public override Task<XxxResponse> Xxx(XxxRequest request, ServerCallContext context)
```

## Startup-конвейер микросервиса

```csharp
builder.LoadConfiguration(ServiceId.Xxx);           // 1. Загрузка конфига из Configuration service
builder.SetRunningAddress(builder.Configuration);   // 2. Настройка Kestrel
builder.AddBarkFluffSerilog("ServiceName");         // 3. Serilog + Seq
builder.Services.AddBarkFluffMetrics("ServiceName"); // 4. Метрики
builder.Services.AddBarkFluffGrpc();                // 5. gRPC + interceptors
builder.Services.AddXAuth(builder.Configuration);   // 6. JWT-аутентификация
app.UseXAuth();                                      // 7. Middleware auth
```

**Логирование (`AddBarkFluffSerilog`):** Seq — всегда (асинхронный батч-синк, не блокирует поток запроса). Console — синхронный stdout-синк: в Development полный вывод, в Production ограничен `Warning+`, чтобы не блокировать горячий путь на каждый запрос, но оставить `docker logs` для ошибок. Переключение по `ASPNETCORE_ENVIRONMENT`. См. `BarkFluff.GrpcServer/SerilogExtensions.cs`.

## RabbitMQ (MassTransit)

```csharp
builder.Services.AddMassTransit(x =>
{
    x.AddConsumer<SomeConsumer>();
    x.UsingRabbitMq((context, cfg) =>
    {
        cfg.Host(builder.Configuration["RabbitMQ:Host"], "/", h =>
        {
            h.Username(builder.Configuration["RabbitMQ:Username"]);
            h.Password(builder.Configuration["RabbitMQ:Password"]);
        });
        cfg.ReceiveEndpoint("queue-name", e =>
        {
            e.ConfigureConsumer<SomeConsumer>(context);
        });
    });
});
```

Типы событий — в [[Shared/Queue]].

### Fan-out для broadcast-событий (масштабирование)

Именованный `ReceiveEndpoint("queue-name", …)` — это **competing consumer**: при N экземплярах
сервиса событие получает только **один** из них. Для событий, которые должны прийти на **каждый**
экземпляр (broadcast-инвалидация кэшей, доставка в живущие на конкретном экземпляре gRPC-стримы),
имя очереди делается **уникальным на экземпляр** через `InstanceId.Current` — тогда MassTransit
создаёт отдельную очередь на экземпляр, привязанную к тому же exchange, и каждая получает копию:

```csharp
cfg.ReceiveEndpoint($"session-revoked-{service}-{InstanceId.Current}", e =>
{
    e.AutoDelete = true;   // очередь исчезает при отключении экземпляра
    e.Durable = false;
    e.ConfigureConsumer<SessionRevokedConsumer>(context);
});
```

`InstanceId.Current` (`Backend/BarkFluff.GrpcServer/XAuth/InstanceId.cs`) — `HOSTNAME` (ID контейнера
в Docker) или `Guid` на старте. Так работает broadcast-инвалидация `TokenRevocationCache` (отзыв
сессий) во всех сервисах с `AddXAuth`. См. `docs/scaling/_shared-token-revocation.md`.

## CQRS-паттерн (MediatR)

```csharp
// Команда
public class XxxCommand : IRequest<XxxResponse>
{
    // свойства из gRPC запроса
}

// Хендлер
public class XxxCommandHandler : IRequestHandler<XxxCommand, XxxResponse>
{
    public async Task<XxxResponse> Handle(XxxCommand request, CancellationToken ct) { }
}

// gRPC-метод
[Authorize(Policy = nameof(TokenType.User))]
public override async Task<XxxResponse> Xxx(XxxRequest request, ServerCallContext context)
{
    return await _mediator.Send(new XxxCommand { /* map */ });
}
```

## CI/CD — GitHub Actions

### Структура пайплайна (с 2025)

Вместо единого `build.yml` (~5000 строк) — **отдельный workflow-файл на каждый микросервис**.

| Папка/файл | Назначение |
|------------|-----------|
| `.github/workflows/build-backend-{service}.yml` | По одному файлу на каждый из 20 backend-сервисов (GitHub runner `ubuntu-latest`) |
| `.github/workflows/build-client-macos.yml` | Сборка macOS-клиента (GitHub runner `macos-latest`) |
| `.github/workflows/build-client-wpf.yml` | Сборка WPF-клиента (GitHub runner `ubuntu-latest`) |
| `.github/workflows/build-client-android.yml` | Сборка Android APK (self-hosted runner) |
| `.github/workflows/build.yml.old` | Архив старого монолитного workflow (~2895 строк) |

Изменения в `Shared/**` сами по себе не запускают сборку backend-микросервисов. Для принудительной пересборки всех сервисов используется `Backend/rebuild.trigger` или ручной `workflow_dispatch`; собственные каталоги сервисов и явно указанные backend-зависимости остаются push-триггерами.

### Подход к сборке backend-микросервисов (Linux runner)

**Двухшаговая модель** для облегчения Docker-образов:

1. **`request-approval`** — запрашивает подтверждение через Telegram-бот (`powerdot/telegram-manual-approval`).
2. **`build`** — после `actions/checkout` устанавливает SDK через `actions/setup-dotnet@v5` по корневому `global.json`, затем выполняет `dotnet publish` (Release, Linux) → `docker build` из `Dockerfile.slim` → `docker push` в приватный registry. Ошибка установки SDK попадает в обычное уведомление о провале сборки в Telegram.

Версия SDK закреплена корневым `global.json` с `rollForward: disable`. SDK устанавливается в каждом `build` job и не должен быть заранее установлен на runner; это делает workflow совместимым с изолированными GitHub-hosted runner'ами.

### Dockerfile.slim

Каждый сервис имеет `Dockerfile.slim` — облегчённый образ **без слоя SDK**:
- Только `FROM aspnet:X.Y-{variant}` (runtime)
- `COPY publish/ .` — копирует pre-built артефакты с раннера
- Для сервисов с chiseled-образами: `COPY --chown=1654:1654`, директории (`logs/`, `data/`) создаются на раннере перед Docker-сборкой
- `BarkFluff.Web` — особый случай: Node/protoc-генерация остаётся в Docker (stage `proto-build`), .NET собирается на раннере

## Клиентская локализация (RU / EN)

Все клиенты, для которых нужна двуязычность ([[Клиенты/iOS]], [[Клиенты/macOS]], [[Клиенты/Windows-WPF]]), реализуют **мгновенное переключение языка без перезапуска**. Источник истины — выбор пользователя в Settings (язык/Russian/English/System), сохраняется локально. При первом запуске берётся системная локаль; если она не `ru` — fallback на `en`. Серверные строки не локализуются — переводим только клиентские.

**SwiftUI (iOS + macOS):** `@Observable LocalizationSettings` с computed `appliedLocale: Locale`, инжект в корне сцен через `.environment(\.locale, container.localizationSettings.appliedLocale)`. SwiftUI ре-рендерит весь tree при изменении observable, `LocalizedStringKey` авто-резолвится по текущей environment-локали. Источник переводов — Apple String Catalog (`Localizable.xcstrings`, JSON с native plural variants). См. подробности в [[Клиенты/iOS]] и [[Клиенты/macOS]].

**WPF (Windows):** swap `ResourceDictionary` (`Strings.ru.xaml` / `Strings.en.xaml`) в `Application.Current.Resources.MergedDictionaries` + событие `LanguageManager.LanguageChanged` для C# код-бихайнда. В XAML — **только `DynamicResource`** для локализованных ключей, `StaticResource` замораживает значение и swap не сработает. См. [[Клиенты/Windows-WPF]].

**WPF V2:** [[Клиенты/Windows-WPF-V2]] использует WPF UI и MVVM. `Views` не содержат UI-логики, `ViewModels` не зависят от `WebApi`, а подключение к ноде инкапсулировано в `INodeConnectionService`. SQLite хранит настройки, палитру и конфигурацию сервисов выбранной ноды рядом с exe; токены остаются только в памяти до отдельной DPAPI-миграции. Темы `System`/`Light`/`Dark` используют Windows accent, а `BarkFluffDark` применяет `#81341E`; авторизация и FastAuth QR скрыты за `IAuthenticationService`.

**BFCore — общий пакет [[Клиенты/iOS]] и [[Клиенты/macOS]]:** содержит собственный xcstrings (`Sources/BFCore/Resources/Localizable.xcstrings`, `resources: [.process("Resources")]` в `Package.swift`). Все локализованные API имеют **locale-aware overload** (`displayName(in: Locale)`, `displayText(in:)`, `previewText(fileName:in:)`, `BFError.errorDescription(in:)`, `DateFormatterHelper.format*(_:locale:)`, `ErrorLocalizer.localize(_:locale:)`). Реактивные views инжектят `@Environment(\.locale)` и пробрасывают в API; дефолт `.current` оставлен для нотификаций/логов вне SwiftUI-контекста.

**Конвенции ключей:**
- Swift (iOS+macOS): `<area>.<screen>.<element>` snake_case (`auth.login.submit`, `enum.theme.system`). iOS и macOS используют **одни и те же ключи** там, где экраны совпадают.
- WPF: `L_<Area>_<Screen>_<Element>` PascalCase (`L_Auth_Login_Submit`).
- BFCore (Swift): префикс `bfcore.` для пакетных ключей (`bfcore.online.last_seen_minutes %lld`).

**Plurals:** Swift — native xcstrings plural variants (RU one/few/many, EN one/other). WPF — нет native, используются ключи `L_X_Plural_One/Few/Many` + хелпер.
