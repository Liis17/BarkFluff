# ChatFolders — гайд для клиентских агентов

Документ описывает клиентское API папок чатов в `BarkFluff.Users` (порт 7001). Все вызовы — gRPC `UsersApi` через XAuth (`x-auth-token` пользователя). Чужие папки невидимы и недоступны на любом эндпоинте; нет публичного, межсервисного или анонимного доступа.

← [[Backend/Users]]

---

## Терминология и идентификаторы

| Поле | Тип на клиенте | Назначение |
|------|----------------|-----------|
| `folder_id` | `string` (Guid в текстовой форме) | **Единственный публичный идентификатор папки.** Возвращается при `Create`, используется во всех остальных RPC. Внутренний `Id` (long) клиенту не виден и не нужен. |
| `chat_id` | `string` (Guid в текстовой форме) | ID чата из Messages-сервиса. **Тот же формат, что `Chat.id` в `messages_api.proto`** (Guid строкой, например `"e3a4...-..."`). Backend хранит плоский массив; не валидирует существование чата на стороне Messages. Невалидный Guid → `ChatIdNotValidException`. |
| `folder_name` | `string` | После `Trim()` от 1 до 64 символов. Пустое или длиннее → `ChatFolderInvalidNameException`. |
| `folder_icon` | `string` | Произвольная строка-идентификатор: emoji (`"📥"`), системный ключ (`"work"`, `"travel"`), или URL. Backend не интерпретирует — клиент сам решает как рендерить. Пустая строка эквивалентна «нет иконки». |
| `sort_order` | `int32` | Порядок отображения. Меньше = выше. Backend сам ставит `max+1` при создании; клиент меняет порядок только через `ReorderChatFolders`. |

**Приватность:** во всех RPC `UserId` берётся из JWT-claim. Клиенту не нужно (и нельзя) передавать его. Любой `folder_id` чужого пользователя приведёт к `ChatFolderNotFoundException` — backend не различает «не существует» и «не моё» наружу.

---

## Жизненный цикл на клиенте

Типичный сценарий первого запуска экрана чатов:

1. `GetChatFolders()` — подгрузить список папок текущего пользователя (отсортирован сервером по `SortOrder, Id`).
2. Для каждой папки клиент сам резолвит `chat_list[]` → `Chat`-объекты через свой кеш / Messages API.
3. Изменения локального состояния (создание, редактирование, перетаскивание, добавление чата) — сразу же синхронизировать соответствующим RPC. После успеха — обновить локальный кеш данными из ответа (все мутирующие RPC, кроме `Delete` и `Reorder`, возвращают свежий `ChatFolderData`).

`UpdatePersonalization` / `Privacy` / другие профильные RPC к папкам не относятся.

---

## RPC-справочник

Все RPC живут в `BarkFluff.Proto.Users.UsersApi`. Авторизация: `TokenType.User`. Транспорт: gRPC, поэтому ошибки приходят через `RpcException` + `x-error-code` trailer.

### 1. `GetChatFolders` — список папок текущего пользователя

**Когда вызывать:**
- При открытии экрана со списком чатов (если папки уже грузились в этой сессии — можно из кеша).
- После любых внешних триггеров инвалидации (push-уведомление о смене настроек на другом устройстве, ручной pull-to-refresh).
- НЕ вызывать после собственных Create/Update/Delete/Add/Remove — все они возвращают актуальный `ChatFolderData` (кроме Delete/Reorder), достаточно обновить локальный кеш точечно.

**Запрос:** `GetChatFoldersRequest{}` — пустой.

**Ответ:** `GetChatFoldersResponse { repeated ChatFolderData folders }`. Уже отсортирован по возрастанию `sort_order`, дальше по `Id`. Может быть пустой массив (нормальное состояние «у пользователя нет ни одной папки»).

**Ошибки:** только инфраструктурные (`Unauthenticated`, `Unavailable`).

**Edge cases:**
- Пустой список — это валидно. Клиент должен показать «папок нет» / соответствующий empty state, а не ошибку.
- `sort_order` может содержать дыры (например, `0, 1, 3, 7`) после удалений и реордеров — клиент не должен на это рассчитывать.

---

### 2. `CreateChatFolder` — создать папку

**Когда вызывать:**
- Пользователь подтвердил форму «Новая папка». Создание без названия или с одними пробелами — блокируйте на UI (после Trim) до отправки.

**Запрос:** `CreateChatFolderRequest { string folder_name; string folder_icon }`.
- `folder_name` — обязательный; backend сделает `Trim()`. После Trim 1..64 символа.
- `folder_icon` — опциональный; пустая строка → сохранится как «нет иконки» (`folder_icon` в ответе будет `""`).

**Ответ:** `CreateChatFolderResponse { ChatFolderData folder }` — полная свежесозданная папка с заполненным `folder_id` (Guid) и автоматическим `sort_order = max+1`. `chat_list` пустой.

**Ошибки:**
- `ChatFolderInvalidNameException` (`8C1A6F4D-1B22-4E1B-8E4D-7E9A5B6C2A11`) — пустое имя или > 64 символов после Trim. Покажите валидационную ошибку прямо в форме, не закрывайте диалог.

**Edge cases:**
- Backend не проверяет уникальность имён — две папки с одинаковым названием это валидно. Если продукт хочет этого избегать — проверка строго на клиенте.
- Создание папки сразу со списком чатов через один RPC не предусмотрено: сначала `Create`, потом цикл `AddChatToFolder` или один `UpdateChatFolder` с `has_chat_list_update=true`.

---

### 3. `UpdateChatFolder` — частичное обновление папки

**Когда вызывать:**
- Пользователь сохранил изменения в форме редактирования (одно или несколько полей).
- Используйте именно этот RPC, если в одной операции меняется несколько полей сразу — иначе предпочитайте более точечные `AddChatToFolder` / `RemoveChatFromFolder`.

**Запрос:** `UpdateChatFolderRequest`:

| Поле | Тип | Семантика |
|------|-----|-----------|
| `folder_id` | `string` | Обязательно. Guid папки. |
| `folder_name` | `optional string` | Если установлено — обновить (после Trim). Если **не установлено** (`HasFolderName == false`) — не трогать. |
| `folder_icon` | `optional string` | Если установлено пустой строкой — **очистить** иконку (записать NULL). Если установлено непустой — заменить. Если не установлено — не трогать. |
| `has_chat_list_update` | `bool` | Флаг намеренной замены списка чатов. **Без него `chat_list` игнорируется.** Это нужно потому что у `repeated` в proto3 нет presence — пустой массив не отличить от «не передан». |
| `chat_list` | `repeated string` | Список Guid'ов чатов в текстовой форме. Учитывается только при `has_chat_list_update == true`. Полностью замещает старый массив. Любой невалидный Guid в списке → `ChatIdNotValidException`. |

**Ответ:** `UpdateChatFolderResponse { ChatFolderData folder }` — папка после обновления.

**Ошибки:**
- `ChatFolderNotFoundException` (`5F0B7B2E-3F6E-4D2B-9B9E-9B7E7C2B9D8A`) — невалидный Guid, удалённая папка или (что снаружи неотличимо) чужой `folder_id`.
- `ChatFolderInvalidNameException` — невалидное `folder_name`.

**Когда НЕ использовать:**
- Изменение только порядка — `ReorderChatFolders`.
- Добавить/удалить один чат — `AddChatToFolder` / `RemoveChatFromFolder`. Они идемпотентны и не подвержены гонкам с параллельными изменениями `chat_list` с других устройств.

**Гонка устройств:** `UpdateChatFolder` с `has_chat_list_update=true` — это full-replace. Если пользователь параллельно добавил чат на другом устройстве, а это устройство отправляет старый список — добавленный чат потеряется. Для сценариев «добавить/убрать один чат» всегда предпочитайте точечные RPC.

---

### 4. `DeleteChatFolder` — удалить папку

**Когда вызывать:**
- Пользователь явно подтвердил удаление. Backend не возвращает «soft-delete» — операция необратима, чаты в Messages не трогаются (удаляется только связь).

**Запрос:** `DeleteChatFolderRequest { string folder_id }`.

**Ответ:** `DeleteChatFolderResponse{}` (пустой).

**Ошибки:**
- `ChatFolderNotFoundException` — невалидный Guid / уже удалена / чужая.

**UX-замечания:**
- На клиенте оптимистично убирайте папку из локального кеша, при ошибке возвращайте назад и показывайте toast.
- После удаления `sort_order` оставшихся папок не пересчитывается — это нормально. Если по UX надо «сжать» порядок — отдельным `ReorderChatFolders`.

---

### 5. `AddChatToFolder` — добавить чат в папку

**Когда вызывать:**
- Пользователь жмёт «Добавить в папку» в контекстном меню чата.
- Drag-and-drop чата в папку.
- Сценарий «создать папку из выделенных чатов»: после `CreateChatFolder` — цикл `AddChatToFolder` (или один `UpdateChatFolder` с has_chat_list_update; первый вариант устойчивее к гонкам).

**Запрос:** `AddChatToFolderRequest { string folder_id; string chat_id }` (`chat_id` — Guid строкой).

**Ответ:** `AddChatToFolderResponse { ChatFolderData folder }` — папка после операции (с обновлённым `chat_list`).

**Ошибки:**
- `ChatFolderNotFoundException` — невалидный/чужой `folder_id`.

**Идемпотентность:** если `chat_id` уже в `chat_list`, backend это видит и не создаёт дубль (но всё равно возвращает текущее состояние). Клиент может смело повторять при ретраях, кешированных тапах и подобных кейсах.

**Edge cases:**
- Backend проверяет, что `chat_id` — валидный Guid (иначе `ChatIdNotValidException`), но **не** проверяет, что чат с таким Guid существует в Messages. Это by design (Users и Messages — разные сервисы), но клиент не должен передавать произвольные строки.
- Один и тот же чат может одновременно лежать в нескольких папках — это не запрещено. Если продукт требует mutual exclusion, реализация на клиенте: перед `Add` сначала локально найти все папки с этим `chat_id` и сделать `RemoveChatFromFolder` для них.

---

### 6. `RemoveChatFromFolder` — убрать чат из папки

**Когда вызывать:**
- «Убрать из папки» в контекстном меню.
- Drag-and-drop чата из папки наружу.
- Реакция на удаление чата из Messages (если клиент знает, что чат больше не существует — стоит вычистить из всех своих папок; backend этого не делает автоматически).

**Запрос:** `RemoveChatFromFolderRequest { string folder_id; string chat_id }` (`chat_id` — Guid строкой).

**Ответ:** `RemoveChatFromFolderResponse { ChatFolderData folder }`.

**Ошибки:**
- `ChatFolderNotFoundException` — папки нет или чужая.

**Идемпотентность:** если `chat_id` уже отсутствует в `chat_list`, операция — no-op, ответ — текущее состояние папки. Безопасна для повторов.

---

### 7. `ReorderChatFolders` — изменить порядок папок

**Когда вызывать:**
- Пользователь закончил drag-and-drop переупорядочивания.
- В UI типа «настройки → порядок папок» по нажатию Save.

**Запрос:** `ReorderChatFoldersRequest { repeated ChatFolderOrder orders }`, где `ChatFolderOrder { string folder_id; int32 sort_order }`. Передавайте только те папки, чей `sort_order` действительно меняется (или все — оба варианта валидны).

**Ответ:** `ReorderChatFoldersResponse{}` (пустой). Чтобы получить актуальное состояние — `GetChatFolders`. На практике клиент после успеха просто применяет к локальному кешу те же `sort_order`, что отправил.

**Ошибки:** только инфраструктурные. Невалидные / чужие `folder_id` **молча игнорируются** (никаких NotFound для каждого ID). Это сделано чтобы массовое переупорядочивание не падало целиком из-за одной устаревшей записи.

**Edge cases:**
- Дубликаты `sort_order` допускаются — backend ничего не нормализует. Клиент сам решает порядок строго возрастающий или с шагом.
- Атомарность: все обновления в одной БД-транзакции (один `SaveChangesAsync`). Промежуточных состояний клиенты не увидят.

## Сводная таблица «Use case → RPC»

| Действие пользователя | RPC | Примечание |
|----------------------|-----|------------|
| Открыть экран со списком папок | `GetChatFolders` | Кешируйте; не дёргайте на каждое UI-событие |
| «Создать папку» (модалка с именем + иконкой) | `CreateChatFolder` | После — добавить в локальный кеш |
| «Создать папку из выделенных N чатов» | `CreateChatFolder` → N × `AddChatToFolder` | Или один `UpdateChatFolder` с `has_chat_list_update`, если важна атомарность списка |
| Переименовать папку | `UpdateChatFolder` (только `folder_name`) | Не указывайте `folder_icon`, не выставляйте `has_chat_list_update` |
| Сменить иконку | `UpdateChatFolder` (только `folder_icon`) | Пустая строка = очистить |
| Очистить иконку отдельной кнопкой | `UpdateChatFolder` с `folder_icon = ""` | `HasFolderIcon` должен быть true |
| Удалить папку | `DeleteChatFolder` | Чаты в Messages не трогаются |
| Добавить чат в папку (контекст-меню) | `AddChatToFolder` | Идемпотентно |
| Убрать чат из папки | `RemoveChatFromFolder` | Идемпотентно |
| Drag-and-drop чата между папками | `RemoveChatFromFolder` (старая) → `AddChatToFolder` (новая) | Две независимые операции; UI применяет оптимистично |
| Drag-and-drop порядка папок | `ReorderChatFolders` | Один RPC после drop |
| Полное редактирование (имя + иконка + чаты) | `UpdateChatFolder` со всеми полями + `has_chat_list_update=true` | Учтите гонки с другими устройствами |
| Чат удалён в Messages — вычистить везде | По всем папкам, где он встречался: `RemoveChatFromFolder` | Backend сам не чистит — это ответственность клиента |

## Ошибки и `x-error-code`

| Код | Класс | Сценарий | UX-рекомендация |
|-----|-------|----------|-----------------|
| `5F0B7B2E-3F6E-4D2B-9B9E-9B7E7C2B9D8A` | `ChatFolderNotFoundException` | Невалидный Guid, удалённая или чужая папка | «Папка не найдена», обновите список через `GetChatFolders` |
| `8C1A6F4D-1B22-4E1B-8E4D-7E9A5B6C2A11` | `ChatFolderInvalidNameException` | `folder_name` пустое или > 64 символов после Trim | Inline-валидация формы, не закрывать диалог |

`gRPC`-ошибки `Unauthenticated` / `Unavailable` обрабатываются общим инфраструктурным слоем клиента (повторный логин / экран нет-связи) — специфичной логики для папок там не нужно.

---

## Локальный кеш на клиенте — рекомендации

- Храните `Map<string folderId, ChatFolderData>` + отдельный отсортированный массив id.
- На любой мутирующий RPC (Create/Update/Add/Remove) применяйте ответ как source of truth: `cache[folder_id] = response.folder`.
- На `Delete` — оптимистично удаляйте, при ошибке откатывайте.
- На `Reorder` — оптимистично применяйте новые `sort_order`, при ошибке делайте `GetChatFolders`.
- При получении push-сигнала об изменении папок с другого устройства (если будет реализован) — полный `GetChatFolders`, не пытайтесь дельта-синхронизацию.

---

## Что **не** делать

- Не передавать `UserId` ни в одном поле — backend его игнорирует и берёт из токена.
- Не использовать `Update` с `has_chat_list_update=true` для добавления одного чата — это лишает идемпотентности и устойчивости к гонкам.
- Не фильтровать чужие папки на клиенте — `GetChatFolders` уже отдаёт только папки авторизованного пользователя.
- Не валидировать `folder_icon` на формат — backend этого не делает, и продукт может в любой момент расширить семантику строки.
- Не полагаться на конкретные значения `sort_order` (нет гарантии плотной нумерации, шаг произвольный, могут быть равные значения).
