# Этап 2.7 — Слияние одновременно созданных DM

## Цель

Гонка «оба пользователя написали друг другу первыми одновременно» (обе ноды создали fed-DM одной UUID-пары с разными ChatId) разрешается детерминированно: обе ноды сходятся к одному чату, сообщения обоих переносятся в него.

## Контекст

- Решение «побеждает меньший ChatId»: [../05-chat-replication.md](../05-chat-replication.md), «Создание чата»; риск №13 в [../09](../09-problems-open-questions.md) — самый сложный корнер-кейс фазы.
- Требуются 2.3 (`FederatedStatus`, UUID-пара, временный `REJECTED:DuplicateFederatedDm`) и 2.2 (outbox, идемпотентность).

## Протокол (зафиксировать в [../05](../05-chat-replication.md) взамен «решение намечено»)

**Канонический порядок Guid**: сравнение строкового представления формата `"D"` lowercase, ordinal (`string.CompareOrdinal`). Победитель пары чатов — чат с меньшей строкой. Одинаково вычислимо на обеих нодах и в сторонних реализациях.

Детект — в `ImportFederatedChat` (заменяет временный `REJECTED:DuplicateFederatedDm` из 2.3): входящий `ChatCreated` c `chat_id_B`, при этом локально есть `Active` fed-DM той же UUID-пары `chat_id_A ≠ chat_id_B`:

```
победитель W = min(chat_id_A, chat_id_B), проигравший L = другой

1. Локальной копии L ещё нет и W == chat_id_A (входящий проиграл):
   → создать копию L? НЕТ: ответить OK + выполнить merge немедленно:
     локально завести не нужно — входящие события чата L будут
     перенаправляться (см. «Перенаправление» ниже)
2. W == chat_id_B (входящий выиграл):
   → локальный чат A пометить Merged (MergedIntoChatId = chat_id_B),
     создать копию W (обычный путь ImportFederatedChat),
     перенести сообщения A → W (локальный UPDATE ChatId, FederatedId сохраняются),
     перезапостить в outbox события сообщений A с chat_id = W
     (идемпотентность по FederatedId на той стороне отсеет дубли)
3. Ответ всегда OK (не REJECTED): отправитель тоже выполнит
   симметричный merge, получив наш ChatCreated (гонка встречная —
   оба ChatCreated в полёте)
```

**Перенаправление входящих**: таблица/колонка `MergedIntoChatId` — события (`NewMessage`/`Edit`/`Delete`/`Read`), адресованные чату со статусом `Merged`, применяются к чату-победителю (та же UUID-пара гарантирует корректность). Это закрывает события, отправленные до того, как вторая сторона узнала о слиянии.

**Исходящие после merge**: `SendMessage` в `Merged`-чат на уровне API не случается (клиент увидит один чат после `ListChats`); события, уже лежащие в outbox с проигравшим chat_id, доедут и применятся через перенаправление на стороне получателя — **не** переписывать outbox задним числом.

## Изменение 1 — миграция

`Chats.MergedIntoChatId uuid NULL` (+ статус `Merged` уже есть с 2.3).

## Изменение 2 — реализация в Messages

- `ImportFederatedChat`: ветка детекта и merge по протоколу выше (транзакционно: пометка, перенос сообщений, создание победителя).
- Перенаправление: общая точка резолва чата для Import/Apply-RPC (`chat_id` → следовать `MergedIntoChatId`, один хоп) — добавь в хелпер 2.3.
- Перенос сообщений: `UPDATE Messages SET ChatId = W WHERE ChatId = L` + `FederatedMessageEvents`, `FederatedReadStates` аналогично; счётчики непрочитанного чата — пересчитать существующим механизмом.
- Публикация внутренних событий для Updates: клиенты обеих сторон должны увидеть итоговое состояние (минимум — события новых сообщений в W; полный «чат исчез/появился» клиенты заберут через `ListChats`; не изобретай новый тип события, если существующих недостаточно — зафиксируй ограничение в Obsidian).
- Запрос на перезапостку в outbox: Messages публикует существующие расширенные события (2.2-контракт) для перенесённых сообщений с `chat_id = W` — консюмеры Federation положат их в outbox штатно. Пометь события признаком «replay при merge», если без него возможен шторм пушей на той стороне (получатель уже имеет сообщения — идемпотентность по `FederatedId` их отсеет до пушей; проверь, что дедуп срабатывает **до** публикации `NewMessageEvent`).

## Изменение 3 — юнит-тесты протокола

- Детерминизм: для пары Guid обе «стороны» (два вызова с зеркальными аргументами) выбирают одного победителя.
- Идемпотентность: повторный `ChatCreated` проигравшего после merge → OK, без изменений.
- Перенаправление: `NewMessage`/`Edit` в проигравший chat_id применяются к победителю.
- Сообщения обеих сторон после merge в одном чате, порядок по `SentAt`.

## Чего НЕ делать

- Не менять нормализацию UUID-пары и не вводить глобальный «lock» между нодами — протокол чисто локально-детерминированный.
- Не переписывать содержимое outbox при merge.
- UX-полировка (анимации слияния и т.п.) — клиентов не касаемся, Фаза 5.

## Критерии готовности

1. Юнит-тесты Изменения 3 — зелёные.
2. Стенд, тест гонки (критерий роадмапа): приостановить диспетчеры outbox обеих нод (конфиг-флаг/остановка контейнера Federation) → пользователь node1 пишет пользователю node2 и наоборот (созданы два чата с разными ChatId) → включить доставку → на **обеих** нодах остался один чат (меньший ChatId) с обоими первыми сообщениями; второй чат помечен `Merged`.
3. Догонка после merge: правка «проигравшего» сообщения с любой стороны применяется корректно (перенаправление работает end-to-end).
