# Фаза 2 — Федеративные DM — планы реализации

Детальные планы по каждому этапу Фазы 2 из [../10-roadmap.md](../10-roadmap.md). Каждый план самодостаточен: исполнитель (Sonnet 5) должен суметь выполнить этап, прочитав только план + указанные в нём файлы, не восстанавливая контекст всей федерации.

**Суть фазы:** переписка 1-на-1 между нодами. Появляется слой remote-пользователей (Users), надёжная доставка событий (outbox в Federation), импорт/экспорт чатов и сообщений (Messages), LWW-разрешение конфликтов, privacy-отказ, catch-up истории и слияние одновременно созданных DM. **Файлы (вложения) и presence/typing — не здесь**: это Фазы 3 и 4. После Фазы 2 два пользователя разных нод полноценно переписываются текстом: доставка, ретраи, правки, удаления, прочтения, приватность, догон истории.

## Предпосылки (проверить до старта)

Фазы 0 и 1 должны быть завершены целиком:

- 0.2/0.3 — `Users.Uuid` и колонки Messages (`LastChangeAt`, `FederatedId`, `SenderUuid`, `ChatMembers.UserUuid`) существуют в снапшотах миграций.
- 0.4 — proto-контракты (`federation_api.proto`, `federation_internal_api.proto`, расширения users/messages) существуют; импорт-RPC отдают `Unimplemented`.
- Фаза 1 — сервис `BarkFluff.Federation` работает: XFed-подпись/проверка (1.3), discovery + KnownServers + анти-SSRF (1.4), Navigator с `GetServerByName` (1.5), двух-нодовый стенд `Backend/dev-federation-testbed/` через nginx (1.6), страница «Федерация» в AdminPanel (1.7). Если стенда или XFed нет — Фаза 1 не закончена, остановись.

## Обязательные правила для исполнителя

1. **Работать в текущей ветке** (`dev`), веток не создавать. После завершения каждого этапа — коммит (`git push` не делать). Формат сообщения: `feat(rearch-phase2): <этап> — <суть>`.
2. **Строго по плану.** Ничего сверх написанного: никаких вложений/файлов (Фаза 3), presence/typing (Фаза 4), групп, E2E-чатов. Если план противоречит реальному коду (файл переехал, API изменился) — остановись и спроси, либо адаптируйся минимально и явно опиши отклонение в коммите.
3. **Обратная совместимость — жёсткое требование.** Существующие сервисы и клиенты не меняют поведения: нефедеративные чаты работают как раньше, старые клиенты не ломаются (proto только расширяется). Всё федеративное включается только при `Federation:Enabled = true`.
4. **Референсные образцы, не строки.** Планы называют файлы-образцы — всегда читай актуальное состояние образца и повторяй его стиль; номера строк ориентировочные.
5. **Миграции EF Core**: известный баг — `dotnet ef migrations add` может падать с `MissingMethodException`. Порядок: сначала `dotnet tool restore && dotnet tool run dotnet-ef migrations add <Name> --project <csproj>`; если падает — писать миграцию вручную (три файла: миграция, `.Designer.cs` с атрибутом `[Migration]`, обновление snapshot; образец — соседние миграции). Миграции применяются на старте сервиса, локальный прогон обязателен.
6. **Библиотеки — только по актуальной документации**: MassTransit (publisher confirms, конфигурация консюмеров), EF Core, gRPC — сверяйся с Context7/официальными доками, не полагайся на память.
7. **Obsidian**: каждый этап дополняет соответствующие файлы: `Backend/Federation.md` (2.2, 2.5, 2.6), `Backend/Users.md` (2.1, 2.5, 2.9), `Backend/Messages.md` (2.3, 2.4, 2.6, 2.7), `Backend/CloudMessaging.md` (2.8), `Backend/Beacon.md`/`Backend/Navigator.md` (2.9), `Shared/Queue.md` (2.2). Это часть definition of done.
8. **Проверка каждого этапа** — раздел «Критерии готовности» в конце плана. Этап не завершён, пока все пункты не пройдены.

## Решения, зафиксированные на уровне фазы

Приняты при планировании фазы по итогам перепроверки роадмапа; уточняют родительские доки (правки доков включены в соответствующие этапы):

- **Этап 2.9 добавлен в роадмап.** Перепроверка нашла две задачи, объявленные в [../01](../01-addressing-identity.md)/[../08](../08-service-migration.md), но отсутствовавшие в таблице Фазы 2: профильные события через федерацию (`UserProfileChanged`/`UserDeactivated`) и расширенная регистрация Beacon в Navigator (federation-поля; в step-1.4 помечена «Фаза 2+»). Без первой протухают кешированные профили remote-пользователей, без второй discovery-источник «Navigator» не работает для прод-нод.
- **Консюмеры RabbitMQ → outbox — этап 2.2.** В таблице роадмапа они не были названы явно (в [../08](../08-service-migration.md), Federation, п. 7 есть). Контракт расширенных Queue-событий тоже в 2.2; Messages начинает заполнять поля в 2.3.
- **Подпись события (`origin_signature`)**: подписываются wire-байты `FederationEvent`, сериализованного отправителем с пустыми `origin_signature`; получатель для проверки очищает поле и пере-сериализует. Для C#↔C# это детерминировано; спецификация протокола (Фаза 6) обязана требовать сериализацию полей в порядке возрастания номеров. Этап 2.2 дописывает уточнение в [../02-trust-and-certs.md](../02-trust-and-certs.md).
- **Хранение исходных событий для catch-up**: чтобы `FetchChatHistory` отдавал события с теми же подписями origin, что и прямая доставка (обещание [../04](../04-federation-service.md)/0.4), Messages хранит последний применённый state-event каждого fed-сообщения как wire-байты (таблица `FederatedMessageEvents`). Свои сообщения нода экспортирует свежими событиями со своей подписью. Детали — этап 2.6.
- **Сверка «тихих дыр» — отдельный S2S-RPC `SyncChatStates`**, а не раздувание `Ping` (пар `(chat_id, last_event_ts)` может быть много, нужна пагинация). Добавление RPC в `federation_api.proto` обратно-совместимо. Этап 2.6.
- **Отказ privacy доводится до отправителя** новым Queue-событием `FederatedChatRejectedEvent`: Federation(A) получает `REJECTED:FederatedDmRejected` → публикует событие → Messages(A) помечает чат отклонённым → дальнейшие отправки в него отвечают понятной ошибкой. Этап 2.5.
- **Server-RPC Users для remote-профилей** (`UpsertRemoteUsers` — батч-upsert от Federation, `GetUsersByUuid` — батч-чтение для Messages) не были в контракте 0.4 — добавляются в 2.1 (добавление RPC обратно-совместимо).
- **Квота `ChatCreated` per-origin** ([../09](../09-problems-open-questions.md) №22) — этап 2.5; в таблице роадмапа не была выделена.
- **Сортировка выдачи сообщений** ([../09](../09-problems-open-questions.md) №41): проверено по коду — `MessagesStorage`/`ChatsStorage` уже сортируют по `SentAt`, риск «поздний импорт в конце чата» не реализуется. Остаётся добавить tie-break при равных `SentAt` (этап 2.3).
- **Вложения в 2.3 не рендерятся**: `NewMessagePayload.attachments` принимаются и сохраняются только как факт (текст доставляется), полный снапшот метаданных и скачивание — Фаза 3 (3.1). Ограничение зафиксировано в критериях 2.3.
- **Восстановление неизвестного чата**: `ImportFederatedMessage` на неизвестный `chat_id` отвечает RETRY с кодом `ChatUnknown`; починка — catch-up (этап 2.6), не «воссоздание из payload» (в `NewMessagePayload` нет данных второго участника).
- **Канонический порядок Guid для слияния DM (2.7)**: сравнение строковой формы `"D"` lowercase, ordinal — одинаково реализуемо на любой платформе.
