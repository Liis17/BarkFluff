# Фаза 3 — Файлы — планы реализации

Детальные планы по каждому этапу Фазы 3 из [../10-roadmap.md](../10-roadmap.md). Каждый план самодостаточен: исполнитель должен суметь выполнить этап, прочитав только план + указанные в нём файлы, не восстанавливая контекст всей федерации.

**Суть фазы:** вложения и аватары в федеративных DM. Файлы **не реплицируются**: живут только на origin-ноде, принимающая нода проксирует байты по запросу ([../06-files.md](../06-files.md) — главный документ фазы). Реплицируется только **снапшот метаданных** (имя/размер/тип/preview_id/размеры) — список чатов и сообщения рендерятся без сетевых походов. Кеш содержимого (включая превью) **запрещён** решением владельца. После Фазы 3 пользователь ноды B видит и скачивает вложения (со стримингом и Range/перемоткой) и аватары собеседников с ноды A — всегда через свою ноду, никогда напрямую с чужой. Presence/typing — Фаза 4, клиентские UI — Фаза 5.

## Предпосылки (проверить до старта)

Фазы 0–2 должны быть завершены. Критично для этой фазы:

Новые proto-поля в фазе нужны точечно (shared, files_api, users_api) — только добавления.
- 1.3/1.4 — `S2SChannelFactory` (XFed + SPKI-пиннинг), `ServerResolver`; XFed-интерсептор поддерживает server-streaming методы.
- 2.1 — `RemoteUsers` (в т.ч. `AvatarFileId`), S2S `GetUserProfile` с privacy-фильтрацией аватара (`AvatarVisibility`).
- 2.2 — outbox, консюмеры (`NewMessageFederationConsumer` и родственные), пайплайн `DeliverEvents`.
- 2.3 — импорт-RPC Messages работают; `SendMessage` fed-чата заполняет федеративные поля событий; стенд node2 дополнен users/messages/updates. **Ограничение 2.3:** вложения fed-сообщений сохраняются только как факт (текст доставляется) — 3.1 заменяет это на полный снапшот.
- 2.4 — `ApplyFederatedEdit` (список вложений при правке пересоздаётся — [../05](../05-chat-replication.md)).
- 2.8/2.9 — `SenderFid` в событиях; профильные события несут `avatar_file_id`. Долг 2.8 «аватар в пуше — Фаза 3» закрывается в 3.4.

**Гейт фазы** (из роадмапа): вложение из fed-сообщения рендерится без похода на origin; нода без общего чата с файлом получает отказ; клиент ноды 2 скачивает файл/видео (с перемоткой) с ноды 1 через свою ноду; аватар отображается при разрешающей privacy и не отображается при `AvatarVisibility=None`; остановленный origin → корректная ошибка, не таймаут-зависание.

## Обязательные правила для исполнителя

1. **Работать в текущей ветке** (`dev`), веток не создавать. После завершения каждого этапа — коммит (`git push` не делать). Формат сообщения: `feat(rearch-phase3): <этап> — <суть>`.
2. **Строго по плану.** Ничего сверх написанного: никакого кеша файлов/превью (запрещено решением владельца), presence/typing (Фаза 4), клиентских UI (Фаза 5), федеративных групп. Если план противоречит реальному коду — остановись и спроси, либо адаптируйся минимально и явно опиши отклонение в коммите.
3. **Обратная совместимость — жёсткое требование.** Локальные вложения и аватары качаются как раньше; proto только расширяется; всё федеративное включается только при `Federation:Enabled = true`; новые ветки скачивания — под наличием fed-признака.
4. **Референсные образцы, не строки.** Планы называют файлы-образцы — читай актуальное состояние образца и повторяй стиль; номера строк ориентировочные.
5. **Миграции EF Core**: известный баг — `dotnet ef migrations add` может падать с `MissingMethodException`. Порядок: сначала `dotnet tool restore && dotnet tool run dotnet-ef migrations add <Name> --project <csproj>`; если падает — писать миграцию вручную (миграция, `.Designer.cs`, snapshot; образец — соседние миграции). Миграции применяются на старте сервиса, локальный прогон обязателен.
6. **Библиотеки — только по актуальной документации**: AWS SDK S3 (`ByteRange`), gRPC server-streaming (deadline/cancellation семантика), EF Core — сверяйся с Context7/официальными доками, не полагайся на память.
7. **Obsidian**: каждый этап дополняет соответствующие файлы: `Backend/Files.md` (3.2–3.5), `Backend/Messages.md` (3.1–3.3), `Backend/Federation.md` (3.2, 3.4, 3.5), `Backend/Users.md` (3.4), `Backend/CloudMessaging.md` (3.4), `Shared/Queue.md` (3.1). Это часть definition of done.
8. **Проверка каждого этапа** — раздел «Критерии готовности» в конце плана. Этап не завершён, пока все пункты не пройдены.
9. Контекст решений — [../06-files.md](../06-files.md) (главный), [../04-federation-service.md](../04-federation-service.md), [../05-chat-replication.md](../05-chat-replication.md); риски №18–21, №44 — [../09-problems-open-questions.md](../09-problems-open-questions.md).

## Решения, зафиксированные на уровне фазы

Приняты при планировании фазы с владельцем; уточняют родительские доки (правки доков включены в соответствующие этапы):

- **Модель доступа к fed-вложениям — temp-capability, в паритет локальным вложениям.** [../06](../06-files.md) описывал прямой маршрут `GET /download/fed/{server}/{fileId}` для всех файлов с проверкой «файл во вложении чата, где пользователь — участник», но существующий `/download` не имеет auth вообще: локальные вложения скачиваются по временным capability-ссылкам (`GetTempDownloadUrl` с user-токеном → temp URL без auth). Решение: fed-вложения идут тем же путём — `GetTempDownloadUrl` принимает fed-refs, Files(B) при выдаче проверяет членство пользователя через Messages(B), скачивание — по обычной temp-ссылке `/download/{tempId}`. Прямой публичный маршрут `/download/fed/{server}/{fileId}` остаётся **только для аватаров** (3.4) — они и локально публичны по Guid. Это уточняет букву роадмапа 3.3 («REST /download/fed/...»); критерий роадмапа (скачивание через свою ноду со стримингом и Range) сохраняется. Правка 06 — этап 3.3.
- **Превью — строго без кеша** (решение владельца): открытый вопрос №19 из [../09](../09-problems-open-questions.md) закрыт — превью тянутся с origin при каждом обращении, как полные файлы; при недоступном origin — placeholder (3.5). Правки 06/09 — этап 3.3.
- **Два независимых уровня проверки доступа:** origin-нода авторизует на уровне **ноды** («file_id фигурирует во вложении fed-чата, участником которого является нода B» — `CheckFileFederationAccess`, 3.2); принимающая нода — на уровне **пользователя** при выдаче ссылки («пользователь — участник чата с этим вложением», 3.3). Ни один уровень не доверяет другому.
- **Защита от превышения размера (№44) — двойная:** Federation(B) обрывает стрим при превышении заявленного `total_size` (первый чанк `FetchFileChunk`), Files(B) — при превышении снапшота из temp-записи. Для аватаров снапшота размера нет — глобальный кап (3.4).
- **Аватары — отдельная ветка доступа на origin:** не по членству в чате, а по `AvatarVisibility` владельца (3.4); open-proxy на принимающей стороне закрыт сверкой (server, file_id) с `RemoteUsers`.
- **Пуш-аватар** (отложенный долг 2.8, «Фаза 3») — входит в 3.4.
- **Удаление fed-сообщения не трогает файл на origin:** файл живёт по правилам origin-ноды; принимающая сторона применяет soft-delete сообщения (2.4) со снапшот-строками вложений как обычно, никаких S2S-вызовов удаления файлов в протоколе нет.
