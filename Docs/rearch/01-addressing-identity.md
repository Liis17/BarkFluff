# 01 — Адресация и идентификация пользователей

## Проблема

Сейчас `UserId` — это `long` (`DateTimeOffset.UtcNow.ToUnixTimeMilliseconds()` в момент регистрации, см. `BarkFluff.Users`). Он уникален **только внутри одной ноды**. Две независимые ноды почти гарантированно породят пересекающиеся ID (это просто миллисекунды). Все таблицы (`ChatMembers.UserId`, `Messages.SenderId`, `ReadBy`, `ChatFolders.OwnerUserId`, prekeys и т.д.) и все proto-контракты ходят с `int64 user_id`.

Для федерации нужен глобально уникальный идентификатор и человекочитаемый адрес.

## Решение

### Три идентификатора пользователя

| Идентификатор | Кто имеет | Стабильность | Где используется |
|---------------|-----------|--------------|------------------|
| `long UserId` | Только локальные пользователи ноды | Стабилен | Весь существующий внутренний код ноды, существующие клиентские API — **не меняется** |
| `Guid UserUuid` | Все: локальные и remote | Стабилен, глобально уникален | Всё, что пересекает границу сервера: федеративный протокол, копии чатов, ссылки на remote-пользователей |
| FID `@username:servername` | Все | **Может меняться** (смена username) | Поиск/адресация человеком, отображение в UI |

Ключевое правило: **`long UserId` никогда не покидает свою ноду.** В S2S-протоколе фигурируют только UUID и FID. Remote-пользователь на нашей ноде существует только как UUID + FID + кешированный профиль; локального `long` у него нет.

### FID — формат и канонизация

```
@{username}:{servername}
```

- `username` — существующий формат `^[a-zA-Z0-9_]{3,32}$` (уже синхронизирован по всем клиентам).
- `servername` — валидный DNS-hostname (без порта; порт federation-эндпоинта определяется через discovery).
- Каноническая форма: username и servername приводятся к lowercase при сравнении/хранении. IDN-домены хранятся и сравниваются **только в punycode (A-label)**: `@bob:bаrkfluff.com` с кириллической «а» визуально неотличим от настоящего — homograph-спуфинг закрывается на уровне хранения/сравнения, а клиенты при смешанных скриптах показывают punycode явно, как браузеры (клиентское требование — [08-service-migration.md](08-service-migration.md)).
- Адрес без `:servername` (или с servername своей ноды) означает локального пользователя — обратная совместимость поиска.

FID — это **указатель**, не первичный ключ. При смене username FID меняется, но UUID и вся история сохраняются. Ноды обязаны уметь резолвить пользователя и по FID (`GetUserProfile(username)`), и по UUID (`GetUserProfileByUuid(uuid)`).

### UUID для локальных пользователей

- Новая колонка `Users.Uuid` (`uuid NOT NULL`, уникальный индекс), генерируется при создании пользователя.
- Backfill-миграция для существующих пользователей: `gen_random_uuid()` каждому.
- UUID отдаётся в `users_api.proto` (`User.uuid`, новое поле) — клиентам он понадобится для отображения и для федеративных чатов.

### Представление remote-пользователей

Новая таблица в **Users**-сервисе (а не в Federation — профили это домен Users):

```
RemoteUsers
  Uuid          uuid PK          -- UUID с домашнего сервера пользователя
  Username      text             -- текущий username (кеш, может протухнуть)
  ServerName    text             -- домен домашней ноды
  FirstName     text
  LastName      text
  Bio           text
  AvatarUrl     text             -- абсолютный URL на origin-сервер (или проксируемый, см. 06-files)
  LastSyncedAt  timestamptz      -- когда профиль обновлялся с домашнего сервера
  UNIQUE (Username, ServerName)  -- неуникальность по времени: при конфликте побеждает свежий резолв
```

Профиль remote-пользователя — **кеш**: обновляется при резолве, при входящих событиях (сервер-источник может вкладывать актуальный профиль) и по TTL (например, раз в сутки при обращении). Источник истины — всегда домашний сервер.

### Как существующие сервисы адресуют remote-пользователей

Основная трудность: `Messages`, `Updates`, `Onliner` повсеместно используют `long`. Два пути:

1. **(Отвергнут)** Выдавать remote-пользователям синтетический локальный `long` — владелец проекта решил: у remote только UUID.
2. **(Принят)** Добавить UUID-адресацию туда, где она нужна:
   - `ChatMembers` получает nullable `UserUuid` (для remote-участника `UserId = NULL`, `UserUuid` заполнен; для локального — наоборот или оба).
   - `Messages.SenderId` дополняется nullable `SenderUuid` (заполняется для сообщений remote-авторов; для локальных достаточно `SenderId`, но UUID проставляется тоже — упрощает репликацию).
   - `ReadBy` (PostgreSQL array of long) — для федеративных чатов read-receipts remote-стороны хранить отдельно: `FederatedReadStates (ChatId, UserUuid, LastReadFederatedMessageId, ReadAt)`, потому что массив long не вместит UUID.
   - Proto: там, где клиент указывает собеседника, вводится `oneof peer { int64 user_id; string user_uuid; }` (новые поля, обратная совместимость сохраняется).

Подробно по каждому сервису — [08-service-migration.md](08-service-migration.md).

## Резолв `@username:servername` (happy path)

1. Клиент вводит `@bob:chat.example.org` в поиске → вызывает новый RPC `UsersApi.ResolveFederatedUser(fid)`.
2. Users видит `servername != наш` → зовёт `Federation.ResolveRemoteUser(fid)` (внутренний service-RPC).
3. Federation: ищет `chat.example.org` в KnownServers; если нет — discovery ([03-discovery.md](03-discovery.md)).
4. Federation → S2S `GetUserProfile(username=bob)` на удалённую ноду (подписанный запрос).
5. Удалённая нода проверяет подпись, применяет privacy-настройки пользователя (аналог `GetUserByUsername`: `ProfileVisibleOnSite`, `AvatarVisibility`, `BioVisibility`) и возвращает `uuid`, профиль, список полей.
6. Federation отдаёт ответ Users → Users делает upsert в `RemoteUsers` → клиент получает карточку пользователя.

## Проблемы, которые надо решить в этом слое

- **Смена username у remote-пользователя**: наша копия FID протухает. Решение: события профиля через федерацию (push с домашнего сервера всем нодам, с которыми есть активные чаты) + lazy-обновление по TTL. При коллизии `(Username, ServerName)` — старую запись переименовывать по данным свежего резолва.
- **Смена username у локального пользователя**: уведомить все ноды, с которыми у него есть чаты (`UserChangedUsername` → Federation outbox).
- **Удаление аккаунта**: разослать нодам-партнёрам событие `UserDeactivated`; их копии чатов остаются (как в email), но профиль помечается удалённым. GDPR-аспект — [09-problems-open-questions.md](09-problems-open-questions.md).
- **Спуфинг**: нода авторитетна **только над своим доменом**. `@bob:chat.example.org` может подтвердить только `chat.example.org` (подпись запроса). Принимая событие, Federation обязан проверять, что `sender.ServerName == origin-сервер подписи`.
- **Уникальность UUID**: полагаемся на статистическую уникальность v4. Коллизия UUID из двух разных нод в `RemoteUsers` невозможна по PK — но вредоносная нода может *заявить* чужой UUID. Защита: UUID привязывается к паре `(Uuid, ServerName)` при первом знакомстве; смена ServerName для известного UUID — подозрительное событие, отклоняется (миграция аккаунтов между нодами — вне скоупа).
