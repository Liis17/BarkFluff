# Фаза 6 — Эксплуатационная готовность — планы реализации

Детальные планы по каждому этапу Фазы 6 из [../10-roadmap.md](../10-roadmap.md). Каждый план самодостаточен: исполнитель должен суметь выполнить этап, прочитав только план + указанные в нём файлы.

**Суть фазы:** федерация из «работает у нас на стенде» превращается в «этим можно эксплуатировать ноду и писать совместимые реализации». Наблюдаемость (метрики + админка), понимание нагрузочного поведения, документация оператора, публичная спецификация протокола и приведение базы знаний в соответствие реальности. Нового продуктового функционала здесь нет.

## Обязательные правила для исполнителя

1. **Работать в текущей ветке** (`dev`), веток не создавать. После завершения каждого этапа — коммит (`git push` не делать). Формат: `feat(rearch-phase6): <этап> — <суть>` (или `docs(rearch-phase6): …` для чисто документационных этапов).
2. **Строго по плану.** Ничего сверх написанного: никакого нового продуктового функционала, никаких «заодно отрефакторим Federation». Если план противоречит коду — остановись и спроси, либо адаптируйся минимально и опиши отклонение в коммите.
3. **Документация пишется по факту, а не по замыслу.** Любое утверждение в доках (ключ конфигурации, имя метрики, порт, путь) сверяется с кодом. Док, расходящийся с реализацией, хуже отсутствующего — на нём будут поднимать чужие ноды.
4. **Никаких секретов в документации и примерах**: приватные ключи, реальные токены, содержимое `.env` продакшена. Только плейсхолдеры.
5. **Референсные образцы, не строки.** Для метрик — `Obsidian/ClaudeVault/Backend/Onliner-Metrics.md`; для страниц админки — `Pages/v2/*.html` (MD3, только `v2/`); для секций портала — существующие записи в `Infrastructure/SeedData.cs`.
6. **Проверка каждого этапа** — раздел «Критерии готовности». Этап не завершён, пока все пункты не пройдены.
7. **Obsidian** правится в каждом этапе по его разделу; 6.5 подводит итог и проверяет целостность ссылок.

## Что проверяет исполнитель, а что — разработчик

Правило репозитория: **Docker для верификации не поднимать** (`CLAUDE.md`), поэтому:

- **Исполнитель (агент)** — код, тесты, сборка, тексты документации, статическая сверка утверждений с кодом.
- **Разработчик (человек)** — всё, что требует живого стека: нагрузочный прогон (6.2 целиком), проверка дашборда на реальных данных Seq (6.1), сквозная проверка инструкции «поднять ноду с нуля» (6.3). Такие пункты помечены **[делает разработчик]**.

## Решения, зафиксированные на уровне фазы

- **Этап 6.2 не выполняется агентом.** Нагрузочный прогон требует живого двух-нодового стека, генерации бэклога и параллельных скачиваний — это Docker и живые сервисы. Поэтому 6.2 сведён к тому, что можно подготовить в репозитории: сценарии, скрипты/утилиту генерации нагрузки, чек-лист снятия показателей и шаблон отчёта. **Прогон и заполнение цифр — задача разработчика**, план это фиксирует явно и не считает этап проваленным из-за незаполненных таблиц.
- **Операционные действия из роадмапа («ручной retry/sync чата» в AdminPanel, [../04-federation-service.md](../04-federation-service.md)) реализуются в 6.1**, а не остаются в вакууме: без них дашборд показывает проблему, но не даёт её исправить. Недостающие internal-RPC добавляются в `federation_internal_api.proto` (добавление RPC обратно-совместимо).
- **Спецификация протокола (6.4) публикуется через существующий Developers-портал** (секции документации + метаданные proto-файлов), а не как отдельный сайт: `Barkfluff.Developers` уже копирует все `Shared/BarkFluff.Proto/*.proto` в output и отдаёт их содержимое, включая `federation_api.proto`/`federation_internal_api.proto`.
- **Спецификация обязана описывать то, что нельзя вывести из .proto**: канонизацию строки подписи и wire-байты запроса, канонизацию `FederationEvent` (очистка полей подписи + детерминированная сериализация), JCS-подпись well-known-документа, семантику LWW и терминальности удаления, коды `EventStatus` и правила retry/permanent. Без этого сторонняя реализация ноды невозможна в принципе ([../09-problems-open-questions.md](../09-problems-open-questions.md) №30).
