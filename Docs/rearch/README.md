# Переход на федеративную архитектуру BarkFluff

Планирование перехода бэкенда от централизованной модели («один кластер — все пользователи») к федеративной: каждый желающий поднимает собственную ноду BarkFluff на своём домене, хранит данные своих пользователей у себя и при этом может переписываться с пользователями других нод по адресу `@username:servername`.

Это **только план**. Ни один документ в этой папке не меняет код — здесь зафиксированы решения, проблемы, задачи и подробное описание перехода по каждому микросервису.

---

## Принятые решения (зафиксированы с владельцем проекта, 2026-07-17)

| Вопрос | Решение |
|--------|---------|
| Объём MVP | Федеративные **личные чаты (DM)** + **онлайн-статусы и typing**. Группы, E2E-чаты (приватные/секретные), боты, звонки — помечены как будущие фазы, прорабатываются отдельными задачами позже |
| Доверие между серверами | TLS для транспорта (**сертификат может быть самоподписанным** — админ ноды делает свой, зависимости от CA нет) + долгоживущий **Ed25519 signing key** каждой ноды, которым подписываются все S2S-запросы. Подлинность обеспечивается подписью, а не цепочкой CA |
| Хранение истории чата | **Каждый сервер хранит свою копию чата** (пассивная репликация при доставке). Расхождения решаются правилом «актуальна версия с более новой UTC-меткой последнего изменения» (LWW). У сообщений должна быть метка времени последнего изменения — частично есть (`EditedAt`), достроить |
| Идентификация пользователей | Локальные пользователи сохраняют свой `long UserId` внутри своего бэкенда **и дополнительно получают UUID**. Remote-пользователи представляются **только UUID + `username:servername`** (username может меняться — стабильный якорь именно UUID) |
| Discovery серверов | **Гибрид**: DNS (`/.well-known/barkfluff`) + Navigator (каталог публичных нод) + **ручное добавление пира администратором в AdminPanel** (сценарий «оба админа — друзья») |
| Размещение S2S-эндпоинтов | **Новый микросервис `BarkFluff.Federation`** — единственная точка входа/выхода федеративного трафика. Остальные сервисы наружу не смотрят |
| Транспорт S2S | **gRPC** (`federation_api.proto` в `Shared/BarkFluff.Proto/`) |
| Файлы/вложения | **Не реплицируются.** Всегда тянутся с оригинального сервера, где файл был загружен (origin-pull через S2S-прокси) |
| Антиспам DM | Между серверами по умолчанию можно переписываться свободно; **пользователь в настройках приватности может запретить входящие сообщения с remote-серверов**. Плюс серверный блоклист нод у администратора |

## Терминология

| Термин | Значение |
|--------|----------|
| **Нода / сервер** | Полный деплой бэкенда BarkFluff (все микросервисы + БД) на своём домене |
| **servername** | DNS-домен ноды, глобальный идентификатор сервера в сети (например `barkfluff.com`, `chat.example.org`) |
| **FID (Federated ID)** | Адрес пользователя `@username:servername` |
| **Домашний сервер (home server)** | Нода, на которой заведён аккаунт пользователя. Клиент всегда подключается только к нему |
| **Remote-пользователь** | Пользователь чужой ноды, видимый локально через федерацию |
| **Origin-сервер** | Для файла — сервер, куда файл был загружен; для сообщения — домашний сервер автора |
| **S2S** | Server-to-server: трафик между Federation-сервисами двух нод |
| **Signing key** | Долгоживущая пара Ed25519 ноды; публичная часть публикуется через discovery, приватной подписываются S2S-запросы |
| **KnownServers** | Локальный реестр известных нод (адрес, ключи, статус, источник) в Federation-сервисе |
| **Outbox** | Персистентная очередь исходящих федеративных событий с ретраями (at-least-once) |

## Прообразы (prior art)

- **Matrix** — server discovery через `/.well-known`, подпись событий Ed25519-ключами серверов, федеративные комнаты. Мы сознательно **не** берём модель полной репликации DAG (слишком дорого), но заимствуем подход к подписям и discovery.
- **XMPP s2s / email (SMTP)** — модель «у каждого свой домен, доставка адресату на его сервер, копия у каждой стороны» — ближе всего к выбранной схеме хранения.
