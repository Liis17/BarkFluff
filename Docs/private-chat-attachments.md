# Вложения в приватных чатах

Проект протокола v1 для приватных чатов обеих сторон на одной ноде. Отправку следует включать после согласования совместимости клиентов и требований к доступу к зашифрованным объектам.

## 1. Формат сообщения

Сегодня Android (`PrivateChatCrypto.kt`, `PrivateChatRepository.kt`), Windows (`PrivateChatCrypto.cs`, `WebApiPrivateChatManager.cs`) и Web (`privatechat.js`) шифруют сырые UTF-8 байты текста ключом приватного чата, полученным через Argon2id. На отправке AAD равен UTF-8 от `barkfluff:private:{chatId}`. На чтении все три берут переданный `associated_data`, а при пустом поле вычисляют старый AAD. AES-256-GCM использует случайный 12-байтовый nonce и выдаёт `ciphertext ‖ tag` с тегом 16 байт. WinUI хранит ключ чата через `DpapiPrivateChatKeyStore` в области нода, пользователь и чат.

Сообщение без вложений проходит по тому же пути. Например, `Привет!` по-прежнему шифруется из байтов `d09fd180d0b8d0b2d0b5d18221` с прежними ключом и AAD. При одинаковом тестовом nonce весь шифротекст совпадает. В рабочем режиме nonce каждый раз новый.

Сообщение с вложениями использует те же поля `SendPrivateMessageRequest` и `shared.EncryptedMessage`.

- `associated_data` — UTF-8 от `barkfluff:private:attachments:v1:{chatId}`, где `chatId` — UUID активного чата в нижнем регистре с дефисами. `v1` задаёт версию всего формата.
- Ключ конверта — HKDF-SHA-256 с 32-байтовым ключом чата в качестве IKM, 32 нулевыми байтами в качестве salt и точным v1 AAD в качестве info. Длина результата — 32 байта. Ключ чата уже получен через Argon2id.
- `nonce` — 12 случайных байт из CSPRNG для каждого нового шифрования, в том числе правки. `ciphertext` — AES-256-GCM от UTF-8 JSON с ключом конверта и v1 AAD, затем 16 байт тега. Предел Messages для `ciphertext` — 65 536 байт, поэтому JSON занимает до 65 520 байт. AAD укладывается в предел 4096 байт.

Получатель сверяет v1 AAD байт-в-байт с ожидаемым для текущего чата и проверяет тег до разбора JSON. Некорректный маркер, ошибка аутентификации или разбора приводят к ошибке сообщения. Неизвестная версия пространства `barkfluff:private:attachments:` отображается как неподдерживаемая. Для остальных AAD используется прежнее чтение текста.

Корневой JSON-объект содержит `text` (строка, может быть пустой) и `attachments` (непустой упорядоченный массив). Каждый элемент содержит следующие поля.

| Поле | Значение |
|---|---|
| `fileId` | UUID готового объекта на ноде чата в нижнем регистре с дефисами |
| `name` | Исходное отображаемое имя файла без пути |
| `mime` | MIME исходного файла без параметров. При неизвестном типе — `application/octet-stream` |
| `size` | Размер plaintext в байтах. JSON-целое от 0 до 2⁵³−1 в десятичной записи без дроби и экспоненты. При отправке действует меньший лимит загрузки ноды и клиента |
| `sha256` | SHA-256 plaintext, 64 строчных hex-символа |
| `key` | Случайный 32-байтовый ключ файлового потока, 64 строчных hex-символа |
| `preview` | Необязательный объект с теми же обязательными полями для превью, без вложенного `preview` |

Кодировка JSON — строгий UTF-8 без BOM. Порядок свойств и пробелы свободны. Дубликаты ключей и поля вне схемы v1 отклоняются. Имя и MIME обрабатываются как недоверенный ввод. При правке текста с сохранением вложений клиент повторно шифрует весь конверт с прежними дескрипторами. Перед включением отправки следует проверить, может ли старый клиент затереть v1 конверт при правке собственного сообщения.

После проверки тега все клиенты отклоняют начальные байты `EF BB BF` до декодирования. Имена свойств сравниваются с учётом регистра после декодирования JSON-экранирования. Набор полей проверяется отдельно в корне, каждом дескрипторе и каждом превью.

- .NET 10 проверяет строгий UTF-8 и разбирает объект через `System.Text.Json` с `JsonDocumentOptions.AllowDuplicateProperties = false`. Затем через `EnumerateObject()` сверяет обязательные и допустимые имена полей. [Документация .NET](https://learn.microsoft.com/dotnet/api/system.text.json.jsondocumentoptions.allowduplicateproperties?view=net-10.0)
- Web декодирует через `TextDecoder("utf-8", { fatal: true })` и проверяет исходный JSON парсером, сохраняющим или отклоняющим повторные имена. Если дальше используется `JSON.parse`, проверка дубликатов выполняется до него. Повторное имя уже свёрнуто к последнему значению к моменту вызова `reviver`. Поля сравниваются по `Object.keys()`. [ECMAScript JSON.parse](https://tc39.es/ecma262/multipage/structured-data.html#sec-json.parse)
- Android декодирует UTF-8 с `CodingErrorAction.REPORT` и до создания `JSONObject` проверяет строгий JSON парсером, который видит все вхождения каждого имени. `JSONTokener` из Android `org.json` сам принимает часть отклонений от JSON и заменяет значения при повторе имени. Допустимые и обязательные поля сверяются через `JSONObject.keys()` или при предварительном разборе. [Исходник Android JSONTokener](https://android.googlesource.com/platform/libcore/+/refs/heads/main/json/src/main/java/org/json/JSONTokener.java)

## 2. Шифрование файлов и превью

Формат объекта — RAW [Tink AES-GCM-HKDF Streaming AEAD](https://developers.google.com/tink/streaming-aead/aes_gcm_hkdf_streaming). Параметры v1 — SHA-256 для HKDF, 32 байта исходного и производного ключей, 4096 байт на сегмент шифротекста, нулевое смещение, без префикса keyset. Для каждого файла и каждого превью генерируются независимые случайные IKM, salt и префикс nonce. AssociatedData потока и HKDF info — ASCII `barkfluff:private:attachments:v1:file` для файла и `barkfluff:private:attachments:v1:preview` для превью.

1. Заголовок из 40 байт состоит из `0x28 ‖ salt[32] ‖ noncePrefix[7]`. Ключ AES-256 получается через HKDF-SHA-256 с указанными IKM, salt и info.
2. Первый сегмент несёт до 4040 байт plaintext, последующие — до 4080. Все промежуточные сегменты полные. Последний содержит остаток, включая полный сегмент при точной границе. Пустой файл имеет один финальный сегмент с нулём байт plaintext и тегом.
3. Сегмент с индексом `i` от нуля шифруется с `noncePrefix ‖ uint32be(i) ‖ final`, где `final` равен `0x01` для последнего сегмента и `0x00` для остальных. AAD вызова AES-GCM пуст. Каждый сегмент записывается как `ciphertext ‖ tag[16]` сразу после заголовка или предыдущего сегмента. Счётчик не переполняется, максимум 2³² сегментов.
4. Из аутентифицированного `size` читатель рассчитывает границы сегментов и ожидаемую длину `40 + size + 16 × число сегментов`. До выделения буферов он проверяет ограничения на число сегментов и размер файла. Затем читает ровно ожидаемые байты, проверяет заголовок, теги, EOF и итоговый SHA-256 plaintext. Ошибка отменяет выдачу файла целиком. Превью проходит те же проверки до декодирования.

## 3. Загрузка, метаданные и скачивание

1. Клиент шифрует файл и при необходимости локально создаёт и отдельно шифрует превью. Каждый объект резервируется через `GetUploadUrl` с типом `MessageAttachmentDocument` и своим UUID `client_operation_id`. В `POST /upload/{uploadId}` передаются только байты зашифрованного объекта, нейтральное имя `attachment.bin` и `application/octet-stream`. `UploadFileCommandHandler` пропускает автоопределение для явного Document, а MIME определяется по нейтральному расширению. `FileTypeDetector` распознаёт сигнатуры медиа, поэтому случайные байты могли бы совпасть с одной из них и запустить обработку при автоопределении. Для Document сервер хранит объект без преобразования или генерации превью.
2. Клиент ждёт подтверждения всех загрузок. В JSON помещается итоговый `fileId` из ответа POST или статуса `completed` от `GET /upload/{uploadId}/status`. Зарезервированный ID может отличаться от итогового из-за дедупликации. При потере ответа проверяется статус той же операции. Повтор загрузки той же операции использует те же байты и тот же ID операции. Если эти байты утрачены, новая шифровка использует новые случайные материалы и новую операцию. При неоднозначном исходе `SendPrivateMessage` следует свериться с историей и избегать автоматической повторной отправки, поскольку приватный RPC не принимает ключ идемпотентности.
3. На той же ноде получатель после аутентификации JSON запрашивает локальный `fileId` через `GetTempDownloadUrl` и скачивает ciphertext по временной ссылке. `GetTempDownloadUrlCommandHandler` выдаёт локальные ссылки аутентифицированному пользователю по известному ID без проверки владения или членства. Конфиденциальность содержимого обеспечивает шифрование. Если продукт требует ограничения доступа даже к ciphertext, до включения нужна отдельная серверная объектная авторизация. Временные ссылки живут только в памяти и запрашиваются заново при истечении срока.
4. Для файла и превью получатель вычисляет ожидаемую длину ciphertext по §2. Он запрашивает весь объект через GET без Range и до чтения тела сверяет `Content-Length` ответа 200 с ожидаемой длиной. При отсутствующем, недоступном, недопустимом или отличающемся значении скачивание отменяется. Клиент принимает только представление без преобразования `Content-Encoding`. При чтении клиент считает фактические байты, немедленно отменяет поток при превышении ожидаемой длины и отклоняет преждевременный EOF. Объект выдаётся только после всех проверок §2. До включения отправки нужно проверить сохранение `Content-Length` на пути от хранилища до клиента и его доступность для Web.

На сервере видны тип Document, нейтральное имя, размер зашифрованного объекта, действия загрузившего аккаунта и маркер v1 в AAD сообщения. Ключи объектов, исходное имя, MIME, исходный размер, хэш plaintext и связь файла и превью хранятся в зашифрованном payload. По размеру объекта v1 можно восстановить исходный размер, поскольку формат не использует padding.

## 4. Дедупликация

В Files уникальный SHA-256 относится к загруженным байтам. Равные открытые файлы при независимом шифровании практически всегда дают разные объекты. Совпадающий ciphertext при повторе той же загрузки или повторном использовании уже загруженных байтов раскрывает равенство объектов. При совпадении хэша Files переиспользует существующий объект и его ID. Если из-за коллизии или ошибки вернутся другие байты, получатель отклонит объект по проверкам длины, AEAD и SHA-256. Для новой самостоятельной отправки того же локального файла генерируется новый объект.

## 5. Федерация

В обычных чатах Files ноды получателя принимает `FedFileRef(origin_server, file_id)`, проверяет доступ пользователя через Messages и выдаёт временную ссылку. При скачивании Federation ноды получателя вызывает подписанный XFed `FetchFile` на ноде-владельце. Там `CheckFileFederationAccess` проверяет связь вложения обычного сообщения с участником на запрашивающей ноде, после чего `FetchFileStream` отдаёт байты. Files ноды получателя передаёт их клиенту.

Текущий `SendPrivateMessageCommandHandler` публикует событие только локальным участникам. Сервер не может создать связь для проверки доступа по `fileId`, который находится в зашифрованном JSON. Поэтому при v1 с текущими контрактами межнодовой отправки нет. В будущем серверу понадобится доставка, история и правки/удаления приватных конвертов через Federation со стабильным идентификатором чата для AAD. Также нужен серверный способ авторизовать скачивание объекта получателем и пиром. Один вариант — связать непрозрачные ссылки на зашифрованные объекты с приватным сообщением на обеих нодах, проверить участника локально и проверить пир на origin, затем передать ciphertext существующим потоком. Такой вариант раскрывает связь файла с сообщением обеим нодам и требует отдельного решения. Ключи и исходные метаданные по-прежнему извлекает только клиент из конверта.

## 6. Старые клиенты и откат

- Android с разблокированным чатом получает ошибку тега при попытке использовать прежний ключ и показывает `[не удалось расшифровать]` без вложений.
- Web с ключом чата по той же причине показывает `🔒 Не удалось расшифровать` без вложений.
- Windows старого формата получает `DecryptionFailed` из `WebApiPrivateChatManager`.
- В iOS и macOS на этой базе есть сгенерированные RPC-типы, но нет потока чтения приватных сообщений на уровне приложения. Сообщение с вложениями там не отображается как доступное приватное сообщение.

Получатели v1 показывают текст и вложения только после успешного чтения конверта. Отправка v1 при первом внедрении выключена по умолчанию и требует подтверждённой поддержки сторон или явно согласованного ограничения совместимости. Для отката выключается отправка v1, а чтение v1 сохраняется, чтобы ранее отправленные сообщения оставались доступны. У старого клиента после отката приложения будет прежнее сообщение об ошибке.

## 7. Угрозы и границы защиты

- Ключ чата общий. Как и у обычного текста приватного чата, AAD привязывает конверт к `chatId`, а криптографическое авторство и защита от повторной доставки внутри этого чата отсутствуют. Обладатель ключа может создать конверт, который пройдёт проверку тега. Повтор существующего конверта в том же чате тоже пройдёт проверку. Отображаемый отправитель берётся из метаданных Messages.
- Подмена байта или сегмента приводит к ошибке тега. Индекс в nonce связывает сегмент с позицией. Последний флаг, ожидаемая длина и проверка EOF защищают от обрезки и добавления данных. Замена целиком проверяется ключом объекта и хэшем из аутентифицированного конверта.
- Повтор шифрования сегмента с той же парой ключ и nonce недопустим. Источник должен оставаться неизменным на протяжении шифрования. При изменении исходника или создании нового объекта начинаются новый поток и новая операция. Сетевой повтор передаёт неизменный ciphertext.
- Клиентские временные файлы, кеш и очередь содержат только ciphertext. Библиотеки превью, декодеры, браузерное хранилище и системные просмотрщики могут создавать собственные файлы. В v1 допускается просмотр в памяти после проверки целостности. Для файлов сверх бюджета памяти просмотр отключён, а явное сохранение пользователем создаёт конечную копию по выбранному пути. До проверки всего объекта клиент может сделать проверочный проход по локальному ciphertext и только затем расшифровать его второй раз в выбранный результат. Пути, ключи, имена, содержимое и временные ссылки исключаются из журналов. Данные в памяти и ссылки на них очищаются по возможности при отмене и смене аккаунта.
- Превью загружается отдельным Document, расшифровывается с собственным ключом и выводится только после проверки и безопасного декодирования в пределах бюджета ресурсов.
- Размер, время, количество загрузок и их корреляция остаются наблюдаемыми. Участник с ключом чата способен сохранить файл. Удаление сообщения очищает ciphertext сообщения, а Files сохраняет объект, поскольку не знает связи с сообщением. Отмена отправки и сбой между загрузкой и отправкой также могут оставить объект. Серверной очистке понадобится политика хранения и связь или отметка жизненного цикла объекта.

## 8. Тестовые векторы

Команда запуска из корня репозитория требует Python 3 и установленный пакет `cryptography`.

```text
python Docs/private-chat-attachments-vectors.py
```

Скрипт проверяет фиксированные ожидаемые байты legacy, v1 payload, одного сегмента (`abc`) и пустого файла. Для четырёх сегментов из 12 201 байта (`byte[i] = i mod 251`) сверяется фиксированный SHA-256 целого шифротекста. Опция `--emit` выводит полные байты всех векторов в hex. Ключи, nonce сообщения, salt, префикс nonce потока, AAD и точная сериализация входа заданы в скрипте. [Тестовые векторы](private-chat-attachments-vectors.py)

Для файловых векторов используется многосегментный файл. Дескриптор меняется только у обрезанного потока с согласованным размером.

| Изменение | Ожидаемый отказ |
|---|---|
| XOR первого байта после заголовка с 1 | Ошибка тега |
| Удаление последнего байта | Ошибка длины |
| Обмен сегментов 1 и 2 при нумерации с нуля | Ошибка тега |
| Добавление 16-байтового финального сегмента пустого файла | Ошибка длины |
| Первые два сегмента с согласованными `size = 8120` и SHA-256 этого префикса | `InvalidTag` на сегменте 1, записанном с `final = 0` и прочитанном с `final = 1` |
| Склейка двух полных сегментов отдельно зашифрованного префикса с остатком исходного ciphertext. Оба потока используют одинаковые тестовые заголовок и IKM | `InvalidTag` на сегменте 1, записанном с `final = 1` и прочитанном с `final = 0` |
| XOR первого байта salt с 1 при неизменных заголовочной длине и длине объекта | `InvalidTag` на сегменте 0 |
| v1 конверт и AAD другого чата при сохранении производного ключа | `InvalidTag` от AES-GCM. Тест вызывает AES-GCM напрямую, чтобы проверить AAD независимо от предварительного сравнения маркера и вывода ключа |
| v1 конверт с прежним ключом чата | `InvalidTag` |
| Свойство `te\u0078t` рядом с `text` | Проверка дубликатов JSON |
| Лишнее поле `extra` в корне | Проверка списка полей v1 |
| UTF-8 BOM перед JSON | Проверка BOM до декодирования |

Скрипт выводит причину каждого отказа. Все константы векторов публичны и предназначены для тестов.

При установленном `tink` скрипт дополнительно проверяет оба направления через `streaming_aead` с RAW-шаблоном `AES256_GCM_HKDF_4KB` и фиксированным тестовым IKM. Tink читает детерминированные векторы, а скрипт читает записи с salt и префиксом nonce, сгенерированными Tink. Сверка с `tink` 1.16.1 прошла для одного и нескольких сегментов, пустого файла и полной границы сегмента. При отсутствии пакета скрипт выводит `SKIP Tink`.

## 9. Платформы и внедрение

Предел первого выпуска на всех клиентах, включая Web, — 16 МиБ plaintext на файл и 1 МиБ на превью. При загрузке также действует меньший лимит ноды на ciphertext с учётом накладных расходов §2. Читатель проверяет лимиты до загрузки и обрабатывает объекты по одному, чтобы ограничить пиковый расход памяти.

| Платформа | API и проверка перед включением |
|---|---|
| WinUI / .NET | Ручной фрейминг Tink по §2. Использовать `HKDF.DeriveKey(SHA256, …)`, `AesGcm(key, 16).Encrypt/Decrypt`, `RandomNumberGenerator.Fill`. Ciphertext и tag передаются в `AesGcm` отдельными буферами. Добавить v1 разбор в WebApi.Core и проверить чтение истории, realtime и правок, повтор загрузки и бюджет памяти. [Документация .NET](https://learn.microsoft.com/dotnet/api/system.security.cryptography.aesgcm) |
| Android / JVM | Для конверта JCA `Cipher.getInstance("AES/GCM/NoPadding")`, `GCMParameterSpec(128, nonce)`, `updateAAD`, `doFinal` и библиотечный HKDF-SHA-256. Для файла создать `com.google.crypto.tink.subtle.AesGcmHkdfStreaming(ikm, "HmacSha256", 32, 4096, 0)` и вызвать `newEncryptingStream/newDecryptingStream` с associated data из §2. `SecureRandom` для исходных ключей и nonce. Проверить потоковый ввод из content URI и отсутствие открытого кеша. [Android Cipher](https://developer.android.com/reference/javax/crypto/Cipher), [Реализация Tink Java](https://github.com/tink-crypto/tink-java/blob/main/src/main/java/com/google/crypto/tink/subtle/AesGcmHkdfStreaming.java) |
| Web | Ручной фрейминг Tink по §2. Использовать `crypto.getRandomValues`, `subtle.importKey`, `subtle.deriveKey` с HKDF/SHA-256. Вызывать `subtle.encrypt` или `subtle.decrypt` отдельно на каждый сегмент с его `iv`, пустым `additionalData` и `tagLength: 128`. Проверить память, число вызовов и доступность secure context. [Web Cryptography API](https://www.w3.org/TR/WebCryptoAPI/) |
| iOS и macOS | Сначала реализовать чтение приватного чата и совместимый вывод ключа. Ручной фрейминг Tink по §2 поверх CryptoKit `HKDF<SHA256>.deriveKey`, `AES.GCM.seal/open`, `AES.GCM.Nonce` и `AES.GCM.SealedBox(nonce:ciphertext:tag:)`. Собирать запись из `ciphertext` и `tag`. Проверить отсутствие открытого кеша в UI и системном просмотрщике. [CryptoKit HKDF](https://developer.apple.com/documentation/cryptokit/hkdf), [CryptoKit SealedBox](https://developer.apple.com/documentation/cryptokit/aes/gcm/sealedbox) |

Web держит расшифрованные части в памяти до итоговой проверки длины, EOF и SHA-256. Для явного сохранения после проверки браузер скачивает `Blob` через object URL. Клиент отзывает URL после использования и освобождает буферы. Проверка выпуска должна покрыть пиковую память и поведение браузера при сохранении, включая его управление временными данными. Приложение не записывает plaintext в IndexedDB или Cache API.

Сначала прогнать векторы на каждой платформе и выпустить чтение. Затем проверить загрузку, историю, обновления, правки, удаление, сбои загрузки и откат в смешанной паре клиентов. После согласования включить отправку на одной ноде. Федерацию проверять отдельно на двух нодах после появления серверной доставки и авторизации.

### Открытые решения

1. **Где включить отправку?** Варианты — сначала одна нода или ожидание межнодовой поддержки. Рекомендация — начать с одной ноды.
2. **Как подтверждать поддержку v1 на устройствах собеседника?** Варианты — явное объявление возможности каждым активным устройством или учёт проверенных версий устройств в тестовой группе. Для общего включения рекомендуется явное объявление возможности на уровне устройства.
3. **Разрешать ли тестовую отправку до появления сигнала возможностей?** Варианты — только тестовые пары с заранее проверенными устройствами или держать отправку выключенной для всех. Рекомендация — включать вручную только для проверенных тестовых пар.
4. **Как авторизовать скачивание ciphertext?** Варианты — текущая выдача аутентифицированному пользователю по известному ID или объектная проверка доступа участника до выдачи ссылки. Рекомендация — для общего включения потребовать объектную проверку доступа.
5. **Какой предел задать для файла?** Варианты — 16 МиБ или меньший общий предел, если испытания выявят нехватку памяти. Рекомендация — начать проверку с 16 МиБ и учитывать лимит ноды.
6. **Какой предел задать для превью?** Варианты — до 1 МиБ или выпуск без превью. Рекомендация — ограничить превью 1 МиБ и проверить бюджет декодирования.
7. **Скрывать ли точный размер?** Варианты — оставить длину наблюдаемой или ввести дополнение до диапазонов в новой версии. Рекомендация — сохранить текущую формулу в v1.
8. **Когда включить серверную очистку объектов осиротевших загрузок и удалённых сообщений?** Варианты — до общего выпуска или после него с принятым риском роста хранилища. Рекомендация — проверить политику очистки до общего выпуска.
9. **Раскрывать ли нодам связь объекта с приватным сообщением?** Варианты — хранить непрозрачную ссылку на объект для авторизации и очистки или проектировать механизм доступа без этой связи. Рекомендация — согласовать раскрытие отдельно перед реализацией федерации.
