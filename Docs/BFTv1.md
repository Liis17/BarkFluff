# BFTv1 — спецификация протокола

BarkFluff Transfer, версия 1. Побайтовый формат туннеля между клиентом и Exit-прокси и преамбулы Relay → Exit.

Статус: черновик спецификации до второго раунда ревью. Реализации (`Shared/BarkFluff.Bft`, Android `com.barkfluff.client.bft`) обязаны проходить общие тест-векторы `Docs/bft/bftv1-vectors.json`.

## 1. Обозначения

- Все многобайтовые целые — big-endian, если не сказано иное. `u8`, `u16`, `u32`, `u64` — беззнаковые целые.
- `‖` — конкатенация байтов.
- `AEAD(k, n, ad, pt)` — ChaCha20-Poly1305 (RFC 8439), результат `ciphertext ‖ tag(16)`.
- Nonce AEAD (12 байт) из счётчика `n` (`u64`): 4 нулевых байта ‖ `n` в **little-endian** (как в Noise для ChaChaPoly).
- `HKDF-Extract`, `HKDF-Expand` — RFC 5869 с SHA-256.
- Метки HKDF и прологи — ASCII без завершающего нуля.
- «Тихое закрытие» — сторона ничего не отправляет, продолжает читать и отбрасывать входящие байты и закрывает TCP через случайное время 1–10 с (или раньше, если соединение закрыл собеседник).

## 2. Слои

```
HTTP/2 (gRPC) или HTTP/1.1 к сервису      байты потока, для BFT непрозрачны
Мультиплексор                             кадры, раздел 6
Сессия Noise_NK_25519_ChaChaPoly_SHA256   раздел 5
Слой записей с обфускацией                раздел 4
Внешняя обёртка: v1 = TCP                 wrapper = 0
```

В транспортной фазе данные шифруются дважды: сообщение Noise лежит внутри записи слоя обфускации. Это сознательный выбор: оба слоя остаются стандартными и проверяются независимо.

## 3. Строка подключения

```
bft://<static-pubkey>.<obfs-key>@<host>:<port>[?token=<access-token>]
```

- `static-pubkey` — статический публичный ключ X25519 Exit, 32 байта, base64url без `=` (43 символа);
- `obfs-key` — ключ обфускации, 32 байта, base64url без `=` (43 символа);
- `host` — DNS-имя, IPv4 или IPv6 в квадратных скобках; `port` — 1–65535;
- `token` — необязательный токен доступа: 1–256 байт UTF-8, percent-encoded.

Неизвестные параметры запроса, другая длина ключей или недопустимые символы — строка отвергается целиком.

## 4. Слой записей

### 4.1. Соль и ключи

Первые 32 байта потока клиент → сервер — случайная соль `salt`. В обратном направлении соли нет.

```
PRK       = HKDF-Extract(salt = salt, IKM = obfs-key)
k_c2s_len = HKDF-Expand(PRK, "BFTv1 obfs c2s len",  32)
k_c2s_dat = HKDF-Expand(PRK, "BFTv1 obfs c2s data", 32)
k_s2c_len = HKDF-Expand(PRK, "BFTv1 obfs s2c len",  32)
k_s2c_dat = HKDF-Expand(PRK, "BFTv1 obfs s2c data", 32)
```

### 4.2. Запись

```
record = AEAD(k_len, n, "", u16 L)                       18 байт
       ‖ AEAD(k_dat, n, "", u16 P ‖ payload ‖ padding)   L байт
```

- `n` — счётчик записей направления, с 0, +1 на каждую запись. Обе части записи используют один `n` и разные ключи.
- `L` — длина второй части вместе с тегом: `L = 2 + P + padLen + 16`.
- `P` — длина `payload`; `padding` — `padLen` нулевых байтов.
- Ограничения: `P ≤ 16400`, `padLen ≤ 1024`, значит `18 ≤ L ≤ 17442`.
- Получатель обязан проверить: `L` в допустимом диапазоне, `2 + P ≤ L − 16`, все байты паддинга нулевые.
- Ключи слоя не перевыпускаются. При `n = 2^48` соединение закрывается.

Открытых магических байтов, версий и длин в потоке нет: всё после соли — выход AEAD.

### 4.3. Паддинг

- Записи хендшейка (первая запись каждой стороны): `padLen` — равномерно случайный из 0..1024.
- Остальные записи: `padLen` из 0..255 на усмотрение отправителя; допустим 0.

### 4.4. Ошибки

- Любая ошибка первой записи клиента (тег длины, диапазон `L`, тег данных, формат, раздел 5.2) — тихое закрытие.
- Любая ошибка записи после успешной первой — немедленное закрытие TCP без отправки данных.
- Обрыв TCP посреди записи — ошибка туннеля; частично полученная запись отбрасывается.

## 5. Сессия

### 5.1. Профиль

`Noise_NK_25519_ChaChaPoly_SHA256` по Noise Protocol Framework rev. 34:

```
<- s
...
-> e, es
<- e, ee
```

- Инициатор — клиент. `s` — статический ключ Exit из строки подключения.
- Полезная нагрузка обоих сообщений хендшейка пустая: сообщение 1 = `e(32) ‖ tag(16)`, сообщение 2 = `e(32) ‖ tag(16)`, по 48 байт.
- Если результат любого DH состоит из одних нулей, хендшейк прерывается (на сервере — тихое закрытие).
- Пролог: `"BFTv1" ‖ salt(32) ‖ ClientInit-заголовок(10)` (раздел 5.2).

### 5.2. Первая запись клиента

```
payload = version u8 ‖ wrapper u8 ‖ timestamp u64 ‖ noise_msg1(48)        58 байт
```

- `version` = 1. `wrapper` = 0 (TCP без внешней обёртки).
- `timestamp` — время клиента, секунды Unix.
- Первые 10 байт — «ClientInit-заголовок», входит в пролог Noise.

Сервер до вычисления DH проверяет по порядку:

1. запись расшифровалась, `P = 58`;
2. `version = 1`, `wrapper` соответствует способу подключения;
3. `|now − timestamp| ≤ 120` с;
4. `salt` отсутствует в кеше виденных солей; после проверки соль заносится в кеш на 300 с.

Любой отказ, включая ошибку Noise, — тихое закрытие.

Лимиты до завершения хендшейка: первая запись целиком должна прийти за 10 с; число незавершённых соединений на IP ограничено (по умолчанию 16); превышение — тихое закрытие.

### 5.3. Первая запись сервера

```
payload = noise_msg2(48)
```

После неё обе стороны выполняют `Split()`: первый `CipherState` — направление клиент → сервер, второй — сервер → клиент.

### 5.4. Транспортная фаза

- `payload` каждой следующей записи — ровно одно транспортное сообщение Noise: `AEAD(k, n, "", plaintext)`.
- `plaintext` — ноль или больше целых кадров мультиплексора; кадр не разрывается между сообщениями. `len(plaintext) ≤ 16384`.
- Rekey: после каждого 65536-го сообщения направления (то есть когда `n` этого `CipherState` становится кратным 65536 и не равным 0) обе стороны применяют к нему `Rekey()` из Noise; `n` не сбрасывается. Сигнализации нет, момент определяется счётчиком.

## 6. Мультиплексор

### 6.1. Кадр

```
frame = type u8 ‖ streamId u32 ‖ length u16 ‖ body(length)
```

`length ≤ 16377` (кадр целиком помещается в одно сообщение Noise). Кадры туннеля имеют `streamId = 0`.

| type | Кадр | streamId | body |
|---|---|---|---|
| 0x01 | `AUTH` | 0 | токен, 1–256 байт UTF-8 |
| 0x02 | `HELLO` | 0 | `idLen u8 ‖ proxyId(idLen) ‖ initialWindow u32 ‖ maxStreams u16 ‖ count u8 ‖ serviceId u8 × count` |
| 0x03 | `OPEN` | ≠ 0 | `serviceId u8` |
| 0x04 | `DATA` | ≠ 0 | байты потока, 1–16377 |
| 0x05 | `WINDOW_UPDATE` | ≠ 0 | `increment u32`, > 0 |
| 0x06 | `CLOSE` | ≠ 0 | пусто |
| 0x07 | `RESET` | ≠ 0 | `code u8` |
| 0x08 | `PING` | 0 | 8 произвольных байт |
| 0x09 | `PONG` | 0 | 8 байт из `PING` |
| 0x0A | `GOAWAY` | 0 | `lastStreamId u32 ‖ code u8` |

Неизвестный тип, неверный `streamId`, неверная длина тела или кадр, недопустимый в текущем состоянии туннеля, — ошибка протокола: `GOAWAY(PROTOCOL_ERROR)` и закрытие.

### 6.2. Начало туннеля

- Exit с включёнными токенами ждёт `AUTH` первым кадром клиента (не дольше 10 с). Токен верен — отправляет `HELLO`; неверен или кадр другой — `GOAWAY(AUTH_FAILED)` и закрытие.
- Exit без токенов отправляет `HELLO` сразу после хендшейка; полученный `AUTH` игнорирует.
- Клиент с токеном отправляет `AUTH` сразу после хендшейка. `OPEN` клиент отправляет только после `HELLO`.
- `HELLO` — первый и единственный такой кадр сервера. `proxyId` — 1–32 байта ASCII. `serviceId` в списке не повторяются.

### 6.3. Идентификаторы сервисов

| id | Сервис | id | Сервис |
|---|---|---|---|
| 1 | `beacon` | 7 | `updates` |
| 2 | `identity` | 8 | `onliner` |
| 3 | `users` | 9 | `fastauth` |
| 4 | `messages` | 10 | `calls` |
| 5 | `files` | 11 | `bots` |
| 6 | `files-media` | 12 | `storage` |

Клиент не передаёт адресов. Upstream определяется только `serviceId`.

### 6.4. Потоки

- Потоки открывает только клиент. `streamId` начинается с 1 и растёт на 1 с каждым `OPEN`. Повтор или уменьшение — ошибка протокола. После `2^32 − 1` нужен новый туннель.
- Подтверждения `OPEN` нет: клиент может сразу слать `DATA`. На недоступный сервис Exit отвечает `RESET(SERVICE_UNAVAILABLE)`, на превышение `maxStreams` — `RESET(STREAM_LIMIT)`.
- `CLOSE` — полузакрытие: отправитель больше не шлёт `DATA` в этом потоке. Поток завершён, когда `CLOSE` отправили обе стороны.
- `RESET` завершает поток немедленно в обе стороны. Кадры завершённого потока, пришедшие позже, молча отбрасываются.

### 6.5. Flow control

- У каждого направления каждого потока есть окно в байтах тела `DATA`. Начальное значение — `initialWindow` из `HELLO` (по умолчанию 262144), одинаковое для обоих направлений.
- `DATA` уменьшает окно отправителя; `WINDOW_UPDATE` от получателя увеличивает на `increment`. Получатель шлёт `WINDOW_UPDATE` по мере того, как приложение забирает данные.
- `DATA` сверх окна или окно больше `2^31 − 1` — `RESET(FLOW_CONTROL)`.
- Окна уровня туннеля нет. Отправитель планирует запись между потоками по кругу, не более одного кадра `DATA` от потока за проход.

### 6.6. Keepalive и завершение

- Сторона, не получавшая данных 30 с, шлёт `PING`. Нет `PONG` за 20 с — туннель считается оборванным. `PONG` отправляется вне очереди потоков.
- `GOAWAY`: потоки с `streamId > lastStreamId` не обработаны и могут быть безопасно повторены в новом туннеле; новые `OPEN` после `GOAWAY` запрещены; существующие потоки дорабатывают.

### 6.7. Коды

`RESET`:

| code | Имя | Смысл |
|---|---|---|
| 0 | `CANCEL` | Отмена стороной приложения |
| 1 | `SERVICE_UNAVAILABLE` | `serviceId` не настроен на Exit |
| 2 | `UPSTREAM_FAILED` | Ошибка на стороне Exit при обслуживании потока |
| 3 | `FLOW_CONTROL` | Нарушение окна |
| 4 | `STREAM_LIMIT` | Превышено `maxStreams` |
| 5 | `IDLE_TIMEOUT` | Поток простаивал дольше лимита |
| 6 | `INTERNAL` | Внутренняя ошибка |

`GOAWAY`:

| code | Имя |
|---|---|
| 0 | `SHUTDOWN` |
| 1 | `AUTH_FAILED` |
| 2 | `PROTOCOL_ERROR` |
| 3 | `OVERLOAD` |

Неизвестный код получатель трактует как `INTERNAL` / `SHUTDOWN`.

## 7. Преамбула Relay

Relay не имеет ключей Exit и не расшифровывает поток клиента.

1. Relay читает первые 32 байта клиента (`salt`). Если они не пришли за 10 с — закрывает соединение.
2. Relay отправляет Exit преамбулу, затем `salt` и все дальнейшие байты клиента без изменений:

```
K_pre    = HKDF-Expand(HKDF-Extract(salt = salt, IKM = relay-key), "BFTv1 relay preamble", 32)
preamble = AEAD(K_pre, 0, "", clientIp(16) ‖ clientPort u16 ‖ timestamp u64 ‖ relayId(16))      58 байт
```

- `relay-key` — общий ключ Relay ↔ Exit, 32 байта.
- `clientIp` — 16 байт IPv6; IPv4 записывается как IPv4-mapped (`::ffff:a.b.c.d`).
- `timestamp` — время Relay, секунды Unix.
- `relayId` — ASCII, дополненный нулями до 16 байт.

Поток на relay-порт Exit: `preamble(58) ‖ salt(32) ‖ записи клиента`. В обратном направлении Relay пересылает байты Exit без изменений.

Exit на relay-порту:

1. принимает соединения только с адресов из allowlist, остальные закрывает сразу;
2. читает 90 байт, выводит `K_pre` из следующей за преамбулой соли и проверяет AEAD;
3. проверяет `|now − timestamp| ≤ 120` с;
4. далее обрабатывает поток как прямое соединение (раздел 5.2, включая кеш солей), но адресом клиента считает `clientIp` из преамбулы.

Ключ преамбулы выводится из соли, поэтому преамбула не подходит ни к какому другому хендшейку. Любой отказ — тихое закрытие. На прямом порту преамбулы нет, адрес клиента берётся из TCP. В v1 цепочка — не более одного Relay.

## 8. Библиотеки

| Примитив | .NET | Android (minSdk 31) |
|---|---|---|
| ChaCha20-Poly1305 | `System.Security.Cryptography.ChaCha20Poly1305` | `javax.crypto.Cipher` `ChaCha20-Poly1305` |
| HKDF, HMAC, SHA-256 | `System.Security.Cryptography.HKDF` | `javax.crypto.Mac` `HmacSHA256`, собственный HKDF |
| X25519 | `BouncyCastle.Cryptography` (уже используется в Federation) | выбирается на этапе Android; совместимость подтверждается векторами |

Noise реализуется в обеих библиотеках поверх этих примитивов и сверяется с опубликованными векторами `Noise_NK_25519_ChaChaPoly_SHA256`.

## 9. Тест-векторы

Файл `Docs/bft/bftv1-vectors.json`, общий для .NET и Android. Все байты — hex. Генерируется скриптом `Docs/bft/generate_vectors.py` — реализацией, независимой от обеих библиотек.

Положительные:

- разбор строки подключения;
- ключи слоя обфускации из `obfs-key` и `salt`;
- записи с паддингом и без;
- полный хендшейк с фиксированными эфемерными ключами: байты обеих первых записей, хеш хендшейка, ключи после `Split()`;
- транспортные записи обоих направлений, включая переход через `Rekey()`;
- кодирование каждого типа кадра;
- преамбула Relay для IPv4 и IPv6.

Отрицательные (реализация обязана отвергнуть):

- изменённый бит в зашифрованной длине, в теле, в каждом из тегов;
- `L` вне диапазона, `P` больше тела, ненулевой паддинг;
- повтор записи и перестановка двух записей;
- обрыв посреди записи;
- неверный `obfs-key`, неверный статический ключ Exit;
- эфемерный ключ малого порядка (нулевой результат DH);
- `timestamp` вне окна, повтор `salt`, неверные `version` и `wrapper`;
- кадры: неизвестный тип, `length` больше остатка сообщения, `streamId = 0` у потокового кадра и наоборот, `WINDOW_UPDATE` с нулём;
- преамбула Relay с чужой солью, с изменённым битом, с просроченным временем.

## 10. Не входит в BFTv1

- Выбор HTTP/1.1 или HTTP/2 внутри потока и внутренний TLS до Exit: это уровень выше мультиплексора, решение фиксируется по итогам прототипа транспорта Android.
- Внешние обёртки, кроме TCP (`wrapper ≠ 0`).
- Цепочки из нескольких Relay.
- Устойчивость к зондированию со стороны того, кто знает строку подключения.
