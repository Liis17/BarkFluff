# BFTv1 — спецификация протокола

BarkFluff Transfer, версия 1. Побайтовый формат туннеля между клиентом и Exit-прокси и преамбулы Relay → Exit.

Статус: черновик спецификации до второго раунда ревью. Реализации (`Shared/BarkFluff.Bft`, Android `com.barkfluff.client.bft`) обязаны проходить общие тест-векторы `Docs/bft/bftv1-vectors.json`.

## 1. Обозначения

- Все многобайтовые целые — big-endian, если не сказано иное. `u8`, `u16`, `u32`, `u64` — беззнаковые целые.
- `‖` — конкатенация байтов.
- `AEAD(k, n, ad, pt)` — ChaCha20-Poly1305 (RFC 8439), результат `ciphertext ‖ tag(16)`.
- Nonce AEAD (12 байт) из счётчика `n` (`u64`): 4 нулевых байта ‖ `n` в **little-endian** (как в Noise для ChaChaPoly).
- `HKDF-Extract`, `HKDF-Expand` — RFC 5869 с SHA-256.
- Метки HKDF и прологи — ASCII без завершающего нуля.
- «Тихое закрытие» — сторона ничего не отправляет, продолжает читать и отбрасывать входящие байты и закрывает TCP через случайное время 1–10 с (или раньше, если соединение закрыл собеседник).

## 2. Слои

```
HTTP/2 (gRPC) или HTTP/1.1 к сервису      байты потока, для BFT непрозрачны
Мультиплексор                             кадры, раздел 6
Сессия Noise_NK_25519_ChaChaPoly_SHA256   раздел 5
Слой записей с обфускацией                раздел 4
Внешняя обёртка: v1 = TCP                 wrapper = 0
```

В транспортной фазе данные шифруются дважды: сообщение Noise лежит внутри записи слоя обфускации. Это сознательный выбор: оба слоя остаются стандартными и проверяются независимо.

## 3. Строка подключения

```
bft://<static-pubkey>.<obfs-key>@<host>:<port>[?token=<access-token>&name=<display-name>]
```

- `static-pubkey` — статический публичный ключ X25519 Exit, 32 байта, base64url без `=` (43 символа);
- `obfs-key` — индивидуальный ключ обфускации пользователя/строки подключения, 32 байта, base64url без `=` (43 символа). Exit настраивает до 1024 таких ключей; отзыв строки подключения означает удаление её ключа из списка;
- `host` — DNS-имя, IPv4 или IPv6 в квадратных скобках; `port` — 1–65535;
- `token` — необязательный дополнительный токен доступа: 1–256 байт UTF-8, percent-encoded; кадр `AUTH` остаётся отдельным необязательным механизмом;
- `name` — необязательное percent-encoded отображаемое имя прокси: 1–64 кодовые точки Unicode после decoding, валидный UTF-8, без управляющих символов.

Порядок `token` и `name` произвольный. Повтор параметра, неизвестный параметр, некорректный UTF-8, другая длина ключей или недопустимые символы — строка отвергается целиком.

Закодированная форма для раздачи пользователям:

```
bft://<base64url(тело)>
```

`тело` — UTF-8 всего, что в классической форме идёт после `bft://` (`<static-pubkey>.<obfs-key>@<host>:<port>[?...]`), в base64url без `=`. Парсер распознаёт закодированную форму, если после `bft://` стоят только символы `A–Z a–z 0–9 - _` (допускается до двух завершающих `=`; не длиннее 4096 символов), декодирует её и проверяет результат по правилам классической формы; вложенное кодирование не допускается. Классическая форма продолжает приниматься. Это кодирование, а не шифрование: ключи и токен восстанавливаются из ссылки без секрета.

## 4. Слой записей

### 4.1. Соль и ключи

Первые 32 байта потока клиент → сервер — случайная соль `salt`. В обратном направлении соли нет. Exit перебирает настроенные `obfs-key` и выбирает первый, с которым аутентифицируется зашифрованная длина первой записи клиента (18 байт). Если ни один ключ не подошёл, Exit закрывает соединение тихо. Это правило одинаково для прямого и relay-порта.

```
PRK       = HKDF-Extract(salt = salt, IKM = obfs-key)
k_c2s_len = HKDF-Expand(PRK, "BFTv1 obfs c2s len",  32)
k_c2s_dat = HKDF-Expand(PRK, "BFTv1 obfs c2s data", 32)
k_s2c_len = HKDF-Expand(PRK, "BFTv1 obfs s2c len",  32)
k_s2c_dat = HKDF-Expand(PRK, "BFTv1 obfs s2c data", 32)
```

### 4.2. Запись

```
record = AEAD(k_len, n, "", u16 L)                       18 байт
       ‖ AEAD(k_dat, n, "", u16 P ‖ payload ‖ padding)   L байт
```

- `n` — счётчик записей направления, с 0, +1 на каждую запись. Обе части записи используют один `n` и разные ключи.
- `L` — длина второй части вместе с тегом: `L = 2 + P + padLen + 16`.
- `P` — длина `payload`; `padding` — `padLen` нулевых байтов.
- Ограничения: `P ≤ 16400`, `padLen ≤ 1024`, значит `18 ≤ L ≤ 17442`.
- Получатель обязан проверить: `L` в допустимом диапазоне, `2 + P ≤ L − 16`, все байты паддинга нулевые.
- Ключи слоя не перевыпускаются. При `n = 2^48` соединение закрывается.

Открытых магических байтов, версий и длин в потоке нет: всё после соли — выход AEAD.

### 4.3. Паддинг

- Записи хендшейка (первая запись каждой стороны): `padLen` — равномерно случайный из 0..1024.
- После хендшейка отправитель для каждой записи с `P < 1024` выбирает `padLen` равномерно случайно из 0..255; при `P ≥ 1024` использует `padLen = 0`.

### 4.4. Ошибки

- Любая ошибка первой записи клиента (тег длины, диапазон `L`, тег данных, формат, раздел 5.2) — тихое закрытие.
- Любая ошибка записи после успешной первой — немедленное закрытие TCP без отправки данных.
- Обрыв TCP посреди записи — ошибка туннеля; частично полученная запись отбрасывается.

## 5. Сессия

### 5.1. Профиль

`Noise_NK_25519_ChaChaPoly_SHA256` по Noise Protocol Framework rev. 34:

```
<- s
...
-> e, es
<- e, ee
```

- Инициатор — клиент. `s` — статический ключ Exit из строки подключения.
- Полезная нагрузка обоих сообщений хендшейка пустая: сообщение 1 = `e(32) ‖ tag(16)`, сообщение 2 = `e(32) ‖ tag(16)`, по 48 байт.
- Если результат любого DH состоит из одних нулей, хендшейк прерывается (на сервере — тихое закрытие).
- Пролог: `"BFTv1" ‖ salt(32) ‖ ClientInit-заголовок(10)` (раздел 5.2).

### 5.2. Первая запись клиента

```
payload = version u8 ‖ wrapper u8 ‖ timestamp u64 ‖ noise_msg1(48)        58 байт
```

- `version` = 1. `wrapper` = 0 (TCP без внешней обёртки).
- `timestamp` — время клиента, секунды Unix.
- Первые 10 байт — «ClientInit-заголовок», входит в пролог Noise.

Exit пробует настроенные ключи, пока тег зашифрованной длины первой записи (18 байт) не аутентифицируется; для первого подошедшего ключа Exit проверяет по порядку:

1. запись расшифровалась, `P = 58`;
2. `version = 1`, `wrapper` соответствует способу подключения;
3. `|now − timestamp| ≤ 120` с;
4. `salt` отсутствует в кеше виденных солей; после проверки соль заносится в кеш на 300 с.

Любой отказ, включая ошибку Noise, — тихое закрытие.

Кеш солей:

- кеш общий для всех `obfs-key`; соль заносится только после проверок первой записи и заголовка, то есть не зная подходящий `obfs-key`, кеш заполнить нельзя;
- проверка и занесение — одна атомарная операция: из двух одновременных соединений с одной солью проходит не больше одного;
- вместимость ограничена (по умолчанию 1 000 000 записей). При заполнении новые сессии отклоняются тихим закрытием, уже занесённые соли не вытесняются до истечения 300 с.

Лимиты до завершения хендшейка (соединения в тихом закрытии считаются незавершёнными):

- первая запись целиком должна прийти за 10 с;
- незавершённых соединений на один IP — не больше 16 (по умолчанию);
- незавершённых соединений всего — не больше 1024 (по умолчанию);
- соединение сверх любого из двух лимитов закрывается сразу, без тихого закрытия.

### 5.3. Первая запись сервера

```
payload = noise_msg2(48)
```

После неё обе стороны выполняют `Split()`: первый `CipherState` — направление клиент → сервер, второй — сервер → клиент.

### 5.4. Транспортная фаза

- `payload` каждой следующей записи — ровно одно транспортное сообщение Noise: `AEAD(k, n, "", plaintext)`.
- `plaintext` — ноль или больше целых кадров мультиплексора; кадр не разрывается между сообщениями. `len(plaintext) ≤ 16384`.
- Rekey: после каждого 65536-го сообщения направления (то есть когда `n` этого `CipherState` становится кратным 65536 и не равным 0) обе стороны применяют к нему `Rekey()` из Noise; `n` не сбрасывается. Сигнализации нет, момент определяется счётчиком.

## 6. Мультиплексор

### 6.1. Кадр

```
frame = type u8 ‖ streamId u32 ‖ length u16 ‖ body(length)
```

`length ≤ 16377` (кадр целиком помещается в одно сообщение Noise). Кадры туннеля имеют `streamId = 0`.

| type | Кадр | streamId | body |
|---|---|---|---|
| 0x01 | `AUTH` | 0 | токен, 1–256 байт UTF-8 |
| 0x02 | `HELLO` | 0 | `idLen u8 ‖ proxyId(idLen) ‖ initialWindow u32 ‖ maxStreams u16 ‖ tlsSpkiSha256(32) ‖ count u8 ‖ serviceId u8 × count` |
| 0x03 | `OPEN` | ≠ 0 | `serviceId u8` |
| 0x04 | `DATA` | ≠ 0 | байты потока, 1–16377 |
| 0x05 | `WINDOW_UPDATE` | ≠ 0 | `increment u32`, > 0 |
| 0x06 | `CLOSE` | ≠ 0 | пусто |
| 0x07 | `RESET` | ≠ 0 | `code u8` |
| 0x08 | `PING` | 0 | 8 произвольных байт |
| 0x09 | `PONG` | 0 | 8 байт из `PING` |
| 0x0A | `GOAWAY` | 0 | `lastStreamId u32 ‖ code u8` |

Ошибка уровня кадров и мультиплексора — это неизвестный тип, `streamId`, не соответствующий таблице, неверная длина или содержимое тела, кадр, недопустимый в текущем состоянии туннеля (раздел 6.2), и случаи, прямо названные в разделе 6.4. Exit при такой ошибке отправляет `GOAWAY(PROTOCOL_ERROR)` и закрывает TCP; клиент закрывает TCP. Ошибка слоя записей после первой записи (§4.4) закрывает соединение немедленно, без отправки данных.

### 6.2. Начало туннеля

- Exit с включёнными токенами ждёт `AUTH` первым кадром клиента (не дольше 10 с). Токен верен — отправляет `HELLO`; неверен или кадр другой — `GOAWAY(AUTH_FAILED)` и закрытие.
- Exit без токенов отправляет `HELLO` сразу после хендшейка; полученный `AUTH` игнорирует.
- Клиент с токеном отправляет `AUTH` сразу после хендшейка. `OPEN` клиент отправляет только после `HELLO`.
- `HELLO` — первый и единственный такой кадр сервера. `proxyId` — 1–32 байта ASCII; `tlsSpkiSha256` — SHA-256 от DER-кодировки SubjectPublicKeyInfo сертификата внутреннего TLS Exit. Подлинность Exit уже проверена Noise, поэтому клиент закрепляет TLS-сертификат по этому пину. `16384 ≤ initialWindow ≤ 2^31 − 1`, `maxStreams ≥ 1`, `serviceId` в списке не повторяются. `HELLO`, нарушающий эти условия, — ошибка протокола.
- Для внутреннего TLS клиент использует имя `bft.internal`.
- `AUTH` и `OPEN` отправляет только клиент; `HELLO` и `GOAWAY` — только Exit. Такой кадр в обратном направлении — ошибка протокола.

### 6.3. Идентификаторы сервисов

| id | Сервис | id | Сервис |
|---|---|---|---|
| 1 | `beacon` | 7 | `updates` |
| 2 | `identity` | 8 | `onliner` |
| 3 | `users` | 9 | `fastauth` |
| 4 | `messages` | 10 | `calls` |
| 5 | `files` | 11 | `bots` |
| 6 | `files-media` | 12 | `storage` |

Клиент не передаёт адресов. Upstream определяется только `serviceId`.

### 6.4. Потоки

Потоки открывает только клиент. `streamId` первого потока — 1, каждого следующего — на 1 больше. После `2^32 − 1` нужен новый туннель. Пусть `maxOpened` — наибольший `streamId`, для которого отправлен (у клиента) или принят (у Exit) `OPEN`; в начале 0.

Подтверждения `OPEN` нет: клиент может сразу слать `DATA`. На недоступный сервис Exit отвечает `RESET(SERVICE_UNAVAILABLE)`, на превышение `maxStreams` одновременно открытых потоков — `RESET(STREAM_LIMIT)`.

`CLOSE` — полузакрытие: отправитель больше не шлёт `DATA`. `RESET` завершает поток немедленно в обе стороны.

Состояние потока у каждой стороны: `open` → после полученного `CLOSE` «закрыт собеседником», после отправленного — «закрыт нами»; когда `CLOSE` отправили обе стороны либо отправлен или получен `RESET` — `closed`. Поток с `streamId ≤ maxOpened`, которого нет среди активных, считается `closed`; отдельно хранить завершённые потоки не нужно.

Действие получателя потокового кадра, проверки сверху вниз:

| Условие | Действие |
|---|---|
| `OPEN`, `streamId ≠ maxOpened + 1` | Ошибка протокола (в том числе для уже завершённого потока) |
| Не `OPEN`, `streamId > maxOpened` | Ошибка протокола |
| Поток `closed` | Кадр молча отбрасывается |
| `DATA` или `CLOSE` в потоке, закрытом собеседником | `RESET(STREAM_CLOSED)` |
| `WINDOW_UPDATE` в потоке, закрытом нами | Отбрасывается |
| Остальное | Обычная обработка |

Гонки следуют из таблицы: после отправки `RESET` поток у отправителя `closed`, и встречные `DATA`, `CLOSE`, `WINDOW_UPDATE`, `RESET` отбрасываются.

### 6.5. Flow control

- У каждого направления каждого потока есть окно в байтах тела `DATA`. Начальное значение — `initialWindow` из `HELLO` (по умолчанию 262144), одинаковое для обоих направлений.
- `DATA` уменьшает окно отправителя; `WINDOW_UPDATE` от получателя увеличивает на `increment`. Получатель шлёт `WINDOW_UPDATE` по мере того, как приложение забирает данные.
- `DATA` сверх окна или окно больше `2^31 − 1` — `RESET(FLOW_CONTROL)`.
- Окна уровня туннеля нет. Отправитель планирует запись между потоками по кругу, не более одного кадра `DATA` от потока за проход; поток с нулевым окном пропускается.
- Получатель буферизует до размера окна на поток и не прекращает читать туннель из-за того, что приложение одного потока не забирает данные.

### 6.6. Keepalive и завершение

- Сторона, не получавшая данных 30 с, шлёт `PING`. Нет `PONG` за 20 с — туннель считается оборванным. `PONG` отправляется вне очереди потоков.
- `GOAWAY` отправляет только Exit и не больше одного раза за туннель. `lastStreamId` — значение `maxOpened` у Exit в момент отправки.
- После отправки `GOAWAY` Exit молча отбрасывает все кадры потоков с `streamId > lastStreamId` и не обращается ради них к upstream; ошибкой протокола они не считаются. Потоки с `streamId ≤ lastStreamId` дорабатывают.
- С кодом, отличным от `SHUTDOWN`, Exit закрывает TCP сразу после `GOAWAY`. С `SHUTDOWN` — после завершения оставшихся потоков или по своему таймауту.
- Клиент после `GOAWAY` не отправляет `OPEN`. Потоки с `streamId > lastStreamId` он считает необработанными: их запросы можно повторить в новом туннеле. Потоки с `streamId ≤ lastStreamId`, оборванные закрытием туннеля, автоматически не повторяются.

### 6.7. Коды

`RESET`:

| code | Имя | Смысл |
|---|---|---|
| 0 | `CANCEL` | Отмена стороной приложения |
| 1 | `SERVICE_UNAVAILABLE` | `serviceId` не настроен на Exit |
| 2 | `UPSTREAM_FAILED` | Ошибка на стороне Exit при обслуживании потока |
| 3 | `FLOW_CONTROL` | Нарушение окна |
| 4 | `STREAM_LIMIT` | Превышено `maxStreams` |
| 5 | `IDLE_TIMEOUT` | Поток простаивал дольше лимита |
| 6 | `INTERNAL` | Внутренняя ошибка |
| 7 | `STREAM_CLOSED` | `DATA` или `CLOSE` после `CLOSE` той же стороны |

`GOAWAY`:

| code | Имя |
|---|---|
| 0 | `SHUTDOWN` |
| 1 | `AUTH_FAILED` |
| 2 | `PROTOCOL_ERROR` |
| 3 | `OVERLOAD` |

Неизвестный код получатель трактует как `INTERNAL` / `SHUTDOWN`.

## 7. Преамбула Relay

Relay не имеет ключей Exit и не расшифровывает поток клиента.

1. Relay читает первые 32 байта клиента (`salt`). Если они не пришли за 10 с — закрывает соединение.
2. Relay генерирует 16 случайных байт `relayNonce` — новые для каждого соединения.
3. Relay отправляет Exit преамбулу, затем `salt` и все дальнейшие байты клиента без изменений:

```
PRK_pre  = HKDF-Extract(salt = salt, IKM = relay-key)
K_pre    = HKDF-Expand(PRK_pre, "BFTv1 relay preamble" ‖ relayNonce, 32)
preamble = relayNonce(16)
         ‖ AEAD(K_pre, 0, "", clientIp(16) ‖ clientPort u16 ‖ timestamp u64 ‖ relayId(16))      74 байта
```

- `relay-key` — общий ключ Relay ↔ Exit, 32 байта.
- `clientIp` — 16 байт IPv6; IPv4 записывается как IPv4-mapped (`::ffff:a.b.c.d`).
- `timestamp` — время Relay, секунды Unix.
- `relayId` — ASCII, дополненный нулями до 16 байт.

Соль выбирает клиент и может её повторять, поэтому уникальность пары (ключ, nonce) обеспечивает `relayNonce`, а не соль. Соль привязывает преамбулу к хендшейку.

Поток на relay-порт Exit: `preamble(74) ‖ salt(32) ‖ записи клиента`. В обратном направлении Relay пересылает байты Exit без изменений.

Exit на relay-порту:

1. принимает соединения только с адресов из allowlist, остальные закрывает сразу;
2. читает 106 байт (не дольше 10 с), выводит `K_pre` из `relayNonce` и следующей за преамбулой соли, проверяет AEAD;
3. проверяет `|now − timestamp| ≤ 120` с;
4. далее обрабатывает поток как прямое соединение (раздел 5.2, включая перебор того же списка `obfs-key`, общий кеш солей и срок первой записи), но адресом клиента считает `clientIp` из преамбулы. Лимит незавершённых соединений на IP считается по `clientIp`.

Любой отказ — тихое закрытие. На прямом порту преамбулы нет, адрес клиента берётся из TCP. В v1 цепочка — не более одного Relay.

| X25519 | `BouncyCastle.Cryptography` (уже используется в Federation) | выбирается на этапе Android; совместимость подтверждается векторами |

Noise реализуется в обеих библиотеках поверх этих примитивов и сверяется с опубликованными векторами `Noise_NK_25519_ChaChaPoly_SHA256`.

## 9. Тест-векторы

Файл `Docs/bft/bftv1-vectors.json`, общий для .NET и Android. Все байты — hex. Генерируется скриптом `Docs/bft/generate_vectors.py` — реализацией, независимой от обеих библиотек.

Положительные:

- разбор строки подключения;
- ключи слоя обфускации из `obfs-key` и `salt`;
- записи с паддингом и без;
- полный хендшейк с фиксированными эфемерными ключами: байты обеих первых записей, хеш хендшейка, ключи после `Split()`;
- транспортные записи обоих направлений, включая переход через `Rekey()`;
- кодирование каждого типа кадра;
- преамбула Relay для IPv4 и IPv6.

Отрицательные (реализация обязана отвергнуть):

- изменённый бит в зашифрованной длине, в теле, в каждом из тегов;
- `L` вне диапазона, `P` больше тела, ненулевой паддинг;
- повтор записи и перестановка двух записей;
- обрыв посреди записи;
- неверный `obfs-key`, неверный статический ключ Exit;
- эфемерный ключ малого порядка (нулевой результат DH);
- `timestamp` вне окна, повтор `salt`, неверные `version` и `wrapper`;
- кадры: неизвестный тип, `length` больше остатка сообщения, `streamId = 0` у потокового кадра и наоборот, `WINDOW_UPDATE` с нулём;
- `HELLO` с `initialWindow` 0 и `2^31`, с повтором `serviceId`;
- преамбула Relay с чужой солью, с изменённым битом, с просроченным временем.

Последовательности мультиплексора (`muxSequences`): кадры, которые получает сторона, и ожидаемое действие на последний из них — по таблице раздела 6.4 и правилам `GOAWAY`.

## 10. Не входит в BFTv1

- Внутренний TLS до Exit, выбор HTTP/1.1 или HTTP/2 и ALPN: это уровень выше мультиплексора. BFT передаёт в `HELLO` только `tlsSpkiSha256`; TLS и ALPN устанавливаются внутри каждого потока поверх BFT.
- Внешние обёртки, кроме TCP (`wrapper ≠ 0`).
- Цепочки из нескольких Relay.
- Устойчивость к зондированию со стороны того, кто знает строку подключения.
- Паддинг маскирует размеры записей с полезной нагрузкой менее 1024 байт по правилу раздела 4.3; тайминги обмена и общий объём переданных данных не скрываются.
