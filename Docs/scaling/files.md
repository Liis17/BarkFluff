# Масштабирование: BarkFluff.Files

**Вердикт: НЕ МОЖЕТ (близко к «может»).** Постоянное хранилище — Minio/S3 (общее, это плюс). Блокеры
— временные файлы на локальном диске при обработке видео/крупных файлов и общий отзыв сессий.

## Блокеры

| Блокер | Файл | Почему ломается при N экземплярах |
|--------|------|-----------------------------------|
| Локальный temp для обложки видео | `Backend/BarkFluff.Files/Services/VideoThumbnailExtractor.cs:45` (`Path.GetTempPath()`) | Пишет во временный файл локального инстанса |
| Локальный temp-буфер для видео и файлов >100 МБ | `Backend/BarkFluff.Files/Features/UploadFile/UploadFileCommandHandler.cs:129-149` (`Path.GetTempFileName()`) | Буферизация загрузки через локальный диск инстанса |
| Отзыв сессий (shared) | эндпоинт `session-revoked-files`; consumer `Consumers/SessionRevokedConsumer.cs` | См. [_shared-token-revocation.md](_shared-token-revocation.md) |
| `TempFileCleanupService` (дублируемый таймер, 1 час) | `Backend/BarkFluff.Files/Services/TempFileCleanupService.cs:9-24` | Идемпотентный DELETE, выполняется N раз; не критично |

## Анализ temp-файлов

Важно: локальный temp здесь **эфемерный и per-request** — файл создаётся, используется в рамках одного
запроса (ffmpeg/ffprobe, буфер загрузки) и удаляется в `finally`. Он **не** является общим состоянием
между запросами и **не** должен быть виден другим инстансам. Поэтому это **не** блокер корректности
масштабирования — при условии, что у каждого инстанса есть свой изолированный `TMPDIR` и достаточно
места на диске.

Реальные требования для нескольких инстансов:

- у каждого инстанса **свой** локальный temp (не общий сетевой том — иначе коллизии/износ);
- достаточный размер temp-раздела под пиковые видео/крупные файлы;
- очистка temp при рестарте (частично закрывает `TempFileCleanupService`).

## План реализации

1. **Зафиксировать как осознанный компромисс.** Оставить локальный temp, но:
   - убедиться, что `Path.GetTempPath()`/`TMPDIR` указывает на локальный (не разделяемый между
     инстансами) каталог; в Docker — на writable-слой контейнера, не на общий volume;
   - задать лимит диска под temp с запасом на пиковые размеры;
   - имена уже уникальны (`Guid.NewGuid():N` / `GetTempFileName`) — коллизий нет.
2. **(Опционально) Вынести буфер в объектное хранилище.** Если локальный диск нежелателен —
   буферизовать крупные загрузки через Minio/S3 (multipart upload) вместо `Path.GetTempFileName()`.
   Более трудоёмко; для v1 не обязательно.
3. **Отзыв сессий** — по общему плану (fan-out `session-revoked-files`).
4. **`TempFileCleanupService`** — по желанию под распределённым локом; не критично.

После п.1 и п.3 сервис масштабируется горизонтально (persistent-данные уже в общем S3).

## Критерии проверки

- `dotnet build Backend/BarkFluff.Files/BarkFluff.Files.csproj`.
- Тесты `BarkFluff.Files.Tests` (в т.ч. `SessionRevokedConsumerTests`) зелёные.
- Ручная логика: загрузка/скачивание/превью работают одинаково на 2 инстансах (данные из общего S3);
  temp одного инстанса не требуется другому; отзыв сессии виден обоим.
