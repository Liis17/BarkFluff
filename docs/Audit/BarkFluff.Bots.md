# Аудит: BarkFluff.Bots

> Дата: 2026-07-10. Дополнение: 2026-07-12. Область: код Bot API (gRPC и HTTP), BotFather, хранение токенов/updates, Docker и nginx.

## Сводка

Bots предоставляет внешний Bot API: HTTP-маршруты `/bot/*` и gRPC `BotsExternalApi` аутентифицируются токеном бота, который генерируется криптографически, хранится только как SHA-256-хеш и сравнивается в constant-time. У исходящих сообщений проверка членства бота в чате делегирована Messages-сервису, а для одного бота разрешён лишь один поток обновлений. Найдены три проблемы: зарегистрированный пользователь может без лимита создавать ботов и получать отдельную квоту хранилища в 1 ГБ на каждого, gRPC-reflection опубликована без авторизации, а крупные multipart-загрузки создают pre-auth нагрузку на nginx и многократно копируются в памяти сервиса.

**SQL-инъекции (доп. проверка 2026-07-22):** не найдены. `BotsStorage`/`BotUpdatesStorage`/`BotFatherSessionsStorage` используют только EF Core LINQ, raw-SQL в сервисе отсутствует.

## Безопасность

### S1. ~~Нет лимита числа ботов на владельца; каждый бот получает квоту вложений 1 ГБ~~ — ~~Medium~~ **Исправлено (2026-07-15)**

**Файл:** `Backend/BarkFluff.Bots/Services/BotFather/BotFatherService.cs` (`/newbot`, `MaxBotsPerOwner`).
**Решение:** Введён жёсткий лимит `MaxBotsPerOwner = 10`. Проверяется на входе в команду `/newbot` (до старта диалога имя→username), считает текущих ботов владельца через `BotsStorage.GetByOwner`; при достижении лимита создание отклоняется с подсказкой удалить существующего бота.

### S2. ~~gRPC-reflection опубликована без авторизации~~ — ~~Medium~~ **Исправлено (2026-07-15)**

**Файл:** `Backend/BarkFluff.Bots/Program.cs`.
**Решение:** `AddGrpcReflection()`/`MapGrpcReflectionService()` включены только под `IsDevelopment()` — тот же паттерн, что уже применён в Beacon/FastAuth/ClientStorage.

### S3. Multipart-загрузка до 50 МБ допускает pre-auth DoS и многократное копирование в память — Medium **→ Отложено**

**Файлы:** nginx-буферизация и общий лимит — `Backend/nginx/bots.conf:16-30`; чтение/копирование файла — `Backend/BarkFluff.Bots/Host/Http/BotApiEndpoints.cs:67-115`; лимитер — `Services/BotRateLimiter.cs:11-26`.
**Проблема:** nginx разрешает тело до 50 МБ для всех `/bot/` и по умолчанию полностью буферизует request body до передачи приложению, то есть до проверки `X-Bot-Token`. Для валидного токена `ReadFormAsync` принимает файл, затем код копирует его в `MemoryStream`, создаёт ещё один массив через `ToArray()` и снова копирует данные в `ByteString.CopyFrom`. Лимитер считает только запросы (до 30/с на бота), но не ограничивает одновременные загрузки или байты.
**Почему это проблема:** Без токена атакующий может удерживать соединения и заполнять временный диск nginx параллельными большими/медленными телами. С одним валидным bot-токеном несколько параллельных 50-МБ файлов создают сотни мегабайт крупных managed-аллокаций на запрос, вызывая LOH/GC pressure и потенциальный OOM до завершения межсервисной загрузки. S1 касается долговременного расхода S3-квоты через множество ботов, а не немедленного отказа инстанса.
**Рекомендация:** Выделить upload-методы в отдельный nginx location, отключить предварительную буферизацию (`proxy_request_buffering off`) и задать `client_body_timeout`, `limit_conn` и IP rate limit; для остальных `/bot/` оставить малый body limit. В приложении снизить максимальный размер файла, добавить concurrency/byte-rate quota и передавать файл потоково без `MemoryStream`/`ToArray`/повторного `ByteString`-копирования. Полный фикс — перевод на client-streaming gRPC или HTTP upload-slot механизм Files-сервиса вместо unary с байтами целиком.

### Позитив

- Bot-токен содержит 32 случайных байта, в БД хранится только SHA-256-хеш, сравнение выполняется через `CryptographicOperations.FixedTimeEquals` (`Services/BotTokenService.cs:14-18,46-50`).
- HTTP-токен передаётся заголовком `X-Bot-Token`, не частью URL (`Host/Http/BotTokenEndpointFilter.cs:9-39`); токены не должны попадать в URL-логи прокси.
- `BotPollingGuard` не допускает параллельные long-poll/stream для одного бота (`Services/BotPollingGuard.cs:11-16`), поэтому один токен не может создать гонку при подтверждении update'ов.
