# Аудит: Barkfluff.CloudMessaging

> Дата: 2026-06-12. Дополнение: 2026-07-12. Область: код сервиса, Dockerfile, nginx, docker-compose.

## Сводка

CloudMessaging — background worker без публичного API: три MassTransit-консьюмера (push о новых сообщениях, dismiss-команды, админ-рассылки) и `FirebaseService` поверх Firebase Admin SDK. Базовая гигиена хорошая: credentials Firebase не закоммичены в репозиторий и не попадают в Docker-образ (в `Backend/sample.env` — только плейсхолдеры, `.dockerignore` исключает `.env`), отправка идёт батчами через `SendEachForMulticastAsync`, в логи ошибок попадает только 10-символьный префикс FCM-токена. Главные проблемы: невалидные (unregistered) токены детектируются, но никогда не удаляются из БД (висящий TODO), батчи новых сообщений и dismiss не чанкуются по лимиту FCM в 500 токенов (при превышении падает вся отправка), а в `docker-compose-master.yml` в контейнер монтируется JSON service-account, который код вообще не читает.

## Безопасность

### S1. Unregistered FCM-токены детектируются, но не удаляются из БД — Medium

**Файл:** `Backend/Barkfluff.CloudMessaging/Services/FirebaseService.cs:159-165` (TODO на строке 164; аналогично 242-247 для dismiss и 339-344 для admin-broadcast)
**Проблема:** При ответе FCM с `MessagingErrorCode.Unregistered` токены собираются в список `unregisteredTokens`, логируется только их количество, после чего список выбрасывается. Комментарий `// TODO: отправить событие на удаление токенов из БД` так и не реализован — ни в одном из трёх методов отправки.
**Почему это проблема:** Мёртвые токены (переустановка приложения, отзыв токена, смена устройства) накапливаются в БД Users бессрочно. Каждый последующий push снова отправляется на них: лишние запросы к FCM, рост `FailureCount`, замусоривание логов ошибками и постепенная деградация полезной доли каждого батча. С точки зрения приватности устаревшие push-токены — это идентификаторы устройств, которые хранятся дольше, чем необходимо.
**Рекомендация:** Реализовать TODO: публиковать в RabbitMQ событие вида `InvalidFcmTokensDetectedEvent` со списком токенов, а в сервисе Users — консьюмер, который очищает поле `FirebaseToken` у соответствующих устройств.

### S2. PII (имя отправителя) в логах уровня Information — Low

**Файл:** `Backend/Barkfluff.CloudMessaging/Consumers/PushNotificationConsumer.cs:113-117`
**Проблема:** После отправки push в лог уровня Information пишется `senderName` (имя+фамилия или username отправителя сообщения): `"Push-уведомления отправлены. Отправитель: {SenderName}..."`. Аналогично заголовок админ-рассылки логируется в `FirebaseService.cs:354-359` и `AdminBroadcastConsumer.cs:34-37`.
**Почему это проблема:** Имена пользователей — персональные данные; они попадают в централизованный Seq и файловые логи, где доступны всем, у кого есть доступ к логам, и хранятся по ретенции логов, а не по правилам хранения PII. Для диагностики достаточно `SenderId`, который уже логируется в той же цепочке.
**Рекомендация:** Убрать `senderName` из лог-сообщения (оставить `SenderId`, `ChatId`, `MessageId`, количество устройств). Для админ-рассылок заголовок менее чувствителен, но его тоже можно заменить на идентификатор рассылки.

### S3. Превью текста сообщения передаётся в инфраструктуру Google (FCM) — Low

**Файл:** `Backend/Barkfluff.CloudMessaging/Services/FirebaseService.cs:115`
**Проблема:** В data-payload push-уведомления включается `message_text` — первые 100 символов текста сообщения (`TruncateMessage(messagePreview, 100)`), а также имя отправителя, название чата и URL аватаров.
**Почему это проблема:** Содержимое личных сообщений в открытом виде проходит через серверы FCM (третья сторона). Это стандартная практика для мессенджеров без E2E, но это осознанный компромисс приватности, который стоит зафиксировать: альтернатива — слать только `chat_id`/`message_id`, а текст подтягивать клиентом по своему API при получении пуша.
**Рекомендация:** Зафиксировать решение в документации. Если приватность приоритетна — перейти на «пустые» пуши (data-only с идентификаторами), клиент уже умеет ходить за сообщением по `message_id`.

### S4. Тихая деградация при ошибке инициализации Firebase — Low

**Файл:** `Backend/Barkfluff.CloudMessaging/Services/FirebaseService.cs:30-34, 63-66, 88-92`
**Проблема:** Если credentials не заданы или `FirebaseApp.Create` упал, конструктор логирует warning/error и оставляет `_messaging = null`; все последующие отправки молча пропускаются (`LogWarning` + `return`) до перезапуска контейнера. Сервис при этом выглядит здоровым: консьюмеры подключены, очередь разгребается.
**Почему это проблема:** Пуши перестают доставляться для всех пользователей, но ни один механизм (health check, метрика, alert) этого не сигнализирует — сообщения из очереди успешно «обрабатываются». Ошибку конфигурации можно не замечать днями.
**Рекомендация:** Либо падать на старте при отсутствии обязательной конфигурации Firebase (fail-fast, как сделано для `UsersService:Host` в `Program.cs:27`), либо завести метрику/health check «firebase_initialized» и алерт на неё.

### S5. Открытый Kestrel-порт без единого endpoint'а — Low

**Файл:** `Backend/Barkfluff.CloudMessaging/Program.cs:19`
**Проблема:** Worker вызывает `SetRunningAddress`, который поднимает Kestrel-листенер HTTP/2 на порту из `RunSettings:Port`, но сервис не маппит ни одного gRPC-сервиса или HTTP-endpoint'а — порт отвечает только 404.
**Почему это проблема:** Лишняя поверхность внутри docker-сети и обязательная (но бессмысленная) конфигурация `RunSettings:Port`, без которой сервис не стартует. Для чистого консьюмера очередей слушатель не нужен.
**Рекомендация:** Убрать `SetRunningAddress` (перейти на generic host) либо использовать порт осмысленно — повесить на него health check endpoint для Docker/оркестратора.

### S6. Admin-broadcast из RabbitMQ принимается как привилегированная команда без проверки источника — Medium

**Файлы:** общие RabbitMQ credentials и endpoint — `Backend/Barkfluff.CloudMessaging/Program.cs:50-70`; consumer — `Consumers/AdminBroadcastConsumer.cs:30-81`; штатный publisher с admin-проверкой — `Backend/Barkfluff.AdminPanel/Endpoints/NotificationsEndpoints.cs:18-45`.
**Проблема:** Штатный HTTP-путь публикации защищён сессией AdminPanel и подтверждением, но `AdminBroadcastConsumer` доверяет любому `AdminBroadcastNotificationEvent`, попавшему в exchange. При пустом `TargetDeviceIds` он запрашивает FCM-токены всех устройств и рассылает переданные `Title`, `Body` и `ImageUrl`. Producer identity, подпись события и отдельный ACL для этого привилегированного типа не проверяются; сервис подключается общими RabbitMQ credentials.
**Почему это проблема:** Компрометация учётных данных RabbitMQ или любого сервиса, способного публиковать в общий exchange, позволяет обойти AdminPanel и отправить всем пользователям фишинговое/вредоносное push-уведомление. Это отдельный привилегированный broadcast-канал; аналогичный общий риск очереди для email описан в `BarkFluff.Notification` S3, но данный consumer и массовый push там не покрыты.
**Рекомендация:** Выделить для admin-broadcast отдельный exchange/vhost и RabbitMQ user/ACL, разрешив publish только AdminPanel, а consume — только CloudMessaging. Дополнительно проверять producer identity или подпись события; ограничить длины полей и допустимую схему `ImageUrl`.

## Производительность

### P1. Батчи новых сообщений и dismiss не чанкуются по лимиту FCM 500 токенов — Medium

**Файл:** `Backend/Barkfluff.CloudMessaging/Services/FirebaseService.cs:99-126` (`SendNotificationBatchAsync`) и `:192-208` (`SendDismissBatchAsync`)
**Проблема:** `MulticastMessage` принимает не более 500 токенов — это зафиксировано в собственном комментарии метода (строка 70: «до 500 токенов») и реализовано чанкованием в `SendAdminBroadcastBatchAsync` (строка 283: `fcmTokens.Chunk(500)`). Но в `SendNotificationBatchAsync` и `SendDismissBatchAsync` весь список токенов кладётся в одно сообщение без чанкования.
**Почему это проблема:** Для группового чата, у участников которого суммарно больше 500 устройств с FCM-токенами, SDK выбросит `ArgumentException` ещё до обращения к FCM. Исключение поймается общим `catch` (строка 168) — push не получит **ни один** из получателей, и сообщение из очереди будет считаться обработанным (консьюмер не ретраит сознательно). Тихая потеря уведомлений, проявляющаяся только на больших чатах.
**Рекомендация:** Вынести чанкование `Chunk(500)` из `SendAdminBroadcastBatchAsync` в общий приватный метод и использовать его во всех трёх местах отправки.

### P2. Запрос FCM-токенов выполняется последовательно после данных отправителя/чата — Low

**Файл:** `Backend/Barkfluff.CloudMessaging/Consumers/PushNotificationConsumer.cs:52-83`
**Проблема:** Вызовы `GetByIdAsync` (Users) и `GetChatInfoAsync` (Messages) корректно распараллелены через `Task.WhenAll`, но `GetDevicesWithFirebaseTokensAsync` запускается только после их завершения, хотя не зависит от их результатов (использует лишь `message.RecipientUserIds`).
**Почему это проблема:** Латентность обработки каждого события = max(users, messages) + tokens вместо max(users, messages, tokens). На потоке сообщений нагруженного мессенджера это лишние десятки миллисекунд на каждое событие очереди и снижение пропускной способности консьюмера.
**Рекомендация:** Запускать все три вызова одновременно и ждать общий `Task.WhenAll`.

### P3. gRPC-вызовы без deadline и (частично) без CancellationToken — Low

**Файл:** `Backend/Barkfluff.CloudMessaging/Consumers/PushNotificationConsumer.cs:52-58`
**Проблема:** `GetByIdAsync` и `GetChatInfoAsync` вызываются без `deadline` и без `cancellationToken` (в отличие от вызова токенов на строке 83, где token передан). Deadline не задан ни у одного вызова в сервисе.
**Почему это проблема:** При зависании/недоступности Users или Messages консьюмер блокируется на неограниченное время (до TCP-таймаутов), занимая слот конкурентности MassTransit; очередь push-уведомлений копится. Отмена при остановке сервиса для этих двух вызовов тоже не работает.
**Рекомендация:** Передавать `context.CancellationToken` во все вызовы и задать разумный `deadline` (например, 5-10 секунд) через `CallOptions` или конфигурацию gRPC-клиента.

## Docker / nginx

### D1. Stale-маунт Firebase service-account JSON в master-compose, который код не читает — Medium

**Файл:** `Backend/docker-compose-master.yml:134-135`
**Проблема:** В прод-конфигурации в контейнер монтируется `./barkfluff-firebase-adminsdk.json:/app/firebase/barkfluff-firebase-adminsdk.json:ro`, но `FirebaseService` читает credentials исключительно из конфигурационных ключей `Firebase:ProjectId/PrivateKey/ClientEmail/...` (`FirebaseService.cs:24-28`) и собирает JSON сам; ни код, ни `GOOGLE_APPLICATION_CREDENTIALS` этот файл не используют. При этом, в отличие от dev-compose (`docker-compose-dev.yml:133-137`), env-переменные `Firebase__*` в master-секции не заданы вовсе — рабочая конфигурация целиком зависит от того, что отдаёт Configuration-сервис.
**Почему это проблема:** Полный приватный ключ service-account лежит на хосте рядом с compose-файлом и напрасно пробрасывается в контейнер — расширение поверхности утечки без функциональной пользы. Одновременно расхождение dev/master маскирует реальный источник конфигурации: если в Configuration ключи `Firebase:*` не заведены, пуши в проде молча отключены (см. S4).
**Рекомендация:** Удалить мёртвый volume-маунт из `docker-compose-master.yml` (и сам файл с хоста, если он там остался). Явно задокументировать/проверить, что `Firebase:*` приходит из Configuration-сервиса, либо выровнять master с dev через env-переменные из `.env`.

### D2. Приватный ключ Firebase передаётся через переменные окружения (dev) — Low

**Файл:** `Backend/docker-compose-dev.yml:133-137`
**Проблема:** `Firebase__PrivateKey` и остальные credentials прокидываются в контейнер обычными env-переменными из `.env`.
**Почему это проблема:** Переменные окружения видны через `docker inspect`, в `/proc/<pid>/environ` и потенциально в диагностических дампах; это слабее, чем Docker secrets или файловый секрет с правами 0400. Для dev-окружения приемлемо, но шаблон легко переезжает в прод.
**Рекомендация:** Для прод-развёртываний использовать Docker secrets / файл, монтируемый с ограниченными правами, и читать ключ из файла; в dev можно оставить как есть.

### D3. Nginx-конфиг отсутствует — ожидаемо, не является проблемой

**Файл:** `Backend/nginx/` (конфига для cloud-messaging нет)
CloudMessaging — чистый background worker: в обоих compose-файлах у сервиса нет секции `ports`, наружу он не публикуется, входящего трафика не имеет. Отсутствие nginx-конфига корректно. Dockerfile (`Backend/Barkfluff.CloudMessaging/Dockerfile`) собран по лучшим практикам: chiseled-образ, непривилегированный пользователь (`USER $APP_UID`, строки 21-22), кэш NuGet через BuildKit; `.dockerignore` исключает `.env` и секреты — в образ credentials не попадают.
