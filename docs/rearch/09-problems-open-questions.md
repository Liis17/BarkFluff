# 09 — Проблемы, риски и открытые вопросы

Реестр всего, что может выстрелить. Статусы: **решено** (решение зафиксировано в доках), **смягчено** (риск принят с контрмерами), **открыто** (требует решения до/во время реализации соответствующей фазы).

Дополнено 2026-07-17 по итогам ревью [11-plan-review.md](11-plan-review.md): обновлены №7, №8, №11, №22; добавлены №35–44.

## Идентичность и адресация

| # | Проблема | Статус | Решение / что делать |
|---|----------|--------|----------------------|
| 1 | Коллизии `long UserId` между нодами | решено | UUID-слой; long не покидает ноду ([01](01-addressing-identity.md)) |
| 2 | Коллизии `Message.Id` (bigserial) | решено | `FederatedId` (uuid) для fed-сообщений ([05](05-chat-replication.md)) |
| 3 | Смена username ломает FID | смягчено | UUID — стабильный якорь; события профиля + TTL-рефреш кеша |
| 4 | Вредоносная нода заявляет чужой UUID | смягчено | UUID пиннится к ServerName при знакомстве; смена — отказ. Миграция аккаунта между нодами — **вне скоупа**, отдельная будущая проработка |
| 5 | Спуфинг авторства | решено | Нода говорит только за свой домен; проверка `sender.server == origin` подписи |

## Доверие и криптография

| # | Проблема | Статус | Решение / что делать |
|---|----------|--------|----------------------|
| 6 | CA может отозвать серт ноды | решено | Self-signed допустим; подлинность — Ed25519-подписи, транспорт — SPKI-пиннинг ([02](02-trust-and-certs.md)) |
| 7 | MITM при первом контакте | решено | Bootstrap-фетч well-known — только по CA-валидному HTTPS (CA нужен лишь для знакомства, S2S от него не зависит; нода без CA-серта знакомится через ручных пиров); кросс-сверка well-known ↔ Navigator обязательна ([02](02-trust-and-certs.md)) |
| 8 | Компрометация signing-ключа | принят остаточный риск | Push `KeyRevoked` всем KnownServers (не ждать суточного рефреша). Окно timestamp защищает только от replay — не от свежих подписей украденным ключом. При компрометации единственного ключа восстановление доверия только внеполосно; офлайновый master-ключ — усиление вне MVP ([02](02-trust-and-certs.md)) |
| 9 | Clock skew между нодами | смягчено | NTP-требование; `Ping` с временем; код ошибки ClockSkew; tie-break в LWW |
| 10 | Ed25519 в .NET 10: доступность API | решено | BCL не содержит плоского Ed25519; выбран `BouncyCastle.Cryptography` 2.6.2 (managed) — [step-0.5-report.md](phase-0/step-0.5-report.md) |
| 11 | Replay-атаки | смягчено | timestamp-окно + идемпотентность мутаций по event_id; nonce-кеш исключён из дизайна как избыточный |
| 35 | SSRF через servername/endpoint (Federation стоит внутри backend-сети) | решено | Обязательная валидация: публичный hostname, запрет приватных диапазонов после резолва, анти-rebinding, только https/grpc; исключение — manual-пиры ([03](03-discovery.md)) |
| 36 | Подпись `sha256(request-bytes)`: protobuf-сериализация не канонична | решено | Хешируются полученные wire-байты без пере-сериализации (кастомный marshaller); конверт SignedRequest отвергнут; стримы — подпись заголовков + первого сообщения ([02](02-trust-and-certs.md)) |

## Консистентность данных

| # | Проблема | Статус | Решение / что делать |
|---|----------|--------|----------------------|
| 12 | Расхождение копий чата (edit/delete) | решено | LWW по `LastChangeAt` + терминальность удаления + идемпотентность ([05](05-chat-replication.md)) |
| 13 | Одновременное создание DM с двух сторон → два ChatId | **открыто** (решение намечено) | Детерминированное слияние по меньшему ChatId; протокол слияния — отдельная задача Фазы 2, самый сложный корнер-кейс |
| 14 | Дозаполнение дыр после долгого даунтайма (> окна ретраев) | решено | `FetchChatHistory` catch-up + dead-letter видимость в AdminPanel |
| 15 | Порядок событий | смягчено | Упорядочивание outbox per-(destination, chat); приёмник дозапрашивает неизвестные сообщения при edit-на-несуществующее |
| 16 | `ReadBy` — массив long, не вмещает remote | решено | `FederatedReadStates` отдельной таблицей |
| 17 | Pin-сообщения в fed-чатах | решено | Pin не федерируется (локальное состояние каждой ноды); pin/unpin не трогают `Message.LastChangeAt`, иначе ломают LWW входящих правок ([05](05-chat-replication.md)) |
| 37 | Потеря события на стыке Messages → RabbitMQ → outbox (краш между коммитом БД и publish) | смягчено | Publisher confirms + сверка `(chat_id, last_event_ts)` в Ping закрывает дыру постфактум ([05](05-chat-replication.md)); transactional outbox в БД Messages — правильное закрытие, бэклог |
| 38 | Head-of-line blocking очереди чата при перманентно отвергаемом событии | решено | Классификация ответов DeliverEvents: retryable → backoff, permanent → сразу DeadLetter, очередь чата едет дальше ([04](04-federation-service.md)) |
| 39 | «Тихие дыры»: получатель не знает о пропущенных событиях | решено | Сверка `(chat_id, last_event_ts)` в Ping / при восстановлении связи → FetchChatHistory ([05](05-chat-replication.md)) |
| 40 | Семантика удаления fed-DM не была определена | решено | Локальное действие (как email), не федерируется; новое входящее сообщение воссоздаёт чат-копию ([05](05-chat-replication.md)) |
| 41 | Поздний импорт (catch-up) ломает сортировку по локальному Id | решено | `MessagesStorage`/`ChatsStorage` уже сортируют по `SentAt`; tie-break `ThenBy(Id)` добавляется в 2.3 для стабильности при равных метках (`Id` — node-local: кросс-нодовый порядок при равных `SentAt` не гарантируется, но это вне требования) ([08](08-service-migration.md), step-2.3) |

## Отложенные фичи (следующие задачи по проработке — по решению владельца)

Каждая — отдельный планировочный документ, когда дойдёт очередь:

| Фича | Ключевые проблемы, уже видимые сейчас |
|------|--------------------------------------|
| **Федеративные группы** | Консистентность членства между N нод; права (UsersCanKick) с remote-модераторами; системные сообщения; выбор «домашней» ноды группы vs репликация; наплыв нод-участников в outbox |
| **Федеративные приватные чаты (passphrase E2E)** | Обмен KdfSalt/PassphraseVerifier между нодами; хранение шифротекста на двух нодах (безопасно — сервер и так не видит plaintext); инвайт-флоу через федерацию |
| **Федеративные секретные чаты (Signal/X3DH)** | Кросс-нодовый `FetchPrekeyBundle` (атомарный расход one-time prekey на чужой ноде!); device-scope доставка на устройства remote-пользователя; Redis-буфер 24ч на чьей стороне |
| **Федеративные боты** | Адресация `@bot:server`; Bot API токены не пересекают ноды — вызовы через федерацию от имени ноды бота |
| **Кросс-нодовые звонки** | LiveKit SFU принадлежит ноде — чей SFU используется; выдача LiveKit-токенов пользователям чужой ноды; TURN/ICE через границы |
| **Пользовательская блокировка отправителей** | Нужен и для локальных; для fed — блок по UUID |
| **Миграция аккаунта между нодами** | Перенос UUID с доказательством владения; редиректы FID |
