# 10 — Roadmap: фазы, задачи, критерии готовности

Порядок выстроен по матрице зависимостей из [08-service-migration.md](08-service-migration.md). Каждая задача — с проверкой (критерием готовности), чтобы фазы можно было вести автономно. Внутри фазы — коммит после каждого пункта (правило проекта).

---

## Фаза 0 — Фундамент идентичности (без федерации)

Можно катить в прод независимо: ничего федеративного ещё не происходит.

> Детальные планы реализации каждого этапа — [phase-0/README.md](phase-0/README.md).

| # | Задача | Проверка |
|---|--------|----------|
| 0.1 | `ServiceId.Federation`, ключи конфигурации, `Federation:ServerName` в Configuration | Конфигурация читается; существующие сервисы не задеты (билд + текущие тесты зелёные) |
| 0.2 | Users: колонка `Uuid` + backfill + отдача в proto | Миграция на копии прод-БД; у всех пользователей уникальный uuid; `GetUser` возвращает uuid; старые клиенты работают |
| 0.3 | Messages: `LastChangeAt` + backfill, `FederatedId`/`SenderUuid`/`ChatMembers.UserUuid` (nullable, пока не используются) | Миграции применяются; все существующие сценарии (unit + ручной прогон) без регрессий |
| 0.4 | Proto: federation_api / federation_internal_api / расширения shared, users, messages, onliner, navigator, beacon | Сборка всех сервисов и клиентских proto-генераций проходит |
| 0.5 | Исследование: Ed25519 в .NET 10 (API, производительность, выбор библиотеки) | Мини-прототип: генерация, подпись, проверка + решение задокументировано в [02](02-trust-and-certs.md) |

## Фаза 1 — Federation-сервис: каркас, доверие, discovery

> Детальные планы реализации каждого этапа — [phase-1/README.md](phase-1/README.md).

| # | Задача | Проверка |
|---|--------|----------|
| 1.1 | Каркас `BarkFluff.Federation` (порт 7030, шаблон платформы, Dockerfile.slim, CI workflow, docker-compose-dev) | Сервис стартует в dev-стеке, метрики видны в Seq |
| 1.2 | Генерация/хранение signing-ключей, `GetServerKeys`, генерация подписанного `/.well-known/barkfluff` | Документ отдаётся, подпись верифицируется сторонним скриптом |
| 1.3 | XFed: подпись исходящих (interceptor) + проверка входящих + SPKI-пиннинг | Интеграционный тест: две локальные ноды (два compose-стека) — `Ping` проходит; подделанная подпись/чужой destination/старый timestamp — отклоняются |
| 1.4 | KnownServers + discovery-цепочка (well-known → Navigator → manual) + фоновой рефреш | Тест: резолв ноды по каждому из трёх источников; блоклист отклоняет запросы |
| 1.5 | Navigator: PostgreSQL-персистентность, federation-поля, валидация регистрации, `GetServerByName` | Рестарт Navigator не теряет реестр; регистрация без валидного well-known отклоняется; старый `ListServers` совместим |
| 1.6 | Nginx: `federation.{domain}`, `/.well-known`, rate-limit зоны; референсный конфиг ноды | Двух-нодовый dev-стенд общается через nginx с self-signed сертами |
| 1.7 | AdminPanel: страница «Федерация» — пиры (список/добавить/блок), свои ключи | Ручной пир добавляется и резолвится; блок работает |

**Гейт фазы:** двух-нодовый стенд, ноды видят друг друга всеми тремя способами discovery, весь S2S подписан и проверяется.

## Фаза 2 — Федеративные DM

> Детальные планы реализации каждого этапа — [phase-2/README.md](phase-2/README.md).

| # | Задача | Проверка |
|---|--------|----------|
| 2.1 | Users: `RemoteUsers`, `ResolveFederatedUser`, S2S `GetUserProfile` с privacy | Резолв `@user:node2` с ноды 1 возвращает профиль; privacy-скрытые поля не утекают |
| 2.2 | Outbox (таблица, диспетчер, backoff, упорядочивание, dead-letter, janitor) + `ProcessedEvents` | Тест: остановить ноду 2 → отправить N сообщений → поднять → все дошли один раз, порядок в чате сохранён |
| 2.3 | Messages: импорт-RPC (`ImportFederatedChat/Message`) + `SendMessage` с uuid-peer + расширенные события | Сообщение с ноды 1 появляется у пользователя ноды 2 в realtime (существующий стрим Updates) |
| 2.4 | Edit/Delete/Read через федерацию + LWW | Правка/удаление/прочтение отражаются на обеих нодах; событие со старой меткой игнорируется (тест с подменой метки) |
| 2.5 | Privacy `AllowFederatedDm` (Users) + отказ `FederatedDmRejected` (Messages) | При включённом запрете новый fed-чат отклоняется, отправитель получает понятную ошибку |
| 2.6 | Catch-up: `ExportChatEvents`/`FetchChatHistory` + триггер при dead-letter/дыре | Нода, пролежавшая дольше окна ретраев, дотягивает историю |
| 2.7 | Слияние одновременно созданных DM (протокол по меньшему ChatId) | Тест гонки: оба пишут первыми одновременно → в итоге один чат на обеих нодах |
| 2.8 | Пуши: имя отправителя из RemoteUsers в CloudMessaging-пути | Push на ноде получателя показывает FID/имя remote-отправителя |
| 2.9 | Профильные события через федерацию (`UserProfileChanged`/`UserDeactivated`) + расширенная регистрация Beacon в Navigator (federation-поля) | Смена имени на ноде 1 обновляет RemoteUsers ноды 2; `GetServerByName` возвращает federation-поля ноды |

**Гейт фазы:** полноценная переписка 1-на-1 между нодами: доставка, ретраи, правки, прочтения, приватность, догон истории.

## Фаза 3 — Файлы

> Детальные планы реализации каждого этапа — [phase-3/README.md](phase-3/README.md).

| # | Задача | Проверка |

## Фаза 4 — Presence и typing

> Детальные планы реализации каждого этапа — [phase-4/README.md](phase-4/README.md).

| # | Задача | Проверка |
|---|--------|----------|
| 4.1 | Messages: федеративный контекст в `CheckChatMembership` (uuid-ветка, признак federated, ноды-участники) + `CheckFederatedPresenceAccess` | Ответ содержит данные для маршрутизации typing; нода без общего чата не получает доступ к presence |
| 4.2 | Onliner: uuid-ветка статусов (Redis, TTL), `OnlinerServerApi` (`UpsertRemoteStatus`/`InjectRemoteTyping`/`GetLocalPresence`), исключение из персиста, интерес-heartbeat | Статус remote-пользователя виден локальному подписчику; remote-статусы не попадают в БД и не гаснут offline-детектором |
| 4.3 | Federation: агрегированный `SubscribePresence` (по стриму на пару нод), reconnect, coalescing, лимиты | Обрыв стрима → статусы гаснут → реконнект восстанавливает; privacy origin-стороны соблюдён |
| 4.4 | Typing: `DeliverTypingOutbound` → `DeliverTyping` → `InjectRemoteTyping` + rate limit | «Печатает…» видно через ноду; спам-частота режется |

## Фаза 5 — Клиенты (этап = клиент)

> Детальные планы реализации каждого этапа — [phase-5/README.md](phase-5/README.md).
>
> Клиенты фазы (решение владельца при планировании): **Web, Android V1, macOS, iOS**. Разбиение изменено относительно исходной редакции роадмапа: функциональное деление «резолв / UI» внутри одного клиента неразделимо, поэтому этап = клиент, а проверка старых клиентов вынесена в 5.6.

| # | Задача | Проверка |
|---|--------|----------|
| 5.1 | Клиентский контракт федерации (гайд для клиентских исполнителей): RPC, поля, FID/punycode, ошибки, placeholder'ы | Гайд в vault сверен с фактическим proto и классами исключений |
| 5.2 | Android V1: резолв FID, отправка по uuid, remote-карточка, presence/typing, placeholder, тумблер приватности | E2E «нашёл → написал → получил ответ» на стенде |
| 5.3 | Web: то же + маршрут Beacon в YARP и перегенерация proto-бандла | E2E на стенде; при выключенной федерации поведение не изменилось |
| 5.4 | macOS + общие Swift-пакеты (BFProto/BFNetworking/BFCore) | E2E на стенде; пакеты готовы для iOS |
| 5.5 | iOS: экраны поверх пакетов из 5.4 | E2E на стенде; паритет с macOS |
| 5.6 | Регрессия старых клиентов (WPF, Linux Qt, предыдущие сборки) против fed-ноды | Обычные чаты работают, fed-чаты деградируют читаемо, приложение не падает |
