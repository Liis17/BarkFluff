# 06 — Файлы и вложения в федерации

## Принятое решение

**Файлы не реплицируются.** Файл живёт только на origin-сервере (нода, куда его загрузили). Вторая сторона всегда тянет данные с оригинального сервера. Без кеша содержимого на принимающей ноде (решение владельца проекта; кеш превью — отдельный открытый вопрос ниже).

## Ссылка на файл в федеративном событии

Сейчас вложение — это `FileId` (Guid) + метаданные из Files-сервиса своей ноды. Через границу сервера уходит **федеративная ссылка**:

```protobuf
message FederatedFileRef {
  string origin_server = 1;  // нода, где лежит файл
  string file_id = 2;        // Guid в Files origin-ноды
  string filename = 3;       // снапшот метаданных — чтобы рисовать UI
  int64  size_bytes = 4;     //   без похода на origin
  int32  attachment_type = 5;
  string preview_file_id = 6;
  int32  image_width = 7;
  int32  image_height = 8;
}
```

Метаданные (имя/размер/тип/размеры) снапшотятся в `MessageAttachments` принимающей ноды при импорте сообщения — список чатов и пузыри сообщений рендерятся без сетевых походов. Тянутся с origin только **байты** файла и превью.

## Скачивание remote-файла

У клиента ноды B нет и не должно быть способа авторизоваться на ноде A. Скачивание — через свою ноду:

```
Клиент B: GET https://{nodeB}/download/fed/{origin_server}/{file_id}   (существующий REST Files + новый маршрут)
  → Files(B): проверяет право (файл фигурирует во вложении чата, где пользователь — участник)
  → FederationInternalApi.FetchRemoteFile(origin_server, file_ref)
  → Federation(B) → S2S FetchFile → Federation(A)
      → проверка подписи + проверка привязки: file_id действительно вложение
        федеративного чата, в котором участвует нода B
      → Files(A) → S3 → stream chunks обратно
  → стрим прокидывается клиенту B (без буферизации на диск, chunked)
```

- Превью — тот же путь с `preview_file_id` (маленькие, быстрые).
- Принимающая нода сверяет фактический объём стрима со снапшотом `size_bytes` и **обрывает стрим при превышении** — защита от ресурсного злоупотребления со стороны origin.
- Загрузка (upload) не меняется вообще: автор всегда загружает на **свою** ноду через существующий `GetUploadUrl` + `POST /upload/{uploadId}`; в федеративное событие уходит готовый `FederatedFileRef`.

## Права доступа на стороне origin

Origin-нода не знает пользователей ноды B по отдельности — авторизация **на уровне ноды**: подписанный S2S-запрос от ноды B + проверка «file_id принадлежит вложению чата, одним из участников которого является пользователь ноды B». Требуется обратный индекс `FileId → ChatId` — он есть через `MessageAttachments`; Files(A) спрашивает Messages(A) (`CheckFileFederationAccess(file_id, requesting_server)` — новый server-RPC) либо Federation(A) валидирует сам через Messages. Дальнейшая раздача файла конкретным пользователям — ответственность ноды B (её обычные проверки членства).

## Аватары remote-пользователей

Аватар — тоже файл origin-ноды. `RemoteUsers.AvatarUrl` хранит федеративную ссылку; клиентам отдаётся проксируемый URL своей ноды (`/download/fed/...`). Профильные аватары публичны с учётом privacy (`AvatarVisibility`) — origin проверяет privacy при `FetchFile` для типа UserAvatar (доступ по privacy, а не по членству в чате).

## Проблемы и компромиссы решения «всегда с origin»

| Проблема | Последствие | Смягчение |
|----------|-------------|-----------|
| Origin-нода лежит | Картинки/файлы в истории не открываются (текст истории — жив, он реплицирован) | Снапшот метаданных даёт честный placeholder «файл недоступен, сервер offline»; повторить позже |
| Латентность: клиент → B → A → S3 | Медленнее локальных файлов, двойной трафик через B | Стриминг без буферизации; HTTP Range-запросы поддержать в FetchFile (перемотка видео) |
| Нагрузка на origin | Популярный файл выкачивается многократно каждой нодой | Зафиксировано решение «без кеша». **Открытый вопрос:** разрешить ли кеш превью (маленькие, дают 90% UX) — вынесен в [09-problems-open-questions.md](09-problems-open-questions.md) |
| Дедупликация по SHA256 | Работает только внутри ноды — норм, кросс-нодовая дедупликация не нужна | — |
| Удаление файла на origin | Копий нет ⇒ файл исчезает у всех — это соответствует духу решения (данные под контролем origin) | UI-обработка 404 |
| Квоты | Чужие файлы не занимают место на нашей ноде — плюс модели. Но `FetchRemoteFile`-трафик — расход канала | Rate limit per-server; метрики `remote_file_fetches`, `remote_file_bytes_out` |
| Злоупотребление FetchFile | Перебор file_id чужой нодой | Guid недостаточно — обязательна проверка привязки к общему чату (выше) + rate limit |

## Изменения по сервисам (сводка)

- **Files**: маршрут `GET /download/fed/{server}/{fileId}`; server-RPC отдачи стрима для Federation; проверка прав через Messages; privacy-проверка для аватаров.
- **Messages**: снапшот `FederatedFileRef` в `MessageAttachments` (новые колонки `OriginServer`, снапшот-поля уже частично есть — filename/size приходят из Files при рендере, для remote станут хранимыми); `CheckFileFederationAccess`.
- **Federation**: `FetchFile` (S2S, сервер и клиент), `FetchRemoteFile` (internal), стриминг chunk'ов, Range.
- **Клиенты**: не отличают remote-файлы от локальных — URL всегда указывает на свою ноду. Изменений почти нет (плюс placeholder «origin недоступен»).
