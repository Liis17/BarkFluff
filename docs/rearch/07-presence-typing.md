# 07 — Федерация онлайн-статусов и typing (Onliner)

Входит в MVP (решение владельца проекта). Оба механизма эфемерны — потеря события некритична, персистентность и ретраи не нужны. Это принципиально другой транспортный профиль, чем у сообщений: **не через outbox**, а через живые S2S-стримы/fire-and-forget вызовы.

## Онлайн-статусы (presence)

### Текущая механика (внутри ноды)

Клиент шлёт heartbeat `SetOnlineStatus`; Onliner держит статусы in-memory; подписчики получают изменения через server-stream `SubscribeToOnlineStatus`; >5 сек без heartbeat → Offline.

### Федеративная схема — один агрегированный стрим на пару нод

Наивный вариант «каждая подписка пользователя = отдельный S2S-стрим» не масштабируется. Вместо этого:

```
Нода B (наши пользователи смотрят на remote-юзеров ноды A):
  Federation(B) держит ОДИН S2S-стрим к ноде A:
    SubscribePresence(user_uuids: [все uuid ноды A, на которые сейчас
                                   подписан хоть один наш пользователь])
  ↑ список обновляется (re-subscribe или control-сообщение) при
    появлении/уходе локальных подписчиков.

Нода A:
  - отдаёт текущие статусы запрошенных uuid + шлёт изменения в стрим;
  - применяет privacy (OnlineVisibility) СВОЕЙ стороной: None/Friends → в стрим
    уходит «скрыт» (как для чужого локального пользователя). Friends === None
    до появления сервиса отношений — существующее правило сохраняется.

Нода B:
  Federation(B) полученные статусы транслирует в Onliner(B) через новый
  server-RPC UpsertRemoteStatus(uuid, status, last_seen)
  → Onliner(B) хранит их в том же in-memory кеше (ключ — uuid-ветка)
  → локальные подписчики получают события существующим механизмом.
```

Детали:

- **Ключи в Onliner**: сейчас всё ключуется `long userId`. Для remote — параллельная ветка `ConcurrentDictionary<Guid uuid, ...>` + подписки клиентов расширяются `oneof` (long для локальных, uuid для remote). В БД remote-статусы **не** персистятся (DatabasePersistenceService их пропускает) — источник истины на чужой ноде.
- **Разрыв S2S-стрима**: все remote-статусы этой ноды → `Unknown/Offline` локально; реконнект с backoff. Стрим также несёт keepalive-ping.
- **Privacy проверяется origin-нодой** (владельцем данных). Нода B дополнительно не фильтрует — ей уже отдали только разрешённое. Меняется privacy у пользователя A → нода A шлёт «скрыт» в активные стримы.
- **Экономия**: нода A может coalesce'ить изменения (не чаще раза в N секунд на пользователя).

## Typing-индикаторы

### Текущая механика

Чистый ретранслятор: `SetTypingStatus(chatId)` каждые 4–5 сек → `TypingEvent` подписчикам чата, кроме автора; членство проверяется через Messages; гаснет по клиентскому таймауту ~6 сек.

### Федеративная схема — fire-and-forget

```
A@nodeA печатает в федеративном DM:
  Onliner(A): проверка членства (как сейчас) → локальным подписчикам как сейчас
    + если чат федеративный: публикация во внутренний канал → Federation(A)
  Federation(A) → S2S DeliverTyping(chat_id, sender_uuid, action) → Federation(B)
    (unary, без ретраев: потерянный typing не страшен; допустим короткий
     coalescing — не слать чаще раза в 2–3 сек на (chat, sender))
  Federation(B): подпись/блоклист → Onliner(B).InjectRemoteTyping(...)
  Onliner(B): ретранслирует TypingEvent локальным подписчикам чата
```

- **Как Onliner(A) узнаёт, что чат федеративный и куда слать**: membership-ответ Messages расширяется признаком федеративности и списком нод-участников (для DM — одна). Альтернатива (хуже): Federation сам резолвит чат на каждый heartbeat.
- **Валидация на приёме**: нода B проверяет, что `sender_uuid` принадлежит origin-ноде и является участником чата (через Messages B — там есть копия членства).
- `TypingEvent` в proto получает `oneof` автора: `user_id` (локальный) / `user_uuid` (remote) — клиентам нужно уметь отобразить «@alice:nodeA печатает…».

## Объём изменений (сводка)

| Сервис | Изменения |
|--------|-----------|
| Onliner | uuid-ветка кеша статусов; server-RPC `UpsertRemoteStatus`, `InjectRemoteTyping` (TokenType.Service); признак федеративности в исходящем typing-потоке; proto: `oneof` идентификатора в статусах и TypingEvent |
| Federation | S2S `SubscribePresence` (сервер и клиент-стороны), `DeliverTyping`; менеджер агрегированных стримов по нодам; coalescing |
| Messages | `CheckChatMembership`-ответ + признак federated + ноды-участники |
| Клиенты | Подписка на статусы remote-собеседников по uuid; отображение typing от FID |

## Риски

- **Трафик presence** — самый болтливый канал федерации. Обязателен coalescing и подписка только на реально наблюдаемых пользователей (открытые чаты/профили), не на всех «знакомых».
- **Асимметрия ожиданий**: нода-партнёр может не поддерживать presence (старая версия протокола) — capability-флаг в `Ping`; UI показывает «статус недоступен».
- Rate limit на `DeliverTyping` per-origin (спам-вектор дешёвых запросов).
