# 02 — Модель доверия, сертификаты и подпись S2S-трафика

## Требования (из постановки задачи)

1. Бэкенды нод общаются между собой **зашифрованно**.
2. **Зависимость от центров сертификации недопустима**: CA может отозвать сертификат конкретной ноды и выключить её из сети. Админ каждой ноды должен иметь возможность сделать свой сертификат сам (self-signed).

## Два независимых слоя

### Слой 1 — транспортное шифрование: TLS (допускается self-signed)

- Весь S2S-трафик — gRPC поверх TLS (HTTP/2). Терминация — на nginx ноды (как сейчас для клиентского трафика).
- Сертификат может быть любым: Let's Encrypt, покупной, **self-signed**. Проверка цепочки CA у S2S-клиента **отключена** (custom `RemoteCertificateValidationCallback`).
- Чтобы self-signed не превращался в «шифруем неизвестно с кем» (MITM), применяется **SPKI-пиннинг**: отпечаток публичного ключа TLS-сертификата ноды публикуется в discovery-документе (`/.well-known/barkfluff`, Navigator, ручная запись админа) и фиксируется в KnownServers. S2S-клиент сверяет отпечаток предъявленного сертификата с закреплённым.
  - Смена TLS-сертификата (плановая ротация) — через обновление discovery-документа: подпись документа signing-ключом (слой 2) делает обновление доверенным.
  - Первый контакт с нодой, у которой нет записи в KnownServers — TOFU (trust on first use) через discovery по DNS: отпечаток берётся из `/.well-known`, который был получен по обычному HTTPS. Риск первого контакта фиксируем как осознанный компромисс.

### Слой 2 — подлинность: Ed25519 signing key ноды

Транспортный TLS (тем более self-signed) не доказывает, что запрос пришёл именно от `chat.example.org`. Подлинность обеспечивается прикладными подписями — по образцу Matrix.

- При первичной настройке ноды генерируется пара Ed25519 (**signing key**). Приватный ключ хранится у Federation-сервиса (см. вопрос хранения ниже), публичный — публикуется через все каналы discovery.
- Ключи версионируются: `key_id` (например `ed25519:1`). Нода может иметь несколько активных ключей (для ротации) и список отозванных с `expired_at`.

### Подпись каждого S2S-запроса

Каждый federation-RPC несёт metadata-заголовок (по аналогии с существующим XAuth):

```
x-bf-origin:      chat.example.org          # имя ноды-отправителя
x-bf-destination: barkfluff.com             # имя ноды-получателя (защита от relay)
x-bf-timestamp:   1789000000000             # unix ms UTC
x-bf-key-id:      ed25519:1
x-bf-signature:   base64(Ed25519-подпись канонической строки)
```

Каноническая строка подписи:

```
{origin}\n{destination}\n{timestamp}\n{grpc-method-full-name}\n{sha256(request-bytes)}
```

Получатель (Federation-сервис ноды-адресата):

1. Проверяет `destination == моё имя` (иначе запрос переслан/зеркалирован — отказ).
2. Проверяет `|now - timestamp| <= окно` (рекомендация: 5 минут) — анти-replay. Для строгих операций дополнительно nonce-кеш в Redis на размер окна.
3. Достаёт публичный ключ `origin` + `key_id` из KnownServers (при отсутствии — discovery на лету).
4. Проверяет подпись. Ошибка → `Unauthenticated`, инкремент метрики, запись в лог.
5. Проверяет, что `origin` не в блоклисте ноды.

Внутри тела события все ссылки на «кто автор» дополнительно валидируются правилом: **нода может говорить только за пользователей своего домена** (`sender.server_name == x-bf-origin`).

### Почему не mTLS

mTLS + пиннинг клиентских сертификатов решал бы обе задачи разом, но:
- усложняет прохождение через nginx/промежуточные прокси (нужен passthrough или проброс клиентского серта);
- привязывает подлинность к TLS-слою — при смене серта рвётся доверие;
- подписи уровня приложения дают доказуемое авторство конкретного события (важно для копий чатов: копия хранит подпись origin-события и может быть перепроверена позже).

Ed25519-подписи + пиннинг TLS-ключа покрывают требования и не зависят от CA. mTLS можно добавить позже как опциональное усиление между дружественными нодами.

## Хранение приватного ключа

Варианты:
1. **Configuration-сервис** (как остальные секреты — `Federation:SigningKeyPrivate`). Просто, вписывается в текущую схему, но секрет лежит в общей конфиг-БД.
2. Файл на диске Federation-контейнера (volume) + путь в конфигурации.
3. Секрет-менеджер — вне текущего стека, избыточно.

**Рекомендация:** вариант 1 для MVP (согласуется с тем, как хранятся `JwtSettings:SecretKey` и service-токены), с зафиксированной задачей на будущее — вынос в отдельное хранилище. Генерация ключа — CLI/эндпоинт первичной инициализации Federation при первом старте (если ключа нет в конфиге — сгенерировать и записать).

## Ротация и компрометация ключей

- **Плановая ротация**: добавить новый `key_id`, публиковать оба, подписывать новым; старый пометить `expired_at` спустя перекрытие (например 30 дней). Ноды-партнёры обновляют ключи при периодическом рефреше discovery (рекомендация: раз в сутки + по требованию при неизвестном `key_id`).
- **Компрометация**: админ генерирует новый ключ, помечает старый отозванным в discovery-документе. Проблема: событие, подписанное украденным ключом в окне до ротации, неотличимо от легитимного. Смягчение — короткое допустимое окно `timestamp` и логирование всех входящих.
- Discovery-документ сам подписывается signing-ключом → цепочка обновлений доверенная после первого знакомства.

## Проблемы и открытые вопросы

- **Часы**: окно `timestamp` требует NTP-синхронизации нод. Рассинхрон > окна = отказ в обслуживании ноде с кривыми часами. Диагностика: специальный код ошибки `ClockSkewDetected` с серверным временем в ответе.
- **Первый контакт (TOFU)**: MITM на пути к `/.well-known` при самом первом знакомстве может подсунуть чужой ключ. Смягчения: кросс-проверка через Navigator (второй независимый канал), ручное добавление пира админом (третий канал), логирование смены ключей.
- **Отзыв доверия ноде** — только локальное решение каждого админа (блоклист) + возможная модерация каталога Navigator. Глобального отзыва нет by design.
- Выбор криптобиблиотеки: .NET 10 — `System.Security.Cryptography` (Ed25519 доступен в .NET 8+ через `Ed25519`? — **проверить**; fallback: NSec/libsodium или BouncyCastle). Зафиксировано как задача исследования в [10-roadmap.md](10-roadmap.md).
