# Этап 5.1 — Клиентский контракт федерации (гайд для клиентских исполнителей)

## Цель

Один документ, из которого исполнитель любого клиента (Android, Web, macOS, iOS и будущие WPF/Qt) узнаёт **всё**, что нужно для поддержки федерации: какие RPC звать, какие поля читать, как рисовать FID, как обрабатывать ошибки и недоступный origin. Клиентские этапы 5.2–5.5 ссылаются на него и не переписывают правила у себя. Кода клиентов этот этап не трогает — только документы.

## Контекст

- Клиентские требования разбросаны по родительским докам: [../08-service-migration.md](../08-service-migration.md) (раздел «Клиенты»), [../01-addressing-identity.md](../01-addressing-identity.md) (FID, punycode), [../05-chat-replication.md](../05-chat-replication.md) (ограничения MVP), [../06-files.md](../06-files.md) («Контракт недоступности для клиентов», дописан этапом 3.5), [../07-presence-typing.md](../07-presence-typing.md) (typing от FID), [../11-plan-review.md](../11-plan-review.md) И-4/И-7 (homograph, экранирование `filename`).
- Образцы формата в vault: `Obsidian/ClaudeVault/Backend/Messages-PinnedMessages-ClientGuide.md`, `Backend/Users-ChatFolders-ClientGuide.md` — тот же жанр «гайд для клиентских агентов»: RPC → когда звать → что делать с ответом → таблица ошибок.
- Все контракты уже существуют в `Shared/BarkFluff.Proto/` (0.4 + добавления Фаз 2–4) — гайд их **описывает**, а не вводит.

**Перед написанием гайда обязательно свериться с фактическим состоянием proto** (`Shared/BarkFluff.Proto/users_api.proto`, `messages_api.proto`, `onliner_api.proto`, `beacon_api.proto`, `shared.proto`, `files_api.proto`): номера полей, точные имена RPC и `error_code`-строки. Гайд, расходящийся с proto, хуже отсутствующего.

## Изменение 1 — новый документ `Obsidian/ClaudeVault/Клиенты/Federation-ClientGuide.md`

Структура (разделы обязательны, содержание — по фактическому коду/proto):

### 1. Модель для клиента

- Три идентификатора: `long user_id` (только локальные), `uuid` (все), FID `@username:servername` (адрес для человека). Правило: **long-ID remote-пользователя не существует** — все обращения к нему только по uuid.
- Своя нода: `BeaconApi.GetServerInfo` → `server_name`, `federation_enabled`. Пустой `server_name` или `federation_enabled = false` ⇒ федеративный UI скрыт целиком.
- Признак «этот собеседник remote»: `ChatMember.server_name` не пуст и не равен своему `server_name` (эквивалентно — `ChatMember.user_id == 0` при заполненном `user_uuid`).

### 2. Поиск и резолв FID

- Когда строка поиска похожа на FID (`@?username:servername`, `username` по маске `^[a-zA-Z0-9_]{3,32}$`, `servername` — валидный hostname), клиент **вместо** `SearchUsers` зовёт `UsersApi.ResolveFederatedUser(fid)`.
- `servername`, совпадающий со своим, = локальный пользователь (обычный поиск).
- Ответ: `found`, `uuid`, `username`, `server_name`, имя/фамилия, `bio`, `avatar_url` (уже проксируемый URL своей ноды; пустой = скрыт privacy или отсутствует).
- `found = false` и ошибки резолва (`ServerNotFound`, недоступность ноды) — сообщения из таблицы ошибок (раздел 6).
- Результат — единичная карточка, не список; в неё обязательно выводится FID.

### 3. Начало и ведение переписки

- Первое сообщение remote-пользователю: `SendMessage` с `user_uuid` (вместо `user_id`) — чат создаётся сервером.
- `GetPersonChatId` — тоже принимает `user_uuid` (заполнять **либо** `user_id`, **либо** `user_uuid`).
- Дальше чат обычный: `chat_id` тот же на обеих нодах, `ListChats`/`ListMessages`/`SubscribeNewMessages` работают без изменений.
- Участники: `ChatMember.user_uuid` + `server_name`; имя/аватар remote-участника приходят в тех же полях, что у локальных (сервер подставляет кеш `RemoteUsers`).
- `Message.sender_uuid`/`federated_id` — для сопоставления сообщений remote-авторов; `Message.federated_read_by` (repeated uuid) — прочтения remote-участников, объединять с существующим `read_by` при рендере галочек.
- Группы: добавление remote-участника в группу отвергается сервером (`FederatedGroupsNotSupported`) — в UI выбора участников группы FID вводить нельзя (или показывать ошибку).

### 4. Отображение

- **FID в UI**: `@username:servername`. Полный FID показывать в карточке профиля, в шапке чата (под именем) и в списке участников; в списке чатов достаточно значка/подписи ноды, чтобы не ломать вёрстку.
- **Punycode-правило (обязательное)**: если `servername` содержит не-ASCII символы **или** смешение письменностей — показывать A-label (punycode, `xn--…`) без попытки «красиво» отрендерить Unicode. Алгоритм для клиента: сервер отдаёт servername уже в канонической A-label форме; клиент **ничего не декодирует обратно** в Unicode. Это и есть простейшая реализация правила — зафиксировать её в гайде явно, чтобы никто не «улучшил» рендер через IDN-декодирование.
- **Свои vs чужие**: у локальных участников подпись ноды не показывается вовсе (шум).
- **Typing**: `TypingEvent.user_uuid` заполнен ⇒ автор remote; подпись «@bob:node печатает…» или имя из карточки участника, если оно уже загружено.
- **Presence**: подписка на статусы обязана включать `user_uuids` (`SubscribeToOnlineStatus`/`ChangeUsersInSubscription`), иначе remote-собеседник вечно «не в сети». `UserOnlineStatus.user_uuid` заполнен ⇒ статус remote-пользователя. Статус `UNKNOWN` для remote означает «нода-партнёр не отдаёт статус» (privacy или обрыв стрима) — рисовать как «нет данных», не как «офлайн».

### 5. Файлы и аватары

- Клиент **не отличает** remote-вложение от локального: URL всегда указывает на свою ноду (`GetTempDownloadUrl` принимает и федеративные вложения).
- Метаданные (`file_name`, размер, тип, размеры картинки) приходят в сообщении и **достаточны для рендера без сети** — плитку/карточку файла рисовать сразу, не дожидаясь ссылки.
- Коды скачивания (контракт 3.5):

| Ответ | Значение | Поведение клиента |
|---|---|---|
| `503` + `Retry-After` | Нода-источник файла недоступна | Placeholder «Сервер собеседника недоступен» + кнопка «Повторить»; не считать файл потерянным |
| `404` | Файл недоступен окончательно (удалён, нет прав, скрыт privacy) | Placeholder «Файл недоступен», кнопку повтора не показывать |
| Оборванная загрузка (truncated) | Origin умер в процессе | Ретрай с `Range` (докачка), если клиент это умеет; иначе — повтор целиком |

- **`file_name` экранировать**: при отображении — как обычный текст (никакого HTML/markdown-парсинга), при сохранении на диск — вырезать разделители пути и `..` (path traversal). Это данные с чужой ноды.
- Аватар remote-пользователя приходит готовым URL своей ноды; при `404` — обычная «болванка» инициалов.

### 6. Ошибки федерации (таблица `x-error-code` → текст пользователю)

Свериться с фактическими `ErrorCode` в `Shared/BarkFluff.Shared.Exceptions` (для федеративных — `Federation/` и `Messages/`), минимум:

| Код | Когда | Что показать |
|---|---|---|
| `FederatedDmRejected` | Получатель запретил сообщения с других серверов | «Пользователь не принимает сообщения с других серверов» |
| `FederatedGroupsNotSupported` | Попытка добавить remote-пользователя в группу | «Пока нельзя добавлять пользователей с других серверов в группы» |
| `ServerNotFound` / резолв не удался | Нода не найдена/не отвечает | «Сервер не найден или недоступен» |
| `FederationNotConfigured` | Федерация выключена на своей ноде | Федеративный UI не показывать вовсе (см. раздел 1) |

### 7. Настройка приватности

- `GetPrivacySettings`/`UpdatePrivacySettings`, поле `deny_federated_dm`.
- В UI — положительная формулировка: «Разрешить сообщения с других серверов», значение `!deny_federated_dm`.
- Действует **только на новые** переписки: существующие федеративные чаты продолжают работать. Обязательно объяснить это подписью под тумблером — иначе пользователь считает настройку сломанной.

### 8. Деградация и совместимость

- Старый клиент против fed-ноды: proto только расширялся, ничего не ломается; федеративные чаты у него выглядят как чат с пустым/техническим именем участника — это ожидаемо (детали — этап 5.6).
- Новый клиент против ноды без федерации: `federation_enabled = false` ⇒ ветки федерации не активируются, поиск ведёт себя как раньше.

## Чего НЕ делать

- Не трогать код клиентов и бэкенда — этап документационный.
- Не изобретать новые RPC/поля: если в гайд просится то, чего нет в proto, — это дыра предыдущих фаз, останови и сообщи.
- Не описывать в гайде федеративные группы, звонки, боты, E2E — их нет в MVP.
- Не дублировать в гайде внутреннюю механику сервера (outbox, LWW, подписи) — гайд читает клиентский исполнитель, ему нужен контракт, а не устройство федерации.
