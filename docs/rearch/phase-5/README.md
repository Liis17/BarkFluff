# Фаза 5 — Клиенты — планы реализации

Детальные планы по каждому этапу Фазы 5 из [../10-roadmap.md](../10-roadmap.md). Каждый план самодостаточен: исполнитель должен суметь выполнить этап, прочитав только план + указанные в нём файлы, не восстанавливая контекст всей федерации.

**Суть фазы:** федерация становится видимой пользователю. Клиент умеет найти человека по адресу `@username:servername`, показать его карточку с указанием чужой ноды, написать ему (адресация по UUID вместо long-ID), отрисовать входящие сообщения/typing/онлайн-статус remote-собеседника, показать честный placeholder для недоступного вложения и дать тумблер «запретить сообщения с других серверов». **Бэкенд в этой фазе не трогаем** — все нужные RPC и поля появились в Фазах 0–4; исключение оговорено ниже (маршрут Beacon для Web).

Клиенты фазы (решение владельца при планировании): **Web, Android V1, macOS, iOS**. Windows WPF и Linux Qt в этой фазе **не дорабатываются** — они проходят как «старые клиенты» в этапе 5.6 (проверка деградации).

## Предпосылки (проверить до старта)

Фазы 0–4 должны быть завершены. Критично для этой фазы:

- 0.4 — proto-контракты: `oneof peer`-поля (`SendMessageRequest.user_uuid`, `GetPersonChatIdRequest.user_uuid`), `ChatMember.user_uuid`/`server_name`, `User.uuid`, `PrivacySettings.deny_federated_dm`, `UsersApi.ResolveFederatedUser`, `GetServerInfoResponse.server_name`/`federation_enabled`, `Message.federated_id`/`sender_uuid`, `UserOnlineStatus.user_uuid`, `TypingEvent.user_uuid`, `Subscribe*.user_uuids`.
- 2.1 — `ResolveFederatedUser` реально работает (резолв FID → карточка remote-пользователя).
- 2.3/2.4 — федеративные DM доставляются, `Message.federated_read_by` отдаётся `ListMessages`.
- 2.5 — `DenyFederatedDm` в privacy + ошибка `FederatedDmRejected` доходит до отправителя.
- 2.9 — Beacon отдаёт `server_name`/`federation_enabled` (клиент обязан знать имя своей ноды, чтобы отличать «своих» от remote).
- Фаза 3 — снапшот метаданных вложений + контракт недоступного origin (3.5: `503 + Retry-After` / `404`).
- Фаза 4 — presence/typing remote-пользователей (uuid-ветка Onliner, `TypingEvent.user_uuid`).

Если чего-то из перечисленного нет — соответствующий UI в клиенте делать нечем: остановись и уточни, а не выдумывай контракт.

## Обязательные правила для исполнителя

1. **Работать в текущей ветке** (`dev`), веток не создавать. После завершения каждого этапа — коммит (`git push` не делать). Формат сообщения: `feat(rearch-phase5): <этап> — <суть>`.
2. **Строго по плану.** Ничего сверх написанного: никаких федеративных групп/звонков/ботов (их нет на бэкенде), никакого редизайна существующих экранов, никаких «заодно поправил». Если план противоречит реальному коду — остановись и спроси, либо адаптируйся минимально и явно опиши отклонение в коммите.
3. **Бэкенд не менять.** Клиентские этапы правят только код своего клиента. Единственное исключение — этап 5.3: у `BarkFluff.Web` (YARP-прокси) нет маршрута на Beacon, без него веб-клиент не может узнать имя своей ноды; правка маршрутизации входит в 5.3 и ограничена этим.
4. **Обратная совместимость и выключенная федерация.** Нода может работать с `Federation:Enabled = false`: тогда `GetServerInfo` вернёт пустой `server_name`/`federation_enabled = false`, и **весь федеративный UI обязан быть скрыт** (поиск по FID, бейджи, тумблер приватности). Ни один существующий сценарий (локальные чаты, поиск по username, вложения) не должен изменить поведение.
5. **Референсные образцы, не строки.** Планы называют файлы-образцы — читай актуальное состояние образца и повторяй его стиль (архитектуру экрана, слой репозиториев, способ локализации); номера строк ориентировочные.
6. **Локализация обязательна.** Все новые пользовательские строки — через существующий механизм клиента и **на всех поддерживаемых языках** (Android: `values/`, `values-en/`, `values-de/`, `values-es/`, `values-zh-rCN/`; Apple: `Localizable.xcstrings` — en/de/es/ru/zh-Hans). Исключение — Web: там строки захардкожены по-русски, i18n-механизма нет, новые строки пишем так же (не заводить i18n «заодно»).
7. **Proto — только копирование из источника.** Единственный источник истины — `Shared/BarkFluff.Proto/*.proto`. Клиентские копии обновляются копированием файла целиком, руками proto не редактировать. Расхождение копии с источником — баг этапа.
8. **Безопасность отображения (жёстко):** servername со смешанными скриптами показывать в punycode ([../01-addressing-identity.md](../01-addressing-identity.md), И-4 из [../11-plan-review.md](../11-plan-review.md)); `filename` из федеративного снапшота экранировать при отображении и санитизировать при сохранении на диск (path traversal). Правила и готовый алгоритм — этап 5.1.
9. **Проверка каждого этапа** — раздел «Критерии готовности» в конце плана. Этап не завершён, пока все пункты не пройдены.
10. **Obsidian**: каждый клиентский этап дополняет свой файл (`Клиенты/Android.md`, `Клиенты/Web.md`, `Клиенты/macOS.md`, `Клиенты/iOS.md` + соответствующие `*-ProjectMap`), 5.1 создаёт `Клиенты/Federation-ClientGuide.md` и добавляет ссылку в `Index.md`. Это часть definition of done.

## Что проверяет исполнитель, а что — разработчик

В этом репозитории действует правило: **Docker для верификации не поднимать** (`CLAUDE.md`). Поэтому критерии готовности в планах фазы разделены:

- **Исполнитель (агент)** — обязан выполнить: сборка клиента, существующие тесты, статическая проверка (диффы, отсутствие регрессий в неизменных путях), самопроверка логики по чек-листу плана. Для Android — `./gradlew assembleDebug`; для Apple — `xcodebuild -scheme Barkfluff build` (или явно зафиксировать, что сборка Xcode недоступна в окружении); для Web — прогон скрипта генерации бандла, если менялись proto, и синтаксическая проверка JS.
- **Разработчик (человек)** — E2E-прогон на двух-нодовом стенде `Backend/dev-federation-testbed/` и дизайн-ревью. Эти пункты в планах помечены **[делает разработчик]**; исполнитель их не пропускает молча, а перечисляет в отчёте по этапу как оставшиеся.

## Решения, зафиксированные на уровне фазы

Приняты при планировании фазы; уточняют роадмап (правки [../10-roadmap.md](../10-roadmap.md) входят в этап 5.1):

- **Нумерация фазы изменена относительно роадмапа.** В роадмапе Фаза 5 была разбита по функциям (5.1 резолв/отправка, 5.2 UI, 5.3 регрессия) с оговоркой «по одному на клиент». На практике функциональное разбиение внутри одного клиента неразделимо (карточку remote-пользователя нельзя показать, не научившись его резолвить), а разбиение по клиентам позволяет вести этапы параллельно и независимо. Поэтому: **этап = клиент**, роадмаповые 5.1 и 5.2 выполняются внутри каждого клиентского этапа, роадмаповый 5.3 стал этапом 5.6.
- **Клиенты фазы: Web, Android V1, macOS, iOS.** Windows WPF и Linux Qt остаются на «читаемой деградации» (5.6). Android V2 (`Android/Barkfluff.ClientV2.Android`) — вне фазы: это отдельная незавершённая ветка клиента, федерацию в неё вносим, когда она догонит V1 по функционалу.
- **Apple-клиенты идут единым блоком 5.4 → 5.5.** iOS и macOS переиспользуют одни и те же локальные Swift-пакеты (`Mac/Barkfluff/Packages/BFCore|BFNetworking|BFProto`), подключённые в iOS-проект по относительному пути. Весь транспортный и доменный слой федерации пишется один раз в 5.4; 5.5 добавляет только iOS-экраны. Обратный порядок (iOS первым) сделал бы 5.4 почти пустым — но менять пакеты пришлось бы всё равно из iOS-этапа, что путает ответственность.
- **Web: Beacon недоступен веб-клиенту.** `Backend/BarkFluff.Web` проксирует восемь gRPC-сервисов (identity, users, messages, files, updates, onliner, fast-auth, calls) — Beacon среди них нет, а `beacon_api.proto` не входит в JS-бандл. Имя своей ноды взять неоткуда. Решение: в 5.3 добавляем маршрут+кластер Beacon в YARP (по образцу существующих) и `beacon_api.proto` в генерацию бандла. Это минимальная бэкенд-правка, оговорённая исключением из правила 3.
- **Тумблер приватности отображается инвертированно.** В proto поле называется `deny_federated_dm` (proto3-default `false` = текущее поведение «разрешено»), в UI показываем положительную формулировку «Разрешить сообщения с других серверов» = `!deny_federated_dm`. Инверсия делается в слое маппинга клиента, а не в тексте настройки.
- **Presence remote-пользователей — не «заодно», а обязательная часть.** Клиент, подписавшийся на статусы только по `user_ids`, для remote-собеседника всегда покажет «не в сети». Подписка обязана включать `user_uuids` (Фаза 4).
- **Единый гайд вместо копипасты в четырёх планах.** Правила отображения FID, punycode, обработки ошибок федерации и placeholder'ов вынесены в `Клиенты/Federation-ClientGuide.md` (этап 5.1) — клиентские планы на него ссылаются, а не переписывают. Это тот же приём, что у существующих `*-ClientGuide.md` в vault.
