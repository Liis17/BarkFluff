# Этап 0.5 — Исследование: Ed25519 для .NET 10

## Цель

Выбрать способ работы с Ed25519 (генерация ключей, подпись, проверка) для Federation-сервиса и задокументировать решение. Результат — **отчёт + мини-прототип**, никакого продакшен-кода. Этап независим от 0.1–0.4.

## Контекст

Federation подписывает каждый исходящий S2S-запрос Ed25519-ключом ноды и проверяет подписи входящих ([../02-trust-and-certs.md](../02-trust-and-certs.md)). Объём операций: подпись — на каждый исходящий S2S-вызов, проверка — на каждый входящий; presence/typing могут дать сотни операций в секунду на нагруженной ноде. Ключи — raw 32 байта (публичный) / 32-байтный seed (приватный), формат совместимый с RFC 8032 (важно для сторонних реализаций нод).

## Вопросы, на которые обязан ответить отчёт

1. **Есть ли Ed25519 в BCL .NET 10** (`System.Security.Cryptography`)? На момент .NET 9 его не было (были RSA/ECDSA/EdDSA — нет; в .NET 10 появились пост-квантовые ML-DSA — это НЕ Ed25519). Проверить по актуальной документации (используй Context7 / официальные docs Microsoft, не полагайся на память): тип `Ed25519`, `SignatureAlgorithm`, что-либо в `Microsoft.Bcl.Cryptography`. Если появился — он кандидат №1 (нет внешних зависимостей).
2. **Кандидаты-библиотеки** (если BCL не умеет). Для каждой: NuGet-имя, актуальная версия (проверь через NuGet MCP `get-latest-package-version`), лицензия, managed или native, активность поддержки:
   - `NSec.Cryptography` — обёртка libsodium (native!);
   - `BouncyCastle.Cryptography` (официальный пакет BC; `Org.BouncyCastle.Math.EC.Rfc8032.Ed25519`) — полностью managed;
   - `Chaos.NaCl` / форки — managed, но малоподдерживаемый;
   - `Geralt` — современная обёртка libsodium (native).
3. **Совместимость с chiseled-контейнерами** — критично: все сервисы деплоятся из `aspnet:10.0-noble-chiseled` (минимальный образ без пакетного менеджера). Native-библиотеки (libsodium) требуют, чтобы `.so` корректно попал в publish и нашёл зависимости в chiseled-окружении. Managed-решение (BouncyCastle) снимает проблему полностью. Проверить фактически: собрать тестовый контейнер на chiseled-базе с каждым финалистом и выполнить подпись/проверку внутри.
4. **Производительность**: бенчмарк подписи и проверки (BenchmarkDotNet или простой Stopwatch-цикл, 10k операций): ops/sec для финалистов. Порог достаточности: ≥ 5000 verify/sec на одном ядре — с запасом покрывает любую реалистичную S2S-нагрузку; если все кандидаты выше порога, производительность перестаёт быть фактором выбора.
5. **Интероперабельность**: подпись, сделанная кандидатом, должна проверяться референсной реализацией (и наоборот). Тест-вектора — из RFC 8032, секция 7.1 (там готовые пары ключ/сообщение/подпись). Прогнать минимум TEST 1–3.
6. **Экспорт/импорт ключей**: raw 32 байта seed/public — без ASN.1/PKCS#8-обёрток (для `/.well-known` и Navigator публикуется raw base64). Убедиться, что API кандидата это умеет напрямую или тривиально.
