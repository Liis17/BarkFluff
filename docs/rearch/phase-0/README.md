# Фаза 0 — Фундамент идентичности: планы реализации

Детальные планы по каждому этапу Фазы 0 из [../10-roadmap.md](../10-roadmap.md). Каждый план самодостаточен: исполнитель (Sonnet 5) должен суметь выполнить этап, прочитав только план + указанные в нём файлы, не восстанавливая контекст всей федерации.

**Суть фазы:** подготовить схемы данных и контракты к федерации, **не включая никакой федеративной логики**. Всё катится в прод независимо: после фазы 0 система ведёт себя ровно как до неё, просто у пользователей появились UUID, у сообщений — метка изменения, в proto — новые (пока не используемые) поля и сервисы.

## Обязательные правила для исполнителя

1. **Работать в текущей ветке** (`dev`), веток не создавать. После завершения каждого этапа — коммит (`git push` не делать). Формат сообщения: `feat(rearch-phase0): <этап> — <суть>` или `docs(...)` для 0.5.
2. **Строго по плану.** Ничего сверх написанного: никаких «заодно отрефакторю», никакой федеративной логики (она в фазах 1+). Если план противоречит реальному коду (файл переехал, номер поля занят) — остановись и спроси, либо адаптируйся минимально и явно опиши отклонение в коммите.
3. **Обратная совместимость — жёсткое требование.** Существующие клиенты (Android, WPF, iOS/macOS, Linux, Web) работают против изменённого бэкенда без перекомпиляции. Поэтому: в proto только добавление полей/RPC с новыми номерами, никаких переименований, удалений, смены типов и переносов существующих полей в oneof.
4. **Миграции EF Core**: известный баг — `dotnet ef migrations add` может падать с `MissingMethodException` (баг тулинга, воспроизводился на Users). Порядок действий:
   - сначала попробовать `dotnet tool restore && dotnet tool run dotnet-ef migrations add <Name> --project <csproj>`;
   - если падает — писать миграцию **вручную**: три файла — `<timestamp>_<Name>.cs`, `<timestamp>_<Name>.Designer.cs` (обязателен: без `[Migration("...")]`-атрибута EF не включит миграцию в `Database.Migrate()`), и обновление `*ContextModelSnapshot.cs`. Образец — соседние миграции в той же папке (например `20260705130000_AddUserIsBot.*` в Users).
   - Миграции применяются автоматически при старте сервиса — отдельного `database update` в проде не нужно, но локально прогнать обязательно.
5. **Obsidian**: по правилам проекта после изменения сервиса обновить его файл в `Obsidian/ClaudeVault/Backend/*.md` (коротко: что добавлено). Это часть definition of done каждого этапа.
6. **Проверка каждого этапа** — раздел «Критерии готовности» в конце плана. Этап не завершён, пока все пункты не пройдены.
7. Контекст решений — в родительских доках [../README.md](../README.md) и далее; читать их целиком не нужно, каждый план ссылается на конкретные разделы, когда это важно.
