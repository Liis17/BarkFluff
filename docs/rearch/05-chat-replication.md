# 05 — Федеративные DM: копии чата и разрешение конфликтов

## Принятая модель

**Каждый сервер хранит свою копию чата**, чтобы чат был доступен обоим участникам на их нодах (в т.ч. когда вторая нода лежит). Копии синхронизируются доставкой событий; расхождения решаются правилом **LWW: актуальна версия сообщения с более новой UTC-меткой последнего изменения**.

Отвергнутые альтернативы: «чат живёт только на сервере-инициаторе» (чат умирает вместе с нодой-хозяином, вся история читается по сети) и полная репликация DAG а-ля Matrix (слишком дорого).

## Идентификаторы

| Сущность | Сейчас | Для федерации |
|----------|--------|---------------|
| `Chat.Id` | `Guid` — генерируется при создании | **Годится как есть**: Guid глобально уникален. Нода-инициатор генерирует, вторая нода создаёт копию с тем же Id |
| `Message.Id` | `bigserial` per-нода — **коллизии гарантированы** | Новое поле `Message.FederatedId` (`uuid NULL`): генерируется домашней нодой автора при отправке. Обе копии сообщения имеют одинаковый `FederatedId`; локальный bigserial остаётся PK и остаётся в клиентском API своей ноды |
| Участники | `ChatMembers.UserId` (long) | Для remote-участника — `UserUuid` ([01-addressing-identity.md](01-addressing-identity.md)) |

Для не-федеративных чатов ничего не меняется (`FederatedId = NULL`).

## Метка последнего изменения (основа LWW)

В `Message` сейчас есть `SentAt` и `EditedAt` (nullable, только для правок). Для детерминированного LWW нужен единый маркер. Добавить:

- `Message.LastChangeAt` (`timestamptz NOT NULL`) — выставляется при создании (=SentAt), правке, удалении, откреплении и любом будущем изменяющем действии. Backfill: `COALESCE(EditedAt, SentAt)`.
- Правило применения входящего события: **применить, только если `event.origin_ts_ms > local.LastChangeAt`**; иначе событие устарело — игнорировать (ответить Ok, это не ошибка).
- Tie-break при равенстве меток (и защита от clock skew): сравнить `(origin_ts_ms, origin_server, event_id)` лексикографически — обе ноды придут к одному победителю.

**Требование к нодам — NTP.** Часы, ушедшие сильнее допустимого окна подписи (5 мин), ломают не только LWW, но и приём запросов вообще ([02-trust-and-certs.md](02-trust-and-certs.md)) — рассинхрон обнаруживается рано через `Ping`.

Отдельный инвариант, снижающий остроту LWW: **редактировать и удалять сообщение может только его автор** (уже так). Значит, конкурирующие правки одного сообщения возможны только с разных устройств одного пользователя — они сериализуются его домашней нодой, и origin-метка одна. Реальные конфликты копий сводятся к переупорядочиванию доставки и повторам — их закрывают идемпотентность по `event_id` и LWW-проверка.

## Жизненный цикл федеративного DM

### Создание чата + первое сообщение

```
1. A@nodeA пишет @bob:nodeB (резолв уже сделан, есть RemoteUser uuid)
2. Messages(A): создаёт Chat {Id=guid, Type=Regular, federated, члены: A(long+uuid), bob(uuid)},
   сохраняет Message {FederatedId, LastChangeAt}, публикует NewMessageEvent (+remote-инфо)
3. Federation(A): outbox → DeliverEvents(nodeB): [ChatCreated, NewMessage]
4. Federation(B): проверки → MessagesServerApi.ImportFederatedChat + ImportFederatedMessage
5. Messages(B): создаёт копию Chat с тем же Id, члены: bob(long+uuid), A(uuid);
   проверяет privacy-настройку боба «запрет федеративных DM» → если запрещено,
   отвечает ошибкой FederatedDmRejected (нода A помечает чат отклонённым, автору — ошибка);
   иначе вставляет сообщение → NewMessageEvent → Updates/пуш работают как обычно
```

Анти-дубль: пара `(uuid_A, uuid_B)` нормализуется — федеративный DM между двумя UUID уникален (аналог существующих `PrivateUserLowId/HighId`, но по UUID). Гонка «оба написали друг другу одновременно» → обе ноды создали чаты с разными ChatId → детерминированное слияние: побеждает чат с меньшим `ChatId` (лексикографически), второй чат обе ноды помечают merged и пересылают его сообщения в победивший. Это самый сложный корнер-кейс — вынесен отдельной задачей в [10-roadmap.md](10-roadmap.md).

### Отправка последующих сообщений

Симметрично: авторская нода сохраняет → outbox → вторая нода импортирует. Каждая нода раздаёт realtime/пуши только **своим** пользователям.

### Правка / удаление

- `MessageEditedPayload { chat_id, federated_message_id, new_content, attachments, origin_ts_ms }` — применяется через LWW.
- Удаление — soft-delete (как сейчас), `MessageDeletedPayload`. Удаление побеждает правку при более новой метке, и наоборот. «Воскрешение» удалённого более поздней правкой допускаем? **Нет**: удаление терминально (локальное правило «редактировать удалённое нельзя» уже есть) — правка с меткой новее удаления игнорируется. Это осознанное отступление от чистого LWW, зафиксировать в протоколе.
- Вложения при правке: список file_ref пересоздаётся (существующая семантика).

### Read receipts

`MessagesReadPayload { chat_id, reader_uuid, read_federated_message_ids[] / up_to }`. На принявшей ноде пишется в `FederatedReadStates` (не в `ReadBy`-массив long). Клиентам отдаётся объединение локальных и федеративных прочтений. Read-события не критичны к порядку — идемпотентны по природе («прочитано до X»).

### Catch-up после даунтайма

Outbox отправителя ретраит до 7 суток — обычно достаточно. Для более длинного даунтайма и для сверки:

- `FetchChatHistory(chat_id, since_ts / cursor)` — нода запрашивает у партнёра события чата, которые пропустила. Вызывается: при `DeadLetter`-уведомлении, при явном «Синхронизировать» в AdminPanel, при обнаружении дыры (пришёл edit на неизвестный `federated_message_id` → дозапросить сообщение).
- Ответ отдаёт сообщения с их актуальным состоянием (не журнал промежуточных правок) — импорт через ту же LWW-логику.

## Что меняется в Messages-сервисе (сводка; детали в [08-service-migration.md](08-service-migration.md))

1. Схема: `Chat.IsFederated`/список remote-участников, `ChatMembers.UserUuid NULL`, `Message.FederatedId NULL`, `Message.SenderUuid NULL`, `Message.LastChangeAt`, таблица `FederatedReadStates`, нормализованная пара UUID для федеративных DM.
2. Новые server-RPC (`TokenType.Service`, зовёт только Federation): `ImportFederatedChat`, `ImportFederatedMessage`, `ApplyFederatedEdit`, `ApplyFederatedDelete`, `ApplyFederatedRead`, `ExportChatEvents(chat_id, cursor)` (обслуживает FetchChatHistory).
3. `SendMessage`: принять remote-получателя (`oneof peer` c uuid), при федеративном чате — проставлять `FederatedId`/`LastChangeAt` и remote-инфо в `NewMessageEvent`.
4. `ListChats`/`ListMessages`/`GetChatInfo`: отдавать участников-remote (uuid, FID, кешированный профиль из Users.RemoteUsers), не падать на `UserId = NULL`.
5. Валидация: импортируемые события принимать только для чатов, где нода-origin действительно участник; лимиты (текст ≤ 4096, вложения ≤ 10) применять и к импортируемым.

## Пуши и realtime

Работают штатно: копия сообщения на ноде получателя порождает обычный `NewMessageEvent` → Updates (стримы) и отложенный пуш через CloudMessaging **этой** ноды. Единственная доработка — отображаемое имя отправителя для пуша брать из `RemoteUsers` (FID при отсутствии имени).

## Ограничения MVP (фиксируем явно)

- Только 1-на-1. Группы с remote-участниками: `AddUser` с FID возвращает понятную ошибку `FederatedGroupsNotSupported`.
- Приватные (passphrase) и секретные (Signal) чаты — только локальные; федеративные E2E — будущая фаза ([09-problems-open-questions.md](09-problems-open-questions.md)).
- Закрепы (pin) в федеративных DM: MVP — не федерировать (локальная фича каждой стороны) или запретить; решить при реализации — отмечено открытым вопросом.
- Пересланные сообщения из федеративного чата в локальный — работают (снапшот-модель forward уже самодостаточна), вложения тянутся с origin ([06-files.md](06-files.md)).
