# BarkFluff

Распределённый мессенджер реального времени: самостоятельные ноды, backend-микросервисы на .NET 10 (gRPC, RabbitMQ/MassTransit, EF Core) и клиенты для Android, Windows (WPF, WinUI), macOS, iOS, Linux (Qt) и веба. Backend — `Backend/`, общие библиотеки и `.proto` — `Shared/`, тесты — `Tests/`, инструменты (Builder конфигурации ноды) — `Tools/`, Docker-окружения — `Docker/`. Подробная карта проектов — в памяти проекта.

## Память проекта — Obsidian

Vault: `Obsidian/BarkFluffVault/` — актуальное описание устройства проекта. Пути исходников в заметках отсчитываются от корня репозитория.

| Раздел | Содержание |
|--------|------------|
| `Obsidian/BarkFluffVault/Index.md` | Навигация по всем заметкам — начинай с неё |
| `Obsidian/BarkFluffVault/Architecture.md` | Проекты, стек, границы, основные потоки и ограничения |
| `Obsidian/BarkFluffVault/Glossary.md` | Словарь терминов предметной области |
| `Obsidian/BarkFluffVault/Testing.md` | Тестовые проекты, провайдеры БД и ограничения проверок |
| `Obsidian/BarkFluffVault/Backend/` | Backend-сервисы: назначение, контракты, потоки, карты исходников |
| `Obsidian/BarkFluffVault/Shared/` | Общие библиотеки: Proto, Auth, Queue, Exceptions, Identity, BFT |
| `Obsidian/BarkFluffVault/Clients/` | Клиентские приложения по платформам |
| `Obsidian/BarkFluffVault/Tools/` | Инструменты, включая Builder |

### Как пользоваться памятью

- Перед задачей прочитай `Index.md` и заметки, относящиеся к задаче.
- Используй память для поиска информации и понимания проекта: где находится компонент, какие у него контракты и связи, почему принято решение. Не перечитывай ради этого весь код.
- Читай исходники в тех местах, которые меняешь, и там, где заметка расходится с кодом или не покрывает вопрос. Факт, на котором основано изменение, проверяй по коду.

### Словарь терминов

- Называй понятия предметной области терминами из `Glossary.md` — в коде, тестах, заметках, issues, коммитах и PR. Синонимы из «Избегать» не используй.
- Если пользователь употребляет термин иначе, чем в словаре, или слово, которое может означать разные понятия, — сразу уточни, что он имеет в виду.
- Если слова пользователя расходятся с кодом (например, в коде понятие устроено иначе), покажи расхождение и спроси, что верно.
- Когда новое понятие или основной термин согласованы, добавь их в `Glossary.md` в той же задаче. Общие понятия программирования и детали реализации в словарь не добавляй.

### Как поддерживать память в актуальном состоянии

- Память должна соответствовать текущему коду. Если изменение затрагивает описанный контракт, поток, зависимость, ограничение или решение, обнови заметку в той же задаче: сервис — `Backend/`, библиотека — `Shared/`, клиент — `Clients/`, общий паттерн — `Architecture.md`.
- Найденное расхождение между заметкой и кодом исправляй, даже если оно не связано с задачей.
- Для нового значимого компонента найди подходящую заметку или создай новую и добавь её в `Index.md`. Внутренние вспомогательные функции, косметические правки и рефакторинг без изменения поведения не документируй.
- Контракты описывай по смыслу. Не копируй код и полные списки методов и полей. Указывай реальные пути и важные символы.
- Причины решений записывай только подтверждённые: документацией, комментарием или словами пользователя. Неизвестную причину не выдумывай.
- Удалённое и неверное убирай из описаний. Changelog, дневники задач и датированные записи не веди: история хранится в git.
- Файлы заметок и папки доменов называй по-английски; текст может быть на русском. При переименовании исправляй wikilinks, ссылки и пути в `AGENTS.md`.

## Git и Pull Request

### Ветки

| Ветка | Назначение |
|-------|------------|
| `master` | Основная, релизная; ветка по умолчанию на GitHub. Изменения — только PR из `dev` |
| `dev` | Промежуточный канал перед релизом. Изменения — только PR из `nightly` |
| `nightly` | Ветка разработки: сюда направляются все новые изменения через PR |

Схема продвижения: `nightly → dev → master`. Все три ветки защищены rulesets (`.github/rulesets/`): изменения только через PR, обязательная проверка `Tests passed`, без force push и удаления.

- Не коммить напрямую в `nightly`, `dev` и `master`. Работай в отдельной рабочей ветке или worktree, созданной от актуальной `nightly`.
- Имя рабочей ветки: `<type>/<short-description>`, где `type` — тип из формата коммитов.
- Если текущая ветка долгоживущая, создай рабочую ветку от актуальной `nightly`. Если ты уже в рабочей ветке или worktree от `nightly`, продолжай в ней. Если база ветки — `dev` или `master` либо её нельзя достоверно подтвердить, остановись и сообщи пользователю.

### Коммиты

- Формат — Conventional Commits: `<type>(<scope>): <описание>`, типы `feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `ci`. Scope — затронутый компонент, например `android`, `web`, `messages`, `updates`, `admin`, `obsidian`; при изменении нескольких компонентов scope можно опустить.
- Один коммит — одна логическая группа изменений. Несвязанные изменения разделяй на отдельные коммиты.
- Заголовок кратко и понятно описывает результат. Язык: русский или английский — в истории используются оба.
- Всё сообщение — ориентировочно до 200 символов. Это не жёсткий предел: сначала сокращай формулировку, а если не помещается — проверь, не стоит ли разделить коммит.
- В своей рабочей ветке или worktree коммить самостоятельно после каждого завершённого этапа. Push — только в свою рабочую ветку.
- Перед коммитом проверяй `git diff --staged`: в коммит попадают только изменения текущей задачи. Чужие незакоммиченные изменения не трогай.
- Не применяй `git reset --hard`, `git clean -fd` и force push без явного разрешения.
- Не добавляй подписи AI, `Co-Authored-By` и упоминания агента без запроса.

### Pull Request

- Изменения попадают в `nightly` через Pull Request из рабочей ветки. Продвижение `nightly → dev` и `dev → master` — PR из соответствующей исходной ветки.
- Создавай PR самостоятельно, когда задача завершена и проверена. Целевая ветка — `nightly`, если пользователь не указал иное.
- Один PR решает одну задачу. Не объединяй несвязанные исправления, рефакторинг и новые функции. Не создавай дубль, если открытый PR для задачи уже есть.
- Название PR следует формату коммитов и описывает результат, а не действия агента. Примеры: `fix(messages): prevent duplicate message publication`, `feat(android): restore attachment drafts after restart`, `docs(obsidian): clarify project memory rules`.
- Перед созданием PR проверь полный diff относительно целевой ветки, выполни доступные целевые проверки, обнови память проекта и убедись, что в diff нет секретов, временных файлов и несвязанных правок.

Описание PR: используй структуру ниже.

**Summary** — что изменено и какую проблему решает; основные технические решения.
**Testing** — какие проверки выполнены, их результаты, что не проверено и почему.
**Compatibility & Risks** — затронутые backend-сервисы, Shared и клиентские платформы; изменения Proto, HTTP API, DTO, событий RabbitMQ, БД и конфигурации; риски развёртывания.
**Visual Changes** — скриншоты до и после, только для изменений UI; для существенных изменений анимаций — короткое видео, если возможно.

Пустые разделы не добавляй.

### CI и merge

- CI — `.github/workflows/ci.yml`. PR в `nightly` запускает проверки затронутых компонентов; PR в `dev` и `master` проверяют только ветку-источник; push в `nightly`, `dev`, `master` — сборка и публикация без повторных тестов. Итоговая проверка PR — `Tests passed`.
- После push самостоятельно отслеживай проверки GitHub Actions; подтверждённые падения исправляй в той же ветке.
- Не утверждай, что CI прошёл, пока это не подтверждено GitHub.
- Замечания ревьюеров, в том числе автоматических, проверяй по коду. Исправляй подтверждённые проблемы; для ложных срабатываний указывай техническую причину.
- Не выполняй merge без явного разрешения пользователя или вызова `/merge`.

### Обновление ветки и merge

- Способ слияния PR: только merge commit — squash и rebase запрещены (так настроены репозиторий и rulesets).
- Отставшая ветка: подтягивай родителя через `git merge`, историю открытого PR не переписывай.
- Конфликты: однозначные конфликты решай самостоятельно, сохраняя намерения обеих сторон; при неоднозначных остановись и спроси.
- После merge: проверь, что изменения отражены в памяти проекта; отследи CI сборки в целевой ветке и исправь подтверждённые падения новым PR; дай краткий отчёт. Рабочую ветку и worktree не удаляй.
- Не обходи защиту веток и проверки: никаких `--admin`, `--no-verify`, отключения или пропуска тестов ради зелёного CI.

### Issues

- Задачи и баги ведутся в issues GitHub этого репозитория.
- Читай через `gh`: поиск `gh issue list --state open --search "<слова>"`, просмотр `gh issue view <N> --comments`.
- Создавать issues, комментировать, менять метки, исполнителей и статус — только по запросу пользователя.
- В PR, который решает issue, указывай `Closes #N`; если решает частично — `Refs #N`.

## Проверка изменений

### Команды

| Действие | Команда |
|----------|---------|
| Сборка сервиса | `dotnet build Backend/BarkFluff.<Service>/BarkFluff.<Service>.csproj` |
| Тесты сервиса | `dotnet test Tests/BarkFluff.<Service>.Tests/BarkFluff.<Service>.Tests.csproj` |
| Один тест | `dotnet test <проект тестов> --filter FullyQualifiedName~<Класс.Метод>` |
| Builder | `dotnet build Tools/BarkFluff.Builder/BarkFluff.Builder.csproj`, `dotnet test Tests/BarkFluff.Builder.Tests/BarkFluff.Builder.Tests.csproj` |
| Android — сборка | `cd Android && ./gradlew :app-v1:assembleDebug` |
| Android — тесты | `cd Android && ./gradlew :core:testDebugUnitTest :app-v1:testNightlyDebugUnitTest` |
| Windows WPF | `dotnet build Windows/BarkFluff.Client.WPF/BarkFluff.Client.WPF.csproj` (на не-Windows добавь `-p:EnableWindowsTargeting=true`) |
| Windows WinUI | `dotnet build Windows/BarkFluff.Client.WinUI/BarkFluff.Client.WinUI.csproj -p:Platform=x64` |
| Web — линтер и форматирование | `npm --prefix Backend/BarkFluff.Web/scripts run lint`, `npm --prefix Backend/BarkFluff.Web/scripts run format:check` |
| Скрипты CI | `python3 -m unittest discover -s .github/tests -p 'test_*.py'` |

`<Service>` — имя сервиса, например `Messages`.

### Затронутые компоненты

- Backend: проверь затронутые `Host`, `Features`, `Domain`, `Services`, `Infrastructure`, `Persistence`, MediatR-обработчики, межсервисные gRPC-клиенты и MassTransit consumers изменённого кода.
- Общая инфраструктура: при изменениях в `Shared/` и `Backend/BarkFluff.GrpcServer/` проверь зависимые сервисы и клиенты.
- Контракты: при изменении `.proto` в `Shared/BarkFluff.Proto/`, общих DTO, событий в `Shared/BarkFluff.Shared.Queue/`, HTTP API, схем БД и конфигурации проверь производителей и потребителей, включая версии, которые используют клиенты.
- Клиенты: учитывай Android, Windows (WPF и WinUI), macOS, iOS, Linux Qt и веб-клиенты там, где их затрагивает изменение. Меняй только затронутые платформы и явно указывай, что не проверено.
- Совместимость: не ломай существующие контракты и сохранённые данные без явной необходимости.
- Обратные операции: если добавлена возможность создать, включить или подключить, проверь, нужны ли удаление, отключение и восстановление.

### Тесты

- Проверяй минимальный достаточный набор: изменённый компонент, затронутые тесты и зависимые контракты. Полную сборку и все тесты запускай для сквозных изменений.
- Для исправления бага по возможности добавляй тест, воспроизводящий проблему. Для новой значимой логики добавляй тесты на поведение и существенные ошибки.
- Не пиши тесты, которые повторяют реализацию или проверяют очевидную передачу параметров.
- Для асинхронных операций жди наблюдаемое событие или состояние, а не произвольную задержку.
- Никогда не сообщай, что тесты прошли, если они не запускались. Если проверка невозможна, назови причину.

### Безопасность окружения

- Не запускай миграции и не изменяй рабочие БД (EF Core) без явного разрешения.
- Не выполняй `docker compose down -v`, удаление Docker volumes, сброс БД и не удаляй пользовательские данные без разрешения. Persistent-данные и резервные копии хранятся рядом с compose в `Docker/nightly/` и `Docker/setup/`.
- Останавливай только процессы, принадлежность которых текущей задаче подтверждена. Не используй `pkill -f` по шаблону имени.
- Не изменяй секреты, токены и реальные конфигурации (Settings, `appsettings*.json`, `.env`, GitHub Secrets, Android `local.properties`) без необходимости и разрешения. Не выводи значения секретов в логи и отчёты.
- Для тестов используй отдельное окружение и изолированные данные.
- Не коммить временные файлы агента, дампы, логи и исследовательские заметки.

### Завершение задачи

Перед завершением проверь:

1. Реализованы ли все запрошенные требования.
2. Не затронуты ли лишние файлы.
3. Проверены ли зависимые контракты и платформы.
4. Не нарушена ли обратная совместимость.
5. Обновлена ли память проекта.
6. Выполнены ли доступные целевые тесты.

В финальном ответе кратко сообщи: что изменено, что проверено и с каким результатом, что не удалось проверить, какие риски остались.

## Документация библиотек — Context7

Для актуальной документации внешних библиотек используй MCP-сервер Context7: сначала `resolve-library-id`, затем запрос документации с конкретной темой.

- перед использованием API библиотек и фреймворков проекта (ASP.NET Core, Grpc.AspNetCore, MassTransit, EF Core, MediatR, Jetpack Compose, WinUI/WPF и др.) — сверяй сигнатуры и поведение для версии из manifests;

- при обновлении версий и миграции между мажорными версиями;

- Версию библиотеки бери из manifests и lock-файлов проекта (`*.csproj`, `Directory.*.props`, `global.json`, `*.gradle.kts`, `package.json`) и запрашивай документацию для неё.
- Context7 не заменяет код проекта: устройство проекта смотри в памяти и исходниках, а Context7 — только для внешних библиотек.
- Если Context7 недоступен в сессии, сообщи об этом и используй официальную документацию библиотеки. Не опирайся молча на память модели.

## Дополнительные правила проекта

### Архитектурные границы

- Не размещай бизнес-логику в gRPC-хостах и HTTP-маршрутах: транспорт принимает и проверяет запрос, вызывает команду или сервис и возвращает результат.
- Соблюдай существующие CQRS/MediatR, DI, XAuth и инфраструктурные паттерны конкретного сервиса.
- Перед созданием общей абстракции проверь реализации в `Shared/` и `Backend/BarkFluff.GrpcServer/`. Не выноси туда логику только ради одного потребителя.

### RabbitMQ и распределённая система

- Учитывай доставку at-least-once и повторные события. Consumers должны безопасно обрабатывать повторную доставку там, где это требуется бизнес-логикой.
- Для связанных изменений БД и публикации событий в Messages и Federation используй существующие `MessageOutboxEntry`/`MessageOutboxDispatcher` и `FederationOutbox`/`OutboxWriter`/`OutboxDispatcher`. В остальных сервисах следуй принятому способу и явно указывай риск рассинхронизации при сбое между записью и публикацией.
- Различай competing consumers и broadcast на все экземпляры; общая очередь не доставляет событие каждому экземпляру.
- Не добавляй блокирующие операции в горячий путь обработки сообщений. Учитывай отмену, таймауты и ошибки межсервисных gRPC/HTTP-вызовов и потоков.
- Не меняй правила XAuth, `x-auth-token`, служебной metadata и клиентских interceptors без отдельного обоснования.

### Производительность

- Для изменений в горячем пути оцени влияние на задержки, память, CPU и число сетевых обращений. Избегай лишних запросов к БД, повторной сериализации и ненужных аллокаций.
- Не передавай крупные объекты через gRPC, gRPC streaming и HTTP без необходимости; не блокируй асинхронный код синхронным ожиданием.
- В UI избегай ненужных перерисовок, постоянных анимаций и полной переработки списков при небольших изменениях.
- Не оптимизируй без доказанной причины: сначала установи проблему.

## Поведенческие правила

Правила для снижения типичных ошибок при написании кода.

**Компромисс:** эти правила смещают баланс в сторону осторожности, а не скорости. Для тривиальных задач — действуй по ситуации.

### 1. Думай перед кодом

**Не предполагай. Не скрывай сомнения. Показывай компромиссы.**

Перед реализацией:

- Явно формулируй свои допущения. Если не уверен — спроси.
- Если возможны несколько трактовок — покажи их, не выбирай молча.
- Если есть более простой подход — скажи об этом. Возражай, когда это оправдано.
- Если что-то неясно — остановись. Назови, что именно сбивает с толку. Спроси.

### 2. Простота прежде всего

**Минимум кода, решающего задачу. Ничего спекулятивного.**

- Никаких функций сверх запрошенного.
- Никаких абстракций для одноразового кода.
- Никакой «гибкости» или «настраиваемости», которую не просили.
- Никакой обработки ошибок для невозможных сценариев.
- Если написал 200 строк, а можно 50 — перепиши.

Спроси себя: «Сказал бы senior-инженер, что это переусложнено?» Если да — упрости.

### 3. Хирургические правки

**Трогай только то, что необходимо. Убирай только свой беспорядок.**

При редактировании существующего кода:

- Не «улучшай» соседний код, комментарии или форматирование.
- Не рефактори то, что не сломано.
- Соблюдай существующий стиль, даже если сделал бы иначе.
- Если заметил несвязанный мёртвый код — упомяни, но не удаляй.

Когда твои изменения создают «сирот»:

- Удаляй импорты/переменные/функции, которые стали неиспользуемыми ИЗ-ЗА твоих изменений.
- Не удаляй ранее существовавший мёртвый код без запроса.

Тест: каждая изменённая строка должна напрямую следовать из запроса пользователя.

### 4. Выполнение, ориентированное на цель

**Определи критерии успеха. Повторяй до проверки.**

Превращай задачи в проверяемые цели:

- «Добавь валидацию» → «Напиши тесты на невалидный ввод, затем сделай, чтобы они проходили»
- «Исправь баг» → «Напиши тест, воспроизводящий баг, затем сделай, чтобы он проходил»
- «Отрефактори X» → «Убедись, что тесты проходят до и после»

Для многошаговых задач кратко изложи план:

```
1. [Шаг] → проверка: [контроль]
2. [Шаг] → проверка: [контроль]
3. [Шаг] → проверка: [контроль]
```

Сильные критерии успеха позволяют работать автономно. Слабые («просто заставь работать») требуют постоянных уточнений.

**Эти правила работают, если:** в диффах меньше лишних изменений, меньше переписываний из-за переусложнения, а уточняющие вопросы возникают до реализации, а не после ошибок.
